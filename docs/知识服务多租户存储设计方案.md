# 知识服务多租户存储改造设计方案

> 目标读者：本项目开发者与运维。
> 状态：**已在代码中实施（P1/P2/P3/P6 完成并实测），生产切换（P4）为待执行步骤** ——
> 见 §14「实施状态」。
> 文中所有「实测」结论均在本机环境验证过，命令与观察结果附在对应位置。

---

## 1. 为什么必须改：当前是「过滤」而不是「隔离」

### 1.1 现状

知识服务的图谱（LightRAG）目前是**单个共享图谱 + 应用层过滤**：

- LightRAG 以独立容器 `huizhi-lightrag` 运行，文件型存储落在 `/data/lightrag`
  （实测容器内文件：`kv_store_text_chunks.json`、`kv_store_full_relations.json`、
  `kv_store_entity_chunks.json`、`kv_store_doc_status.json`、
  `graph_chunk_entity_relation.graphml`）。
- 知识服务通过 HTTP 调 LightRAG 的 `/query`、`/query/data`。
- 因为服务端的 `rag.workspace` 是进程级、`/query` 系列接口**不接受按请求的
  workspace**（实测：`query_routes.py` 中 `workspace` 出现 **0** 次），所以现有实现
  改为「写入时把空间编进来源标识（文件名前缀），查询后按该前缀过滤」。

### 1.2 问题的本质

这是**读后过滤**，不是存储层隔离。三个后果：

1. **正确性依赖应用代码**。任何一条漏掉过滤的读取路径就是一次越权；过滤逻辑与
   写入格式必须永远同步（现有代码里 `SPACE_SEP` 的注释已经在提醒这件事）。
2. **图谱本身是混在一起的**。实体/关系在同一张图里合并，不同案件的同一实体
   （同名的人、公司）会被 LightRAG 合并成一个节点。这不仅是「可能读到别人的」，
   还会**污染推断结果**——正是使用者担心的「数据冲突导致错乱」。
3. **无法审计**。数据库里看不出哪条边属于哪个案件。

### 1.3 对照：数据空间侧已经是存储层隔离

数据表侧每个路径一个 PostgreSQL schema，跨路径的表在 SQL 层面就不存在。本项目
已为它补上「显式引用他人 schema 一律拒绝」的防护（见主文档 §2.9）。知识侧要达到
同等强度，必须让「跨租户读取」在**存储引擎层面不可能发生**，而不是在应用层被拦下。

## 2. 目标与非目标

### 目标

- **G1 存储层强制隔离**：查询某个租户的数据时，其他租户的行**在 SQL 层面不可见**，
  不依赖应用层过滤。
- **G2 图谱不跨案合并**：不同案件的同名实体不合并，避免推断污染。
- **G3 与现有路径模型一致**：隔离粒度对齐「路径」，智能体挂载哪些路径就能检索
  哪些，语义与数据空间侧一致。
- **G4 可增量迁移**：现有 23 篇文档 / 1724 个 chunk 平滑迁入，不丢数据、可回滚。
- **G5 不破坏现有分层**：主应用拥有路径模型，知识服务保持「不认识路径」，
  由主应用传入 workspace 标识。
- **G6 可按需扩展**：多挂载 = 查多个 workspace 合并，语义清晰、可解释。

### 非目标

- 不引入独立图数据库（Neo4j/AGE）。LightRAG 自带的 Postgres 后端已能满足，且我们
  已经在用 `pgvector/pgvector:pg17`，无需新增存储组件。
- 不做跨租户的联邦查询（那是「共享」需求，用公共区路径表达即可）。
- 本期不处理向量索引的量化/压缩（属于容量优化，见 §10）。

## 3. 技术选型

### 3.1 关键实测发现（**已在本机跑通，非推测**）

LightRAG **1.5.6** 自带完整的 PostgreSQL 存储后端，且不需要 Apache AGE：

```
PGKVStorage, PGVectorStorage, PGTableGraphStorage, PGDocStatusStorage
```

**实测（`/tmp/feasibility.py`，2 个 workspace + 1.5.x 真机）**：

1. 进程内 `LightRAG(workspace=..., kv_storage="PGKVStorage",
   vector_storage="PGVectorStorage", graph_storage="PGTableGraphStorage",
   doc_status_storage="PGDocStatusStorage")` 可正常实例化并
   `initialize_storages()` 建表。
2. **隔离生效**：A workspace 读 B workspace 的行返回 `None`；同一 doc id 在
   两个 workspace 中各存一份互不覆盖。
3. **每张表的主键都含 `workspace`**（实测 13 张表的 PK）：
   `lightrag_doc_full(workspace,id)`、`lightrag_doc_chunks(workspace,id)`、
   `lightrag_vdb_entity(workspace,id)`、`lightrag_graph_nodes(workspace,namespace,id)`、
   `lightrag_graph_edges(workspace,namespace,src_id,tgt_id)` …
   —— 隔离由**主键**保证，不是靠应用过滤。

> **修正一处原设计假设**：原方案选 `PGGraphStorage`，实测它会调用
> `create_graph()` 等 Cypher 包装函数，**要求 Apache AGE 扩展**（本机
> `pg_available_extensions` 里没有 `age`，实际报
> `function create_graph(unknown) does not exist`）。改用
> **`PGTableGraphStorage`**：纯普通表 + 索引，**不依赖 AGE、也不依赖 pgvector**，
> 且同样把 `workspace` 放进主键。这是本机已验证可用的组合。

因此：

> **一个 Postgres 库天然支持多 workspace，隔离由主键与查询条件在引擎层保证。**

`PostgreSQLDB` 从 `POSTGRES_*` 环境变量读取配置（含 `POSTGRES_DATABASE`、
`POSTGRES_WORKSPACE`、`POSTGRES_MAX_CONNECTIONS`），`LightRAG.__init__` 接受
`workspace=` 参数。

### 3.2 方案对比

| 方案 | 隔离强度 | 成本 | 结论 |
|---|---|---|---|
| A. 维持文件存储 + 前缀过滤（现状） | 应用层 | 0 | ✗ 不满足 G1/G2 |
| B. 每租户一个 LightRAG 服务实例 | 存储层 | 极高：每实例独立进程/端口，容器内存上限 32G，10 个租户=10 个进程 | ✗ 不满足「最小化原则」，运维不可行 |
| C. 每租户一个独立 Postgres 库 | 存储层 | 高：库数=租户数，连接数与备份复杂度爆炸 | ✗ |
| D. **单 Postgres 库 + `workspace` 列隔离** | **存储层** | **中**：复用现有 pgvector 实例，LightRAG 原生支持 | **✓ 推荐** |
| E. 维护 LightRAG 的 fork，改 `/query` 支持 header | 存储层 | 中高：需长期跟进上游，风险外溢 | 备选（见 §12 风险） |

### 3.3 推荐：方案 D —— 进程内 LightRAG + 共享 Postgres + workspace 列

- 知识服务**不再通过 HTTP 调独立的 lightrag 容器**，改为**进程内**按 workspace
  实例化 `LightRAG`（每个 workspace 一个实例对象，共享同一个连接池配置）。
- 所有 workspace 的数据落在**同一个** Postgres 库（复用现有
  `pgvector/pgvector:pg17` 实例），用 `workspace` 列区分。
- 移除独立的 `huizhi-lightrag` 容器（或保留但仅用于应急查询，见 §12）。

> 这个改动把「图谱隔离」从应用层下沉到存储层，同时**减少**一个容器，符合项目的
> 镜像/资源最小化原则。

## 4. 隔离模型

### 4.1 workspace 的粒度 = 路径（path）

**这是本设计的核心决定。**

理由：

- 使用者要隔离的是**案件**，而案件在系统里就是「路径」。
- LightRAG 在**同一 workspace 内会合并实体/关系**（这正是图谱的价值，也是污染源）。
  因此两个案件若共享 workspace，同名实体必然合并 —— 与 G2 直接冲突。
- 所以 workspace 必须**细到路径**，而不是账号。

### 4.2 workspace 命名

```
workspace(path) = "ws_" + path_uuid_without_dashes     # 32 位十六进制
```

- 路径 id 是 UUID，去掉连字符后只含 `[0-9a-f]`，天然满足 LightRAG
  `validate_workspace` 的限制（禁 `/`、`\`、`.`、`..`），无需转义。
- 长度固定 35 字符，可读、可索引。
- **与数据空间的 schema 命名同源**（`p_<同样 32 位>`），便于运维对照：
  一个路径 = 一个 `p_xxx` 数据 schema = 一个 `ws_xxx` 图谱 workspace。

### 4.3 根路径与公共区

- 每个账号的**根路径**对应公共区，其 workspace 承载所有**未归类**文档。
- 与现有语义完全一致：「未绑定 = 公共」。

### 4.4 智能体的可检索集合

```
queryable_workspaces(agent) = { workspace(P) : P ∈ agent_path_ids(agent) }
```

- 空集合 = 拒绝（fail-closed），与数据侧 `data_search_path() -> None` 同一约定。
- 多挂载 = 查多个 workspace，**各自独立检索后合并**，按分数归并、按 chunk 去重。
- 关键性质：**每次查询只触碰被授权 workspace 的行**，跨案件不可能读到，因为
  SQL 的 `WHERE workspace = ANY(...)` 里根本不包含其他 workspace。

## 5. 存储层设计

### 5.1 复用现有实例

复用 `pgvector/pgvector:pg17`（生产已确认带 pgvector）。

**修正**：LightRAG 的表名是**固定**的（`lightrag_doc_chunks` 等，实测不含 schema
前缀），隔离靠 `workspace` 列而非 schema 名，所以「每租户一个 schema」不适用。
物理边界改为**同一个 Postgres 实例上的独立数据库**（图谱库与业务库分开），
理由：备份/恢复可独立、误操作不波及业务表、`max_connections` 也可分别核算。

```
huizhi_knowledge            (业务库：spaces / documents / chunks / jobs ...)
huizhi_knowledge_graph      (图谱库：LightRAG 的 13 张表，全部键含 workspace)
```

```
huizhi_knowledge (database)
├── public                       # 业务表：spaces / documents / chunks / jobs ...
└── lightrag                     # 图谱表（LightRAG 管理，全部以 (workspace, id) 为主键）
    ├── lightrag_doc_chunks
    ├── lightrag_doc_full
    ├── lightrag_vdb_entity / lightrag_vdb_relation / lightrag_vdb_chunks
    ├── lightrag_doc_status
    └── lightrag_llm_cache
```

> 具体表名以 LightRAG 1.5.6 为准（实施时以 `\dt lightrag.*` 核对）。若 LightRAG
> 不支持指定 schema，则退而使用独立数据库 `huizhi_knowledge_graph`（同实例），
> 隔离强度不变。

### 5.2 必要的扩展与索引

- `vector` 扩展（pgvector）—— 实体/关系/分块三种向量列。
- 索引：`(workspace)` 单列索引是**最低要求**（所有查询都带该条件）；
  向量列上的 HNSW/IVFFlat 索引由 LightRAG 自行创建，需确认在 `WHERE workspace=...`
  之下依然走索引（见 §11 验收 M4）。
- 容量估算：现有 1724 chunk、2 个空间。按「每 chunk 1 条向量 + 实体/关系向量」，
  1024 维 float32 ≈ 4KB/向量；1 万 chunk 规模约数百 MB，PG 完全可承载。

### 5.3 元数据表（知识服务新增）

为支持「按 workspace 列文档」「移动文档」需要一张映射表：

```sql
CREATE TABLE document_workspaces (
    document_id   TEXT PRIMARY KEY,
    workspace     TEXT NOT NULL,
    moved_at      TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX document_workspaces_workspace_idx ON document_workspaces (workspace);
```

- `documents.space_id` 保留（空间仍用于账号级归属与 UI 分组），
  `document_workspaces` 记录**图谱归属**（即路径）。
- **单一事实来源**：图谱归属只在 knowledge service 内维护；主应用的
  `platform.resource_bindings` 仍是「路径 ↔ 文档」的权威表。两者必须一致，
  由迁移与写入路径保证（见 §7、§8）。

## 6. 服务层改造

### 6.1 进程内 LightRAG 实例管理

```python
class GraphPool:
    """按 workspace 惰性创建并缓存 LightRAG 实例，共享一份 PG 配置。"""

    def __init__(self, settings): ...
    def get(self, workspace: str) -> LightRAG: ...   # 惰性 + LRU 上限
    def invalidate(self, workspace: str) -> None: ...  # 删除/移动后释放
```

要点：

- **惰性创建**：只有被查询/写入过的 workspace 才实例化，避免「1 万个路径 = 1 万个实例」。
- **LRU 上限**：超过 N（建议 32）时关闭最久未用实例（`finalize_storage()` 释放连接）。
- **线程/协程安全**：LightRAG 的写入是异步的，用 per-workspace 锁串行化同一
  workspace 的写入，避免并发抽取导致实体重复。
- **连接预算**：每实例一个 asyncpg 池。必须限制池大小（`max_connections`）并让
  `Σ(实例池) < PG max_connections`。建议单池 2~4，LRU 上限 32 → 最多 ~128 连接，
  需要相应抬高 PG `max_connections`（现有平台库也要用，见 §10 风险）。

### 6.2 接口改造（知识服务）

**保持「不认识路径」**，只增加 workspace 维度参数，由主应用传值：

| 接口 | 变更 |
|---|---|
| `POST /v1/documents/upload` | 增加 `workspace` 表单字段（必填）。写入时把文档归入该 workspace。 |
| `POST /v1/search` | 增加 `workspaces: list[str]`（必填，非空）。对每个 workspace 独立检索后合并。 |
| `GET /v1/documents` | 增加 `workspace` 过滤（可选）。 |
| `POST /v1/documents/{id}/move` | **新增**：把文档从一个 workspace 移到另一个（见 §7.3）。 |
| `DELETE /v1/documents/{id}` | 删除时同时清理其在对应 workspace 的图谱数据。 |

**移除**：来源标识里编空间/文档 id 的前缀技巧（`SPACE_SEP` 及其过滤逻辑）——
workspace 列已经承担隔离，前缀只剩历史包袱。**保留**旧前缀的解析仅用于迁移识别。

### 6.3 多 workspace 检索的合并语义

```python
async def search(query, workspaces, top_k):
    per_ws = await asyncio.gather(*(rag(w).search(query, top_k) for w in workspaces))
    merged = merge_by_score(per_ws)      # 归一化分数后归并，按 chunk id 去重
    return merged[:top_k]
```

- **不做跨 workspace 的图谱游走**（那是「混合两个案件的图谱」，与 G2 冲突）。
  只在**结果层**合并。
- 去重键用 chunk id（全局唯一），避免同一分块在多个 workspace 重复计数
  （同一文档只属于一个 workspace，理论上不重复，去重是防御性的）。
- 分数归一化：不同 workspace 的分数分布可能不同，合并前按各自 top-1 归一，
  避免某个 workspace 因绝对分高而整体淹没另一个（实施时需实测校准）。

## 7. 迁移方案

### 7.1 现状数据

实测：`2 spaces / 23 documents / 1724 chunks`，图谱数据在**
文件**（`/data/lightrag/*.json` + `.graphml`），且 lightrag 容器当前未运行（
`LIGHTRAG_URL` 为空）。

**重要**：所有既有文档都是「未绑定」= 公共区 = 根路径。因此映射是明确的：

```
每个账号的现有文档  →  workspace(该账号根路径)
```

### 7.2 迁移步骤（幂等、可重跑、可回滚）

```
阶段 M0  准备
  - 建 lightrag 索引结构与 document_workspaces 表
  - 备份：/data/lightrag 目录 + 业务库（pg_dump）

阶段 M1  启动扫描（后台任务，不阻塞服务启动）
  - 读 documents 表 + 旧来源标识，解析出 (document, filename, 原空间)
  - 为每个账号解析根路径 → workspace 名
  - 记录 platform.legacy_import_state（复用既有迁移状态表模式）

阶段 M2  逐个 workspace 重建图谱
  - 对每个 workspace：从业务库取该 workspace 的文档原文（chunks 已有）
  - 调 LightRAG insert（进程内）重建实体/关系/向量
  - 幂等键：(document_id, content_hash)；重复插入跳过
  - 逐文档 try/except 隔离，单个失败不影响其余；失败进 status='failed' 可重试

阶段 M3  校验
  - 文档级：迁移后每个 workspace 的文档数 = 业务库对应文档数
  - chunk 级：每文档 chunk 数一致
  - 抽样：随机取若干文档，检索其独有词应能命中（证明图谱真的建起来了）
  - 失败清单必须为空才继续

阶段 M4  切换
  - 配置切到进程内 LightRAG（PG 后端）
  - 保留旧 /data/lightrag 目录**只读**至少一个发布周期（回滚用）
  - 停用 huizhi-lightrag 容器
```

### 7.3 文档在路径间移动

移动 = **跨 workspace 重建**（图谱无法原地改归属）：

```
1. 标记文档状态 moving（列表显示「迁移中」，期间不可检索）
2. 在新 workspace 重建（复用 M2 的重建逻辑）
3. 校验新 workspace 检索可用
4. 删除旧 workspace 中该文档的图谱数据
5. 更新 document_workspaces
6. 清 document 状态
```

**必须显式说明的取舍**：移动有成本（要重新抽取实体/关系，可能数十秒到数分钟），
不像数据表移动那样是元数据操作。UI 上应提示「正在移动」，并允许失败重试；
**失败时保持原 workspace 不变**（先建后删，天然幂等）。

> 备选（更快但弱）：不重建图谱，只把「文档 → workspace」映射改掉，检索时按
> 「文档所属 workspace + 该文档的 chunk」过滤。但这会让图谱查询无法参与
> （实体已混入旧 workspace），等于放弃图谱能力 —— 不作为默认方案。

### 7.4 回滚

- 迁移期间：业务库未被破坏性修改（只新增 `document_workspaces`），
  旧文件存储原样保留 → 回滚 = 把配置切回 `LIGHTRAG_URL` 指向旧容器。
- 迁移后：旧文件目录保留一个周期；确认无问题再删除。

## 8. 权限强制点（与主应用配合）

隔离落在存储层后，强制点收敛为**一处**：主应用决定「传给知识服务的 workspace 集合」。

| 强制点 | 文件 | 规则 |
|---|---|---|
| 检索 | `agents/tools/knowledge.py::query_knowledge` | 传 `workspaces = {ws(P) : P ∈ agent_path_ids}`；空集合直接返回「无可用知识路径」，不发请求 |
| 文档详情 | `agents/tools/knowledge.py::get_document_detail` | 先校验该文档所属 workspace 在授权集合内，否则拒绝（防止凭空写 id） |
| 列表 | `app/routers/knowledge.py::list_knowledge_documents_v2` | 按路径解析出 workspace 集合并传给知识服务 |
| 上传 | `app/routers/knowledge.py::upload_knowledge_document` | 传目标路径的 workspace（已实现的 `path_id` 直接映射） |
| 移动 | 新增 `POST /api/paths/{id}/resources` 触发的迁移任务 | 先鉴权路径归属，再触发 §7.3 |

**关键收益**：应用层不再需要「过滤检索结果」—— 它只是把 workspace 名单交给
存储层。即使应用层某处忘了过滤，它也只能看到「传进去的那些 workspace」，
而传什么由唯一的授权函数决定。

## 9. 运维设计

### 9.1 连接与资源

| 项 | 建议值 | 理由 |
|---|---|---|
| PG `max_connections` | ≥ 300 | 平台库池 + 业务池 + 图谱池（LRU 32 × 2~4） |
| 单 workspace 池 `max_connections` | 2~4 | 单 workspace 并发低 |
| GraphPool LRU 上限 | 32 | 内存与连接数的平衡；超限释放最久未用 |
| 图谱容器内存 | 移除（进程内） | 省下一个 32G 上限的容器 |

### 9.2 备份与恢复

- 图谱并入业务库备份（`pg_dump`）—— **这是本改造的额外收益**：图谱不再只有文件
  副本，能和业务数据一起事务性备份/恢复。
- 恢复演练：`pg_restore` 后按 workspace 抽查检索可用。
- 旧文件目录在切换后保留一个周期。

### 9.3 监控

- `Σ(活跃 LightRAG 实例)`、图谱池连接数、单次检索耗时（按 workspace 数分解）。
- 迁移进度：`legacy_import_state` 的 `done/failed/pending` 计数。
- 容量：`pg_total_relation_size('lightrag.*')` 与行数按 workspace 分组。

## 10. 风险与取舍

| # | 风险 | 影响 | 缓解 |
|---|---|---|---|
| R1 | 进程内 LightRAG 引入额外依赖与内存占用 | 知识服务容器内存上升 | 实测基准后再定 LRU 上限；必要时把图谱读写拆到独立 worker |
| R2 | 多 workspace 检索的 N 次查询放大延迟 | 挂载 5 个路径 = 5 次检索 | 并发 `gather`；对 workspace 数设上限（如 10）并提示；缓存同一 query 的 workspace 结果 |
| R3 | 移动文档需重建图谱，耗时明显 | 用户感知慢 | UI 显示「迁移中」；先建后删可重试；失败保持原状 |
| R4 | LightRAG 上游 API 变动 | 升级困难 | 固定版本（1.5.6）+ 适配层 `lightrag_bridge` 隔离调用面；不 fork |
| R5 | 图谱表与业务表同库争用资源 | 大检索影响上传 | schema 分离 + 索引核对；必要时拆到同实例的独立库 |
| R6 | 向量索引在 `workspace` 过滤下的效率 | 慢查询 | 验收项 M4 专门测；必要时建 `(workspace)` 复合索引或按 workspace 分区 |
| R7 | 分数归一化主观 | 合并结果可能偏向某个 workspace | 保留原始分数便于排查；先按 top-1 归一，实测校准 |

## 11. 验收标准（必须实测，不接受「逻辑上应该行」）

| # | 验收项 | 方法 | 通过标准 |
|---|---|---|---|
| M1 | 隔离由引擎在查询时保证 | 审查所有图谱查询路径，逐条确认都带 `workspace` 条件 | **任何一条缺该条件即为不通过**；再用「只挂 A 的智能体」实测，其结果集脚本化断言不含 B 的任何 chunk id |
| M2 | 图谱不跨案合并 | 案件A、B 各上传含**同名实体**的文档；查询该实体 | A 的检索不返回 B 的实体；两案件实体在不同 workspace 各存一份 |
| M3 | 多挂载合并 | 挂 A+B，查共同词 | 两案结果都出现，且**不出现**案件C 的内容 |
| M4 | 向量检索走索引 | `EXPLAIN ANALYZE` 带 `WHERE workspace=...` 的向量查询 | 使用索引而非全表扫描；10 万 chunk 下 P95 < 1s |
| M5 | 迁移完整性 | 迁移前后按 workspace 对比文档数/chunk 数 | 逐项相等；失败清单为空 |
| M6 | 迁移幂等 | 迁移任务重跑一次 | 无重复数据；状态仍为完成 |
| M7 | 移动文档 | 在测试1 上传→移到案件A→在两端分别检索 | 移动后案件A 可检索、测试1 不可检索；期间失败可重试且原状态不变 |
| M8 | 无授权即拒绝 | 新建智能体不挂任何路径 | 检索返回「无可用知识路径」，且不发任何图谱查询（抓请求验证） |
| M9 | 备份可恢复 | `pg_dump` → 恢复 → 抽查检索 | 检索结果与恢复前一致 |
| M10 | 删除清理 | 删除文档后检查图谱表 | 该文档在对应 workspace 的 chunk/实体引用被清除 |

> **关于 M1 的诚实说明。「存储层隔离」在这里的准确含义是：隔离条件进入 SQL 的
> `WHERE workspace = ANY(...)`，由数据库在执行检索时就排除其他租户的行，而不是
> 先把所有租户的数据取回、再由 Python 过滤。
>
> 它与「每租户一个独立库/schema」的强度仍有差别：后者是物理上互不可见，前者
> 依赖**调用方传入正确的 workspace 列表**。因此本方案的真实防线是两条：
> ① 唯一授权函数产出该列表（`agent_path_ids` → workspace 映射，见 §8）；
> ② M1 的逐条审查确保没有查询绕过它。
>
> 这个代价是清醒选择的：LightRAG 的 PG 后端使用固定表名 + `workspace` 列，不支持
> 按 schema 分租户；而每租户独立库会带来库数量与连接数爆炸（§3.2 方案 C）。如果
> 后续合规要求「物理不可见」，再评估 fork LightRAG 改查询接口（§3.2 方案 E）。

**关键配置**：`KNOWLEDGE_GRAPH_DATABASE_URL` 留空 = 保持旧的共享图谱；填 DSN 即启用
多租户。因此**升级默认不改变行为**，切换是一个显式动作。

### 实施中实测到的两个真实缺陷（均已修）

1. **`adelete_by_doc_id` 要的是 LightRAG 自己的 `doc-<md5>`，不是我们写的
   `file_path`。** 传路径时它匹配不到任何行、却仍返回成功 —— 「删除成功」是假的，
   实体/关系会永久残留。现在先解析出真正的 doc id，并以「是否真的删掉了行」作为
   返回值。
2. **`ainsert` 正常返回 ≠ 文档可用。** 抽取超时/模型报错时 LightRAG 会把该文档记为
   `failed`，而 `ainsert` 仍然正常返回；若据此判定成功，迁移会报「0 失败」却什么
   都没建成。现在插入后回查文档状态，只有 `processed` 才算成功。

### 本机环境的吞吐限制（不影响生产，但必须知道）

本机用 MLX 小模型做实体抽取，一个几百 KB 的文档会超过 LightRAG 的
`max_execution_timeout`（= `llm_timeout × 2` = **480s**）而失败。这是**本地模型速度**
问题，不是实现问题 —— 生产用的模型吞吐更高。但由此得到两条运维要求：

- 迁移必须能**断点续跑**（已实现：`skipped` 计数 + 逐文档隔离 + 失败清单）；
- 迁移应在生产**低峰**执行，并预留足够时间（1724 chunk 按当前规模估算需要数小时）。

### P4 生产切换步骤（待执行）

1. 建图谱库：`CREATE DATABASE huizhi_knowledge_graph`（复用现有 pgvector 实例）
2. 在 `knowledege-service/.env` 设 `KNOWLEDGE_GRAPH_DATABASE_URL` 指向它
3. 重启知识服务；启动日志应出现 `graph: workspace ws_xxx ready`
