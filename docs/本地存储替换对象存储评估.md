# 本地存储替换为对象存储：可行性评估、开源方案比选与用户隔离设计

- 评估对象：`huizhi-assistant-v2.2.1`（警务内网，50–500 人规模）
- 评估日期：2026-10-21
- 交付性质：**方案评估**，不含代码改动
- 前置结论来源：`docs/商用级扩展方案.md`（§3 对象存储）、`docs/多租户权限与隔离审查报告.md`

> **术语澄清**：本文的"云存储"指**内网自建的 S3 兼容对象存储**（MinIO/Ceph RGW 等），
> 不是公有云。警务内网的数据不出网要求，决定了公有云对象存储通常不可行；若客户已有
> 私有云的对象存储服务，按 §4 的"客户既有 S3"路径评估。

## 0. 结论摘要

### 0.1 三句话结论

> **范围**：本节及全文的"迁移"只针对**业务文件**（知识库原件、聊天附件、生成物、导出包、
> 备份等用户/业务产生的内容）。运行日志、缓存、密钥、数据库数据目录这类**运行时文件**
> 本来就应该留在服务器上，不在讨论范围——这一点与你的判断一致。

1. **业务文件 100% 可迁移**：知识库原件、聊天附件、生成的 DOCX/图表、会话导出包、备份，
   都是"写一次、读多次、整文件访问"，天然适合对象存储。
   **会话正文不需要迁**——它已经在 PostgreSQL 里；磁盘上的 `sessions/*.json` 只是每 2 秒
   重写的运行时快照，应该迁到 PG，而不是对象存储。
   **智能体生成的代码与技能也能进对象存储**，但要用"快照 + 本地物化"模型（§3.5）：
   对象存储是版本权威副本，执行前物化到本地工作副本，**不直接执行对象存储里的文件**。
2. **稳定性优先的前提下，首选"客户既有的 S3 兼容存储"**；若必须自建，**3 节点 MinIO**
   是工程上最省事、故障面最小的默认选择；**已有 Ceph 运维能力**才选 Ceph RGW；
   NFS 只能当过渡，不能当目标。
3. **对象存储不解决权限问题**。它只把"文件在哪"从本机变成网络服务；"A 能不能读 B 的文件"
   仍然由应用层 + 凭证 + 前缀策略决定。隔离必须按 §5 单独设计，且**不能**因为"用了对象
   存储"就放松现有的账号根目录校验。

### 0.2 可行性判定（按资产）

**（1）业务数据——本次评估的对象**

| 业务数据 | 当前形态 | 是否迁移 | 结论 |
| --- | --- | --- | --- |
| 知识空间原始文档 | 文件 `data/files/<space_id>/<doc_id>-<name>` | ✅ **迁对象存储** | 最优先；写一次、读多次、整文件读 |
| 聊天附件（原件） | 文件 `<workspace>/media/<uuid>_<name>` | ✅ **迁对象存储** | 上传端点 `console.py:565-590` 直接写 media；20MB 上限 |
| 生成的 DOCX / 图表 | 文件 `<workspace>/media/` | ✅ **迁对象存储** | 写一次、下载一次 |
| 会话导出包 | 文件（导出接口产生） | ✅ **迁对象存储** | 业务文件，适合版本化保存 |
| 备份包 | 文件 `working.backups/*.zip` | ✅ **应该迁** | 对象存储的版本化 + Object Lock 解决防篡改/防勒索 |
| 审计归档 | PG 表 | ✅ **归档到对象存储** | 在线查 PG，冷数据 WORM 归档 |
| **智能体生成的代码 / 代码工程** | 目录 `coding_projects/<name>`（可能是 git 仓库） | ✅ **快照到对象存储** | 每个版本一个快照（推荐 `git bundle`）；本地保留工作副本用于执行 |
| **技能包（含 scripts）** | 目录 `SKILL.md` + `scripts/` | ✅ **打包快照到对象存储** | 内容寻址 + manifest；物化后执行；启用前必须过扫描器 |
| **自定义 HTTP 工具 / MCP 配置** | **数据库记录 / 配置文件**，不是代码文件 | ❌ **不进对象存储** | 小配置且可能含凭据；应进 PG/密钥管理并加密（见 §3.6） |
| 数据分析导入暂存 | 文件 `data_uploads/<account>/<task>/<file>` | ◐ 可选 | 短生命周期；放本地 + 过期清理更简单，放对象存储需 TTL |
| **会话正文 / 历史** | **PostgreSQL** `platform.conversation_history` | ❌ **不需要迁** | 已经在库里，按 `workspace_key` 隔离；没有对应的"业务文件" |
| 数据表（分析库） | PostgreSQL（每账号库 + 路径 schema） | ❌ 不需要 | 本来就是数据库 |

**（2）运行时文件——按你的判断留在服务器**

| 运行时文件 | 为什么不能/不该进对象存储 |
| --- | --- |
| 会话状态快照 `sessions/*.json` | 每 2 秒整文件重写（约 4MB）；PUT 语义不适合。**应迁到 PG**，不是对象存储 |
| `chats.json` / `jobs.json` 索引 | KB 级、频繁整体重写；留本地或随后续改造并入 PG |
| checkpoint `shadow.git` | Git 需要大量小文件、锁、原子 rename |
| 浏览器 profile `.browser-profile` | Chromium 用 mmap、文件锁、SQLite WAL |
| LightRAG 本地工作目录 / index | 随机读写与文件锁；隔离模式已改用 PG |
| 日志 | 追加写；本地落盘 + 采集转发 |
| `working.secret` | 安全边界；应移出业务容器 |
| 插件 / 模型 | 运行时依赖与代码包（管理员安装/镜像内置） |
| `postgres-data/` | 块设备语义 |

**一句话**：业务文件（含生成的代码与技能）全部可迁；运行时文件全部保留。代码改造集中在
"上传/下载/删除/解析取件"四条路径，外加"快照 + 物化"一套同步机制（§3.5）。

### 0.3 推荐路径

```
先抽象（StoragePort）→ 双写 → 影子读 → 切读 → 停双写 → 下线本地路径
存储选型：客户既有 S3 ＞ 3 节点 MinIO ＞ Ceph RGW（已有 Ceph 时）＞ SeaweedFS（许可受限时的备选）
部署形态：对象存储独立 3 节点 / 独立磁盘，不与 PostgreSQL 争同一批盘
```

工程估算：文档类改造 **15–20 人日**；代码/技能的快照与物化 **5–8 人日**；部署与迁移验证
**5–8 人日**。不含会话状态迁 PG（独立项目，约 10–15 人日）。

### 1.2 运行时文件：为什么必须留在本地

这里列的是**运行时文件**，不是业务数据。它们在业务上可以丢（可从 PG / 对象存储重建），
但在运行上依赖 POSIX 语义，搬进对象存储只会更慢、更不稳定：

| 类别 | 代表 | 原因 | 正确做法 |
| --- | --- | --- | --- |
| **POSIX 语义依赖** | checkpoint git、浏览器 profile、代码工程 | 锁、rename、mmap、append、目录遍历；S3 都没有 | 留本地卷；跨实例时用共享文件系统（见 §4.6） |
| **高频整文件重写** | 会话状态、`chats.json` | 对象存储按 PUT 计费/计次，2 秒一次会把存储打成热点 | 改存 PostgreSQL（行级更新 + 事务） |
| **安全边界** | `working.secret` | 放共享存储等于扩大暴露面 | 移出业务容器，启动时注入 |
| **追加写/流式** | 日志 | 对象不可追加，只能整对象重写 | 本地落盘 + 采集（Loki/Filebeat） |
| **数据库数据目录** | `postgres-data` | 需要块设备与 fsync 语义 | 本地 NVMe + 备份到对象存储 |

### 1.2.1 会话的存储真相（避免把"会话"当成要迁的文件）

很多"会话要不要上对象存储"的讨论，前提就是错的。当前的实际形态是：

| 层次 | 存在哪 | 说明 |
| --- | --- | --- |
| 会话正文 / 完整轨迹 | **PostgreSQL** `platform.conversation_history` | 按 `workspace_key` 隔离；控制台历史、导出、重放都读它 |
| 会话元数据 / 索引 | `<workspace>/chats.json` | 小文件；列表与标题 |
| 会话状态快照 | `<workspace>/sessions/<channel>/*.json` | 每 2 秒重写的运行时快照（含图片 base64），**不是业务真相** |
| 会话导出包 | 导出接口按需生成 | 这是业务文件，可进对象存储 |
| 聊天附件原件 | `<workspace>/media/<uuid>_<name>` | 业务文件，可进对象存储 |
| 聊天附件的解析文本 | PostgreSQL（消息 + 知识分块） | 已在库里 |

**结论**：会话作为"业务数据"早就在数据库里，不需要对象存储；需要迁移的是它周边的
**附件与导出包**。真正该动的是那张 4MB 快照——把 `state.json` 从"每 2 秒整文件重写"
改成 PostgreSQL 行级更新，这属于会话状态改造项目，与对象存储无关。

## 2. 为什么值得做（以及它解决不了什么）

### 2.1 收益

| 收益 | 说明 |
| --- | --- |
| **容量与扩容解耦** | 文档增长不再需要给应用容器扩盘/迁移目录；加节点即可 |
| **应用无状态化前置** | 多副本、滚动升级、故障迁移都要求"文件不在本机"（`docs/商用级扩展方案.md` §5.3） |
| **不可变性/防篡改** | 版本化 + Object Lock（WORM）可满足审计与防勒索；本地盘做不到 |
| **备份与恢复** | 备份不再是"打 zip 放本机"，而是对象级版本 + 跨节点冗余；pgBackRest 可直接归档 WAL |
| **故障域** | 数据不再依赖"应用宿主机那一块盘"；单盘/单节点故障可自愈 |
| **多租户配额** | 可按前缀统计用量，做账号级配额（客户一定会问） |

### 2.2 它解决不了什么（必须先说清楚）

| 不解决 | 原因 |
| --- | --- |
| **越权访问** | 对象存储只认凭证。应用如果把 B 的 key 返回给 A 的请求，存储层不会拦 |
| **数据分级/密级** | 对象存储没有"密级"概念；要在应用层做标签与策略 |
| **检索** | 对象存储不能全文检索；向量/图谱仍在 PG |
| **小文件高频写** | 会话状态、checkpoint 这类负载上去只会更慢 |
| **合规审计** | 需要应用侧记录"谁在什么时候取了哪个对象"，存储日志只是补充 |
| **可执行内容的一致性** | 代码/技能的快照、物化、并发写冲突仍要应用层解决（§3.5） |

**结论**：对象存储是"存得更稳"，不是"权限更安全"。隔离要单独做（§5）。

## 3. 接口抽象：StoragePort

### 3.1 为什么要抽象，而不是直接调 SDK

当前代码直接依赖本地路径（`documents.path` 存绝对路径、`FileResponse(path=...)`、
`os.remove`）。直接改成 SDK 调用会把存储实现散到十几个调用点，回滚困难、也没法保留
本地实现做对照。正确做法是**一个薄端口，两份实现**：

```python
class StoragePort(Protocol):
    async def put_stream(key, chunks, *, content_type, max_bytes) -> PutResult
    async def open_stream(key, *, range=None) -> AsyncIterator[bytes]
    async def stat(key) -> ObjectStat | None      # 不存在返回 None，不抛
    async def delete(key) -> None                 # 幂等
    def presign_get(key, *, expires=300, filename=None) -> str
```

- `LocalFsStorage`：保持现有行为（回滚、本地开发、对照测试）；
- `S3Storage`：boto3 实现，走 `run_sync_io(POOL_FILE, ...)`（boto3 是同步库，
  **禁止出现在事件循环上**——这是本仓库已经踩过的坑）。

### 3.2 必须保持的语义（每一条都对应一个已知事故）

| 语义 | 原因 |
| --- | --- |
| **内容寻址**：key 含 sha256 | 上传幂等、天然去重、对象名不含用户可控字符串（防路径穿越） |
| **先写对象、后提交数据库行** | 失败只会留下孤儿对象（可 GC）；反序会出现"有行无对象"——用户可见的坏数据 |
| **删除：先删行（事务）→ 再删对象（异步重试）** | 删除对象失败不能让用户看到 500；孤儿由 GC 处理 |
| **分片读写** | 预览/下载不能把整文件读进内存（现有代理下载就是这样，见隔离报告 OPS-06） |
| **边写边算 sha256** | 不要写完再读一遍；现有上传已这么做，保持 |
| **幂等 delete / stat 返回 None** | 重试安全；不要把"不存在"变成异常路径 |
| **写入临时对象再改名（或内容寻址直接落最终 key）** | 避免半截对象被读到 |

### 3.3 解析器如何拿到本地文件（关键决策）

MinerU / `soffice` 需要**真实文件路径**。三种做法：

| 方案 | 评价 |
| --- | --- |
| **A. 下载到本地 scratch（推荐）** | worker 处理前把对象拉到 `/scratch/<doc_id>`，处理完删除；热文档按容量 LRU 保留。语义清晰、无新增依赖 |
| B. FUSE 挂载（s3fs/goofs/JuiceFS） | 无代码改动，但把 FUSE 的不确定性引入解析热路径；本仓库刚花大力气把解析的进程树/pids 收住，不建议 |
| C. 解析器直接读 S3 | 需要改 MinerU 调用方式，不现实 |

**推荐 A**，并加两条约束：

1. scratch 目录**按账号分目录**（与现有账号根目录模型一致），处理完立即删除；
2. 下载前校验对象大小上限（防止把 10GB 文件拉到 scratch 打满盘）；scratch 盘设置配额与水位告警。

### 3.4 需要改的调用点（只涉及业务文件）

迁移的代码面比想象中小——只集中在这几条路径：

| 调用点 | 现在 | 改后 |
| --- | --- | --- |
| 知识文档上传 `knowledge-service/app/main.py:247-262` | `target_path.open("wb")` 流式写盘 | `storage.put_stream(key, ...)` |
| 知识文档下载/预览 `main.py:417` | `FileResponse(path=document["path"])` | 代理流式（默认）或短时效预签名 |
| 知识文档删除 `store.py:740-746` | `os.remove(file_path)` | `storage.delete(key)`（异步重试） |
| 解析取件 `parsers.py` / worker | 直接读本地路径 | `storage.materialize(key) -> scratch_path`，处理完删除 |
| 聊天附件上传 `app/routers/console.py:565-590` | `file.read()` 全量进内存后 `write_bytes` | `storage.put_stream`（顺带修掉 20MB 全量读内存） |
| 文档生成 `generate_docx.py` / 图表 `generate_chart.py` | 写 `media_dir` | 写对象存储（`hz-artifacts/<tenant>/...`） |
| 发送文件 `send_file.py` | 按账号根解析本地路径 | 本地有则直接用；否则 `materialize` 到 scratch 后发送 |
| 会话导出 `app/chats/api.py` | 生成 JSON 文件返回 | 生成后 `put_stream`，返回下载地址 |
| 备份创建/恢复 `app/routers/backup.py` | 打包 zip 到本地 | pgBackRest + 配置快照写入 `hz-backups`；恢复从对象存储读 |
| 技能创建/编辑/导入 `agents/skill_system/workspace_service.py`、`pool_service.py` | 直接写技能目录 | 目录写完后打包快照（tar + manifest）上传；启用前扫描 |
| 代码工程 `app/routers/project_directory.py` | 目录/git 仓库 | 保存/提交时生成 `git bundle` 快照；换节点时物化 |
| 代码文件编辑 `app/routers/workspace.py:912-1000`（code-files） | 直接读写本地文件 | 本地读写不变；按保存时机触发快照 |

**不需要改的**：会话状态、checkpoint、浏览器、日志、插件、模型——这些是运行时文件。
自定义 HTTP 工具与 MCP 配置也不改（它们是 PG/配置文件，不是对象）。

### 3.5 可执行内容：快照 + 本地物化（关键设计）

智能体生成的代码、技能与文档的本质区别是**它们会被执行**。所以不能像文档那样
"按需从对象存储读"，而要用"对象存储是权威副本、本地是工作副本"的模型。

#### 3.6.1 三类内容，三种存法（形态已核实）

| 类别 | 实际形态 | 存储模型 | 执行位置 |
| --- | --- | --- | --- |
| 智能体生成的代码 / 代码工程 | 目录 `coding_projects/<name>`，可能是 git 仓库 | 每次保存/提交产生一个**快照对象**：推荐 `git bundle`（单文件、含完整历史、可校验），或 `tar.zst` | 本地工作副本 |
| 技能 | 目录 `SKILL.md` + `scripts/`（`skill_system/models.py:62`） | 打包成 `tar` + `manifest.json`（含文件清单与 hash），内容寻址 | 本地物化到 `skills/` 后执行 |
| 自定义 HTTP 工具 | **数据库记录**（`name/url/method/headers`，`routers/tools.py:272`） | **不进对象存储**：PG 存储 + `headers` 加密 | 应用进程（HTTP 调用） |
| MCP 配置 | driver card 文件 + 凭证库（`app/mcp/config_service.py:258-291`） | **不进对象存储**：小配置 + 密钥，建议 PG/密钥管理 | 应用进程（spawn） |
| 插件 | 代码包（管理员安装，`plugins/loader.py`） | 运行时依赖，留本地；只把备份放 `hz-backups` | 本地 |

> 结论：**"工具"里只有代码/脚本形态的才需要对象存储**。HTTP 工具与 MCP 配置是元数据，
> 放进对象存储既无收益，还会把凭据散到一个新的地方。

#### 3.6.2 同步规则（决定稳定性）

1. **写**：本地写入照常；在"显式保存 / 轮次结束 / git commit"时上传快照。
   **不要每写一个文件就 PUT 一次**——那会变成小文件风暴（对象存储按请求计费）。
2. **读**：本地有就直接用；本地没有（换节点、被清理）时 `materialize(snapshot_id)`
   到工作区再执行。**不执行对象存储里的文件，也不用 FUSE 挂载**（理由同 §3.3）。
3. **冲突**：同一工程同一时刻只允许一个写者（会话租约 / agent 锁）。快照是"整目录版本"，
   不做文件级合并；需要多人协作时改用 Git 服务（见 3.6.3）。
4. **回滚**：快照按 `(project, version)` 保存，`current_version` 指针存 PG。回滚=切换指针 +
   重新物化；不覆盖旧版本。
5. **保留与清理**：每个工程保留最近 N 个版本（如 20）+ 按时间清理；对象走生命周期规则，
   不要只增不删。
6. **校验**：物化后核对 manifest 里的 hash；不一致即拒绝执行并告警（防止半截快照被执行）。

#### 3.6.3 代码工程：对象存储 bundle，还是 Git 服务？

| 做法 | 优点 | 缺点 |
| --- | --- | --- |
| 对象存储存 `git bundle` | 只需一种存储（符合"业务数据全部进对象存储"）；单文件、含历史、可校验 | 不能在线浏览/协作；每次快照是整包 |
| 部署 Gitea/GitLab 作为代码主存 | 浏览、diff、PR、权限模型现成 | 多一个有状态服务；与"全部进对象存储"的目标不一致 |

**建议**：以对象存储的 bundle 为权威副本；Git 服务作为可选增强（定期把 bundle 推过去）。
两者不冲突，也便于以后把"代码"单独拆出去。

#### 3.6.4 与技能分享/审批的衔接

现有流程是"分享 → 对方审批 → `copytree` 到对方技能目录"。改成对象存储后：

- 分享物 = **快照引用 + manifest**（不是共享同一个前缀）；
- 审批通过后从对象存储物化到接收者的 `skills/`，重新生成目录名与 hash；
- **启用前必须过 `skill_scanner`**（默认 `block`，不要停在 `warn`）；
- 记录 provenance：谁生成、何时、父版本、扫描结果、被谁安装。

### 3.6 数据模型改造

`documents` 表新增/调整（保留 `path` 作为兼容列）：

```sql
ALTER TABLE documents ADD COLUMN storage_backend TEXT NOT NULL DEFAULT 'local';
ALTER TABLE documents ADD COLUMN storage_key TEXT;          -- 对象键；local 实现可存相对路径
ALTER TABLE documents ADD COLUMN checksum TEXT;             -- sha256，已有 content_hash 可复用
CREATE INDEX ON documents (storage_backend, storage_key);
```

读取时按 `storage_backend` 分派；写入时双写阶段两列都填。**不修改 `path` 的既有语义**，
保证回滚时旧代码仍能工作。

## 4. 开源方案比选（稳定性优先）

### 4.1 评分维度与权重

| 维度 | 权重 | 说明 |
| --- | --- | --- |
| 稳定性与成熟度 | 30 | 生产运行年限、公开故障案例、社区规模、被谁在用 |
| 运维复杂度（越低越好） | 20 | 组件数量、升级路径、日常操作、故障定位难度 |
| 数据耐久与故障恢复 | 20 | 副本/纠删码、重建速度、部分故障下的可用性 |
| 与本场景契合度 | 15 | 大对象流式、Range 读、S3 API 完整度、小元数据操作 |
| 许可与合规 | 10 | 商用交付的许可义务（AGPL/LGPL/Apache） |
| 内网生态与可维护性 | 5 | 离线安装、中文资料、国产化适配、人才可得性 |

评分 1–5，加权后满分 100。

### 4.2 候选与评分

| 方案 | 许可 | 稳定性 | 运维 | 耐久 | 契合 | 许可分 | 生态 | **加权分** |

| **Ceph RGW** | LGPL-2.1 | 5 | 2 | 5 | 4 | 5 | 3 | **83** |
| **MinIO（3 节点）** | **AGPL-3.0** | 4 | 4 | 4 | 5 | 2 | 4 | **79** |

| **NFS / NAS 共享** | 视产品 | 4 | 4 | 3 | 2 | 5 | 4 | **72** |

| **Apache Ozone** | Apache-2.0 | 4 | 1 | 5 | 3 | 5 | 2 | **69** |

> 商业版的功能边界近年有调整，例如控制台是否包含在社区版）。

### 4.3 逐个评价（稳定性视角）

**客户既有 S3（首选）**
- 稳定性最高：不是我们运维，故障责任在存储方；通常已有运维团队与监控。
- 风险：S3 API 兼容度参差（multipart、presign、Object Lock 不一定全）、申请流程长、
  网络策略需协调。落地前做一次兼容性冒烟测试（§8.4）。
- 适用：客户已有私有云/对象存储服务，或愿意采购。

**Ceph RGW（有 Ceph 团队时的最佳解）**
- 最成熟、最"经得起生产"的对象存储；LGPL 对商用交付友好。
- 真正的门槛是运维：MON/OSD/MGR、CRUSH 调优、PG 合并、故障域规划、升级窗口。
  **没有专职存储运维时，Ceph 是稳定性风险而不是保障**（一次误操作可能整池不可用）。
- 资源占用大：小规模（<50TB）用 Ceph 性价比低。
- 适用：客户已有 Ceph 集群（RGW 直接开一个租户），或团队里有 Ceph 经验。

**MinIO（自建默认）**
- 单二进制、部署极简、S3 API 完整度高（multipart、presign、versioning、Object Lock、
  桶配额都有），3 节点纠删码即可容忍单节点/单盘故障；社区与文档最丰富。
- 稳定性风险不在软件本身，而在**运维细节**：升级要按版本节奏、`mc admin heal` 要监控、
  容量水位要留足、时间同步必须准（签名对时钟敏感）。
- 许可：AGPL-3.0。**作为产品的一部分交付给客户、或对外提供服务时，需要法务确认义务**
  （源码提供范围、修改后的分发义务）。如果这一条过不了，见下面的备选。
- 适用：内网自建、3 节点、50–500 人规模——本项目的推荐默认值。

**JuiceFS（"零代码改动"的诱惑）**
- 用 FUSE 把对象存储挂成 POSIX 文件系统，元数据放 Redis/MySQL/PG/TiKV。
- 优点：`documents.path` 不用改，现有代码几乎不动；大文件顺序读写性能好。
- 缺点：多一个有状态组件（元数据库）要 HA；FUSE 在解析热路径上的语义/挂起风险；
  权限仍是 POSIX uid/gid，不天然带租户维度。
- 结论：**如果"不改代码"是硬约束，可以评估**；但作为长期架构，不如 StoragePort 干净。

**NFS / NAS 共享**
- 成本最低、改动最小（把本地目录换成 NFS 挂载），POSIX 语义完整，适合"先解决多副本共享"。
- 但它是**共享文件系统，不是对象存储**：没有版本化、没有 Object Lock、没有对象级生命周期、
  元数据操作慢、单点（除非 HA NAS）。
- 结论：**只作为过渡**（比如多副本上线前的临时方案），不作为目标形态。

**SeaweedFS**
- Apache-2.0（许可友好）、小文件场景好、部署比 Ceph 轻。
- 但社区规模与生产案例少于 MinIO/Ceph，S3 兼容性以 Filer 层实现，复杂查询/版本化能力弱。
- 结论：AGPL 过不了、又不想上 Ceph 时的备选；需要自己做更充分的压测与故障演练。

**Apache Ozone**
- Hadoop 生态、真正的分布式对象存储、Apache-2.0。
- 组件多（OM/SCM/Datanode）、运维门槛高、小规模不划算。
- 结论：不建议在当前规模引入。

**Garage**
- Rust、单二进制、面向"跨机房/边缘"设计，部署简单。
- 生态与中文资料少，S3 兼容子集；适合边缘/多站点，不适合作为本项目主存储。

### 4.4 选择树

```
客户已有 S3 兼容存储？
├─ 是 → 用它（先做兼容性冒烟：multipart / Range / presign / 版本化）
└─ 否 → 有专职存储运维或已有 Ceph？
        ├─ 是 → Ceph RGW（独立租户）
        └─ 否 → 许可能接受 AGPL？
                ├─ 是 → MinIO 3 节点（默认推荐）
                └─ 否 → SeaweedFS（需补压测）或采购商业 S3 产品
```

**不推荐**在本项目规模引入 Ozone / Garage；**不建议**把 NFS 当最终形态。

### 4.5 稳定性对比（故障视角）

| 故障 | MinIO 3 节点 | Ceph RGW | NFS（单机） | 客户 S3 |
| --- | --- | --- | --- | --- |
| 单盘坏 | 纠删码自动重建，可读写 | 自动恢复（视 CRUSH） | 视 RAID | 存储方处理 |
| 单节点坏 | 继续服务（EC:2） | 继续服务 | **服务中断** | 存储方处理 |
| 升级 | 逐节点滚动 | 需要规划（MON/OSD 顺序） | 停机窗口 | 存储方处理 |
| 误删 | 版本化 + Object Lock 可救 | 快照/版本化（需配置） | 备份才能救 | 视配置 |
| 容量满 | 写入失败（需提前告警） | 接近满时性能下降 | 写满即断 | 存储方处理 |
| 时钟漂移 | 签名失败（需 NTP） | 影响较小 | 无 | 无 |

## 5. 用户隔离设计（严格隔离）

### 5.1 隔离的五个层次

只做其中一层都不够，必须叠加：

| 层 | 措施 | 防什么 |
| --- | --- | --- |
| 1. 网络 | 对象存储只开给应用/知识服务，不对终端网段开放；管理口独立 | 绕过应用直连 |
| 2. 凭证 | 应用持有**服务端凭证**，绝不下发客户端；如做每租户凭证，按前缀授权 | 凭证泄露后的横向 |
| 3. 前缀 | key 含租户维度；服务端强制拼接，客户端不能构造 | 应用 bug 导致的越权 |
| 4. 加密 | 每租户 DEK（信封加密）+ SSE-KMS；密钥与数据分离 | 磁盘/备份泄露 |
| 5. 审计 | 记录 who → object key → 动作；异常检测 | 事后追责与发现 |

### 5.2 key 布局（内容寻址 + 租户维度）

```
hz-docs/<tenant>/<space_id>/<document_id>/<sha256[0:2]>/<sha256>.<ext>
hz-artifacts/<tenant>/<agent_id>/<session_id>/<artifact_id>-<name>
hz-chat-uploads/<tenant>/<agent_id>/<message_id>/<sha256>.<ext>
hz-code/<tenant>/<project_id>/<version>.bundle       # 代码工程快照（git bundle）
hz-skills/<tenant>/<skill_id>/<version>.tar.zst     # 技能包（内含 manifest.json）
hz-backups/<year>/<month>/<backup_id>/...
hz-audit-archive/<year>/<month>/<day>/...
```

规则：

1. **`<tenant>` 用账号名的哈希**（与现有目录命名口径一致），不出现明文用户名；
2. **key 里不出现用户可控的原始字符串**（文件名只作为后缀白名单校验后的扩展名；
   原始文件名存数据库，下载时通过 `Content-Disposition` 还原）；
3. **内容寻址**：同一内容只存一份；上传天然幂等；对象一旦写入不可变；
4. **对象键只由服务端生成**：`put_stream` 的签名是"接受 tenant/id/内容"，而不是"接受 key"；
   任何暴露"客户端指定 key"的接口都是漏洞；
5. 不使用"每租户一个 bucket"：bucket 数量是稀缺资源，且跨租户统计/迁移困难。隔离靠
   前缀 + 凭证 + 服务端强制；
6. **代码/技能的快照按版本一对象**（`<version>.bundle` / `<version>.tar.zst`），写入后不可变；
   "当前版本"只是数据库里的一个指针，回滚不改写历史对象。

### 5.3 访问路径：唯一入口

```
浏览器 ──▶ 主应用（鉴权 + 授权 + 生成 key）──▶ 对象存储
                     │
知识服务 ────────────┘（只接受主应用签名令牌，不接受自称身份）
```

- 对象存储**不对终端开放**；`presign` 默认关闭（见 §5.4）；
- 知识服务访问对象存储使用**独立的服务账号**，且只能读写 `hz-docs/<tenant>/` 下
  由主应用传入的 key（令牌里带 tenant 与允许的 key 前缀）；
- **禁止**把 S3 凭证放进 `env` 透传给 agent 工具（隔离报告 KB-10 的同类问题）。

### 5.4 下载：代理流式 vs 预签名

| 方式 | 优点 | 风险 | 建议 |
| --- | --- | --- | --- |
| **代理流式**（应用读对象、转发给浏览器） | 权限校验在应用里；对象存储不对外；审计完整 | 双份带宽；应用需流式实现 | **默认** |
| 预签名 URL（浏览器直连对象存储） | 不占应用带宽 | URL 泄露=对象可读（有效期）；需对象存储对终端网段开放 | 可选，仅大文件、短有效期（≤5 分钟）、绑定单对象、记录签发审计 |

实现上做成配置 `STORAGE_DELIVERY=proxy|presign`，**同一时刻只启用一种**，避免"一半走代理
一半走预签名"导致审计缺口。

### 5.5 每租户凭证（纵深防御）

如果客户的合规要求"即使应用被攻破也不能跨租户读"，可以进一步：

- 为每个租户创建独立的服务账号，策略只允许 `s3:GetObject/PutObject/DeleteObject` 于
  `arn:aws:s3:::hz-docs/<tenant>/*`；
- 应用在服务租户请求时**切换凭证**（短期 STS 或 MinIO 的临时凭证）；
- 代价：凭证管理复杂度上升、连接池按租户分裂。
- **建议**：第一阶段先用单一服务账号 + 服务端强制前缀（应用层隔离已经足够强）；
  等客户明确提出"应用被攻破也不许跨租户"时再上每租户凭证。

### 5.6 配额与限流

| 项 | 做法 |
| --- | --- |
| 账号容量配额 | 按前缀累计对象大小（PG 计数或对象存储桶配额），超限时上传端点返回 413 并给出"已用/上限" |
| 单文件上限 | 沿用现有 `KNOWLEDGE_MAX_FILE_MB`（注意它曾经"只能调大不能调小"，已修） |
| 并发上传 | 每账号并发上限 + 全局闸门（避免 50 人同时传大文件打满带宽） |
| 请求速率 | 每账号 PUT/GET 速率限制；异常（大量 LIST）告警 |

### 5.7 加密与密钥

- **传输**：对象存储启用 TLS（内网也建议，至少管理面）；
- **静态**：SSE-S3 或 SSE-KMS；若做每租户隔离，用**信封加密**：
  每租户一个 DEK，用 KMS 主密钥包裹；对象头存 wrapped DEK；
- **密钥管理**：主密钥不与数据同库；轮换与吊销流程写进运维手册；
- **备份**：备份对象同样加密（pgBackRest cipher + SSE）。

### 5.8 审计与异常检测

必须能回答："谁在什么时候、从哪个 IP、取了哪个账号的哪个对象"。

| 记录 | 来源 |
| --- | --- |
| 应用侧：user、action、tenant、key、大小、结果、request_id | 应用审计表（现有 `platform.audit_events` 扩展） |
| 存储侧：访问日志（MinIO audit webhook / Ceph RGW log） | 落到独立日志主题，保留期按合规 |
| 异常规则 | 同一账号访问多个 tenant 前缀；短时间大量 GET；非工作时段批量下载；访问不存在的 key 频率异常（探测） |

### 5.9 反模式清单（评审时逐条对照）

- ❌ 客户端传 `key`、`path`、`bucket`；
- ❌ 用用户名/文件名直接拼 key；
- ❌ 公开读 bucket 或 `*` 策略；
- ❌ 预签名 URL 通配多对象/长有效期；
- ❌ 把 S3 凭证注入 agent 环境变量；
- ❌ 只靠前缀隔离而没有服务端强制（应用 bug 即越权）；
- ❌ 让 LIST 权限对普通账号开放（可枚举他人 key）；
- ❌ 删除时只删数据库行、不删对象（或反之）而无补偿任务；
- ❌ 解析器直接用 FUSE 读对象存储（不确定性进入热路径）。

### 5.10 生成代码与技能的额外要求

这两类是"会执行的内容"，隔离要求比文档多一层：

| 要求 | 做法 |
| --- | --- |
| **来源与版本** | 每个快照记录 creator（username + agent_id）、生成时间、父版本、扫描结果；不可变，修改产生新版本 |
| **启用前扫描** | 技能与可执行代码在物化后、启用前必须过 `skill_scanner`；生产环境 `mode=block`，不要停在 `warn` |
| **执行边界** | 代码只在本地工作副本里执行，且受执行面沙箱约束（见隔离报告 §6.4）；**禁止**从对象存储直接 mmap/执行 |
| **租户前缀** | `hz-artifacts/<tenant>/code/...`、`hz-artifacts/<tenant>/skills/...`；key 由服务端生成 |
| **分享** | 只走现有"分享 → 审批 → 复制"流程；分享的是快照引用与副本，不是共享同一前缀 |
| **审计** | 记录"谁在何时物化并执行了哪个版本"；跨账号命中即告警 |
| **配额** | 代码/技能快照单独计数；按工程保留 N 版，避免只增不删 |

### 5.11 与现有账号模型的对齐

现有模型是"账号根目录 + resolve 校验"。对象存储版本必须保持同样的判定：

| 现有 | 对象存储 |
| --- | --- |
| `get_user_root(username)` | `tenant_prefix(username)` |
| `ensure_inside_account(path)` | `assert_key_in_tenant(key, tenant)` + 服务端生成 key |
| 文件工具拒绝越界 | `StoragePort` 只接受"资源引用"，不接受裸 key |
| 预览限定账号根 | 代理下载时按 `documents.owner_id` 校验后再取对象 |

**判据**：把 `ensure_inside_account` 的测试用例平移到对象存储实现上，必须全部通过。

## 6. 部署与容量

### 6.1 拓扑建议

| 场景 | 建议 |
| --- | --- |
| 单机（当前形态） | 对象存储与应用**同机但独立磁盘**；MinIO 单节点（无纠删码，仅防盘故障靠 RAID）——**不推荐**，等于换个地方放单点 |
| 3 台以上（推荐） | MinIO 3 节点独立部署（或复用应用节点但独立数据盘），万兆内网 |
| 客户已有存储 | 直接接入，应用侧只配 endpoint/凭证 |
| 与 PG 的关系 | **不要与 PostgreSQL 共用数据盘**：PG 的 fsync 与对象的顺序写互相干扰 |

### 6.2 容量公式与档位

```
可用容量 ≈ 裸盘容量 × 可用率 × 0.8(预留)
可用率 = N / (N + M)   （EC:N+M，即数据盘 N、校验盘 M）

关键约束（比容量公式更重要）：
  任一节点故障时丢失的盘数必须 ≤ M。
  例：3 节点 × 每节点 4 盘 = 12 盘，单节点故障会丢 4 盘，
      因此必须 M ≥ 4（EC:4+4），可用率 8/12 ≈ 67%。
  只配 EC:2 的话，丢一块盘没事，丢一个节点就整池不可用。
```

| 档位 | 知识文档 | 生成物+附件 | 备份 | 可用容量需求 | 配置建议（裸容量） |
| --- | --- | --- | --- | --- | --- |
| 小 | 200GB | 100GB | 200GB | ~500GB | 3 节点 × 2×2TB = 12TB（EC:2+2 可用 50% → 4.8TB） |
| 中 | 1TB | 500GB | 1TB | ~2.5TB | 3 节点 × 4×2TB = 24TB（EC:4+4 可用 67% → 9.6TB） |
| 大 | 5TB | 2TB | 5TB | ~12TB | 4 节点 × 4×4TB = 64TB（EC:4+4 → 25TB） |
| 很大 | 20TB+ | 10TB | 20TB | ~50TB | 4+ 节点 × 8×8TB / Ceph（3 副本可用 33%） |

（按 20% 预留估算；实际按 §1.3 的实测数据替换。校验盘数量要按"单节点故障丢盘数"
反推，不要照抄默认值。）

### 6.3 性能量级（50 人）

| 负载 | 估算 | 结论 |
| --- | --- | --- |
| 上传 | 50 人 × 5 份/天 × 5MB ≈ 1.25GB/天 | 吞吐可忽略；瓶颈在解析不在存储 |
| 解析读取 | 每文档一次整读（≤10GB） | 顺序读，本地 scratch 缓存后不受网络限制 |
| 预览/下载 | 峰值几十次/分钟 | Range 读；代理流式 |
| 备份 | 每日增量 + WAL | 与业务错峰 |

**结论**：本场景的存储需求是"容量与耐久"，不是 IOPS。**不要为了性能过度设计**。

### 6.4 网络与磁盘

- 万兆内网（1Gbps 下 10GB 文档单次读取约 80 秒，会明显拖慢解析）；
- 数据盘 NVMe/SSD 优先（对象存储的元数据操作对延迟敏感）；HDD 适合冷数据/备份；
- 时钟同步（NTP）必须可靠——签名对时间偏差敏感（±15 分钟即失败）。

## 7. 迁移方案（可回滚）

### 7.1 五个阶段（每阶段独立可回滚）

| 阶段 | 动作 | 回滚 |
| --- | --- | --- |
| 1 双写 | 新上传同时写本地与对象存储；读取仍走本地；新增 `storage_key` 列 | 配置项关掉双写 |
| 2 回填 | 后台把存量文档复制到对象存储（按 `documents` 表遍历、幂等、可中断） | 不切读即无影响 |
| 3 影子读 | 5% 请求从对象存储读并与本地比对（大小 + sha256），只记日志 | 关采样 |
| 4 切读 | 默认从对象存储读；本地作为 fallback（文件被清理时仍能服务） | 配置切回本地 |
| 5 停双写 + 下线 | 只写对象存储；本地文件保留一个版本周期后清理 | 保留本地目录与代码路径一个版本 |

**顺序不可颠倒**：没有双写就回填 → 回填期间的新文件会丢；没有影子读就切读 → 兼容性问题
要等用户报错才发现。

### 7.2 回填与校验

- 回填按 `documents.id` 分页，**每批记录进度**（可续跑）；失败逐条记录、不中断整批
  （对应本仓库"清理循环必须逐个容错"的教训）；
- 校验：对象大小 + sha256 与数据库一致；抽样做 Range 读（验证分片）；
- **反向巡检**：每小时抽 N 条"有行必有对象"，缺失立即告警（用户可见的坏数据）；
- 孤儿对象：标记-清除，宽限期 24 小时再删（防误删）。

### 7.3 备份策略的变化

| 现在 | 改造后 |
| --- | --- |
| 备份 zip 打包工作区 | pgBackRest 全量+增量+WAL → 对象存储；工作区/生成物靠对象存储版本化 |
| 手动/定时脚本 | 定时任务 + 恢复演练（季度） |
| 本机一份 | 对象存储多节点 + 可选的跨站点复制 |

注意：**备份对象要单独一个 bucket 并开 Object Lock**，且与在线数据使用不同的凭证
（防勒索/误删）。

### 7.4 与"会话状态迁 PG"的关系

对象存储迁移**不解决**会话状态的高频写问题。两者是独立项目：

- 对象存储：文档/生成物/备份（本评估）；
- 会话状态：`state.json` → PostgreSQL（行级更新），同时把 checkpoint 的 git 存储策略重新评估。
- 如果先做对象存储、后做状态迁移，中间不会有冲突；**建议按这个顺序**（对象存储风险低、
  收益直接）。

## 8. 稳定性验证（不能只看"能跑"）

### 8.1 故障注入清单

| 故障 | 期望 |
| --- | --- |
| 杀 1 个存储节点 | 读写继续（EC:2）；`heal` 自动/手动触发并在预期时间内完成 |
| 拔 1 块盘 | 同上；告警；重建不影响在线请求 |
| 存储网络分区 30 秒 | 请求失败快速返回（有超时），不拖垮应用事件循环；恢复后自动重连 |
| 容量写满 | 上传返回明确 507/413；不产生半截对象；不阻塞读取 |
| 时钟偏差 20 分钟 | 签名失败有明确错误（提前发现 NTP 问题） |
| 慢盘（延迟 1s） | 应用超时生效；线程池不被占满（`POOL_FILE` 池有界） |
| 对象存储整体不可用 | 上传快速失败（可读错误）；已缓存文档仍可预览；应用其他功能不受影响 |

### 8.2 一致性验证

- 每次上传后：`stat` 大小 + `sha256` 与本地计算一致；
- 抽样 Range 读（首/中/尾各一段）拼接后 hash 一致；
- 并发上传同一内容：只产生一个对象（内容寻址），数据库行按所有者各自记录；
- 删除后：对象不存在（`stat` 返回 None），数据库行不存在，GC 不误删其他引用。

### 8.3 恢复演练

- 从对象存储恢复一份 30 天前的文档，校验可解析、可预览；
- 从备份恢复 PG 到独立实例，与对象存储的文档对上（抽样 100 条）；
- 演练记录进运维手册（客户验收会看）。

### 8.4 基准与兼容性冒烟

- MinIO：`warp` 或 `mc bench` 跑 4KB/1MB/64MB 混合负载，记录 P50/P95；
- 客户既有存储：先跑**兼容性冒烟**——multipart 上传（>100MB）、Range GET、presign、
  版本化、Object Lock、中文/特殊字符 key、时钟偏差；
- 应用侧：上传/下载/预览/删除四条链路各跑 100 次，检查无内存在增长。

### 8.5 观测指标

| 指标 | 告警阈值（建议） |
| --- | --- |
| 对象存储可用性 | 连续 3 次探测失败 |
| PUT/GET P95 延迟 | > 1s（内网） |
| 错误率（5xx/超时） | > 1% 持续 5 分钟 |
| 容量水位 | > 80% 警告，> 90% 严重 |
| `heal` 状态 | 有未完成 heal 超过 1 小时 |
| 孤儿对象/缺失对象巡检 | 任意缺失即告警 |
| 上传失败率（按账号） | 单账号 > 10% 持续 10 分钟 |

## 10. 结论与建议

### 10.1 建议的决策

| 决策 | 建议 |
| --- | --- |
| 做不做 | **做**：业务文件全量迁移（知识库原件、聊天附件、生成物、导出包、备份）；生成代码与技能按"快照 + 本地物化"迁；运行时文件保留；会话状态另立项目迁 PG |
| 选型 | 客户既有 S3 ＞ MinIO 3 节点 ＞ Ceph RGW（有 Ceph 时）＞ SeaweedFS（AGPL 受阻时） |
| 接口 | StoragePort + LocalFs/S3 双实现，不直接散调 SDK |
| 解析器 | 本地 scratch + LRU + 配额，**不上 FUSE** |
| 下载 | 默认代理流式；预签名作为可选（短时效、单对象） |
| 隔离 | 内容寻址 key + 租户前缀 + 服务端唯一入口 + 配额 + 加密 + 审计 |
| 迁移 | 双写 → 回填 → 影子读 → 切读 → 停双写，每步可回滚 |

### 10.2 分阶段

| 阶段 | 内容 | 工期 |
| --- | --- | --- |
| P0 | 测量现有数据量；选型会（含法务）；兼容性冒烟 | 1 周 |
| P1 | StoragePort + S3 实现 + 双写 + 回填 + 影子读 | 2–3 周 |
| P2 | 切读 + 解析器 scratch + 配额 + GC/巡检 + 代码/技能快照与物化 | 2–3 周 |
| P3 | 备份迁 pgBackRest→对象存储；Object Lock/版本化；故障演练 | 1–2 周 |
| P4（独立） | 会话状态迁 PG；checkpoint 策略重评 | 2–3 周 |

### 10.3 需要你确认的输入

1. **客户是否已有 S3 兼容的对象存储**（品牌、版本、是否支持 versioning/Object Lock/presign）；
2. **现网数据量**（§1.3 的三条命令输出）；
3. **许可约束**：AGPL 是否可接受（决定 MinIO 还是 SeaweedFS/客户存储）；
4. **服务器与网络**：几台可用、是否有万兆、是否愿意为存储单独加 3 台/独立盘；
5. **交付形态**：客户自建还是我方托管（决定凭证与密钥管理方式）；
6. **是否需要"应用被攻破也不许跨租户"**（决定是否上每租户凭证/信封加密）；
7. **生成代码是否需要在线浏览/协作**（决定只存 bundle，还是加一个 Gitea/GitLab）。

这六项确认后，§6.2 的容量档位与 §4.4 的选择树可以收敛成唯一方案，再进入实现。
