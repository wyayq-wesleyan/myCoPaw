# 50 人并发改造方案

> 目标：把系统从"能跑"改造到"**50 人同时使用不排队恶化、不互相拖垮**"。
>
> 本方案基于对现有代码的逐项核查（含实测数据），不是推测。每一项都标注了
> **实测依据**、**改动风险**、**与其它改动的交互**、**验证方式**、**回滚方式**。
>
> 编写日期：2026-10-10　适用版本：`huizhi-runtime:2.2.1`

---

## 0. 结论摘要

### 0.1 真正的瓶颈排序（按"决定 50 人能否可用"排序）

| # | 瓶颈 | 性质 | 现状实测 | 影响 |
| --- | --- | --- | --- | --- |
| **B1** | **模型服务并发只有 6** | 部署/架构 | `QWENPAW_LLM_MAX_CONCURRENT=6` | ❌ 50 人排队，长任务击穿 300s 上限直接报错 |
| **B2** | **全应用共享 ≤32 线程的同步 IO 池** | 代码/架构 | `to_thread` 默认 `min(32, cpu+4)` | ❌ 50 人 × 每 2s 一次 checkpoint ≈ 50 任务/秒 抢 32 线程 |
| **B3** | **checkpoint 每 2 秒整文件重写 4MB** | 代码 | 实测 state.json 4MB（1.9MB 图片 base64） | ❌ 50 人 = 100MB/s 写盘 + 大量 JSON 序列化 |
| **B4** | **21 个 async 端点直接跑同步 DB** | 代码 | `paths.py` 等，0 处 `to_thread` | ❌ 单个慢查询卡死**所有**用户的请求 |
| **B5** | **轮询放大** | 前端 | 2.5s / 3s 轮询；`/paths/tree` 每次 42 次 DB + 全量分页 HTTP | ❌ 空转即产生 ~840 DB 操作/秒 |
| **B6** | 平台库连接池仅 8 条 | 配置 | 第 9 个并发开始排队 | ⚠️ 抖动 |
| **B7** | 知识 worker 单线程串行 | 代码/部署 | 一次只处理一个文档，MinerU 超时 15 分钟 | ⚠️ 上传高峰排长队 |
| **B8** | 审计进程锁 + 每工具调用一次插入 | 代码 | 全局 `RLock` 串行 | ⚠️ 工具密集时成串行点 |
| **B9** | shell 工具无并发上限 | 代码 | 无 semaphore | ⚠️ 可无限堆子进程 |
| **B10** | 无自动备份 | 运维 | 仅 README 手动步骤 | ⚠️ 数据风险 |

### 0.2 改造原则（这是"不制造新问题"的核心）

1. **先测量，再改**：每阶段上线前后都跑同一套压测脚本，用数字判断是否真的改善。
2. **一次只改一层**：并发改造牵一发动全身（线程池、连接池、锁、状态存储互相耦合），分层推进、每层可独立回滚。
3. **先加"上限与隔离"，再"放开并发"**：没有背压的放开并发只会把过载点从 A 挪到 B。
4. **不改变数据语义**：checkpoint / 转录的**内容与恢复语义必须保持一致**，只改"怎么写、写多频"。
5. **失败要可见**：任何新增限制（池满、队列满）都必须给出**可读原因**，不能退化成一个光秃秃的超时。

## 1. 现状容量评估（实测）

### 1.1 进程与线程

| 项 | 实测值 | 来源 |
| --- | --- | --- |
| 主应用进程数 | **1**（`workers=1`，`--workers` 已废弃） | `cli/app_cmd.py:156` |
| asyncio 默认线程池 | **≤32**（`min(32, cpu+4)`） | Python 3.12 语义 |
| 知识服务 api / worker | 各 **1 进程** | compose `command` |
| 知识 worker 处理并发 | **1**（单 `while True` + `claim_job`） | `worker.py:139` |

> **关键**：`run_sync_io` / `asyncio.to_thread` 全部落到**同一个**默认线程池。全应用所有同步 IO（DB、文件、子进程）共享这 ≤32 个线程。

### 1.2 一次对话回合的开销

| 操作 | 频率 | 走线程池? |
| --- | --- | --- |
| session checkpoint | **每 2 秒** | 是（2 次 `run_sync_io`） |
| checkpoint 数据量 | **4MB**（图片 base64 1.9MB + tool_result 1.9MB） | — |
| 转录写入 | 每消息/每 tool_result 一行 | 是（`to_thread`） |
| 审计插入 | 每工具调用一次 | 否（直接），但有进程锁 |
| LLM 流式 | 整轮 | 否（网络） |

**50 人同时对话的推演**：
```
checkpoint: 50 人 ÷ 2 秒 = 25 次/秒 × 2 次线程跳 = 50 个线程任务/秒
每个任务: 序列化 4MB JSON + 写盘
可用线程: ≤32
```
→ **线程池在 50 人满负载时是饱和状态**，任何额外同步 IO（保存会话、读配置、写文件）都要排队。

### 1.3 数据库连接

| 池 | 每进程上限 | 数量 | 小计 |
| --- | --- | --- | --- |
| 平台库（platform_store） | 8 | 1 进程 | 8 |
| 数据表元数据池 | 10 | 1 进程 | 10 |
| 数据表目标池 | 16 池 × 2 | 1 进程 | 32 |
| 知识服务 store | 30 | 2 进程 | 60 |
| 图谱共享池 | 8 | 2 进程 | 16 |
| **合计** | | | **≈126** |
| PostgreSQL `max_connections` | | | **200** |

### 1.4 事件循环阻塞点（精确清点）

**21 个 async 端点存在同步 DB 调用**（脚本扫描，非估计）：

```
agents.py:        create_agent / copy_agent / delete_agent
knowledge.py:     migrate_legacy_graph_workspaces / _resolve_path_document_filter
                  / upload_knowledge_document / delete_knowledge_document
paths.py:         list_paths / path_tree_with_contents / create_path / rename_path
                  / move_path / delete_path / list_assignable_resources
                  / bind_resource / unbind_resource / unbind_resource_any_path
                  / bind_agent / unbind_agent
providers.py:     list_all_providers / delete_custom_provider_endpoint
```

其中 `path_tree_with_contents` 最重：**42 次平台库操作 + 全量分页拉取文档列表**。

### 1.5 前端轮询

| 页面 | 间隔 | 每次请求 | 触发条件 |
| --- | --- | --- | --- |
| 知识空间 | **2.5s** | `loadDocuments` + `refreshTree`(=`/paths/tree`) | 账号有 pending 任务 |
| 数据空间 | **3s** | `fetchTables` + `loadJobCounts` + `refreshTree` | 账号有导入在跑 |

50 人 × `/paths/tree`(42 DB) ÷ 2.5s ≈ **840 DB 操作/秒**（仅轮询）。

## 2. 分阶段改造计划

> 顺序按 **依赖关系** 排列，不是按重要性。**严禁跳阶段**——例如先把同步 DB 塞进线程池（阶段 2），
> 却不先扩大/隔离线程池（阶段 1），会把线程池打爆，反而更糟。

---

### 阶段 0（前置）：观测能力（必须先做）

**为什么必须先做**：现在的报错都是二手的（"连接已满"来自池，但不知道谁占着）。没有观测，
后面每个优化都无法证伪，只能靠感觉——这正是这个项目此前反复"修了又出"的原因。

| 改动 | 内容 |
| --- | --- |
| 0.1 | 新增 `/api/debug/concurrency`（仅 admin）：返回各池的 `_used`/`_pool`/等待次数/峰值 |
| 0.2 | 新增 `/api/debug/threadpool`：返回默认线程池的活跃/排队估算 |
| 0.3 | 池满、线程池饱和、LLM 排队超时 → **统一记一条 WARN**，含当时的池快照 |
| 0.4 | 提供 `scripts/bench_concurrency.py`：模拟 N 个并发用户跑一轮对话，输出 P50/P95 延迟与失败数 |

**风险**：极低（只读接口 + 日志）。
**验证**：接口能返回真实数字；压测脚本能在本机跑通。

---

### 阶段 1：线程池（B2）

**问题**：全应用共享 ≤32 线程，且**没有区分"快操作"与"慢操作"**。一个 4MB checkpoint
和一个"读配置"抢同一批线程。

**改动**：

| 改动 | 内容 |
| --- | --- |
| 1.1 | 启动时**显式创建**三个专用 executor，替换默认池：`io_fast`（DB/配置，16 线程）、`io_file`（会话/文件，8 线程）、`io_subprocess`（shell/MinerU，4 线程） |
| 1.2 | `run_sync_io` 增加 `pool="fast"\|"file"\|"subprocess"` 参数，默认 `fast`；按调用点归类（**显式归类，不靠猜**） |
| 1.3 | 每个池加**有界队列 + 满时明确报错**（`ThreadPoolBusy`），而不是无限排队 |
| 1.4 | 启动日志打印三个池的容量，便于容量核对 |

**为什么分池而不是只调大**：调大单一池会让"50 个 checkpoint 挤掉所有 DB 查询"变成
"50 个 checkpoint 挤掉 50 个 DB 查询"——只是把墙推远。**分池才是隔离**：慢的文件写
不会占住 DB 查询要用的线程。

**风险与交互**：
- ⚠️ **线程数总量上升**：16+8+4=28，但默认池原本就 ≤32，所以**总线程数不增反略降**。
- ⚠️ `run_sync_io` 被大量调用（脚本扫描确认多处在用），必须**逐个归类**；归类错误只影响
  隔离效果，不会导致功能错误（最坏是同池竞争）。
- ⚠️ **不能在这个阶段把 paths.py 的 DB 调用搬进来**——那是阶段 3，顺序不能反。

**验证**：压测对比前后 P95；确认三个池互不影响（人为压满 `file` 池，`fast` 池仍可用）。
**回滚**：`run_sync_io` 忽略 `pool` 参数、退回默认池即可。

---

### 阶段 2：checkpoint 与状态存储（B3）

**这是最需要"不改变语义"的一处。** 会话状态是崩溃恢复的唯一依据，改错了会丢数据。

**问题**：4MB 整文件、每 2 秒重写；其中 1.9MB 是**图片 base64**，内容在整轮对话里**根本不变**。

**改动（三层，从最安全到最激进）**：

| 改动 | 内容 | 语义影响 |
| --- | --- | --- |
| 2.1 | **大块外置**：`data`(base64 媒体) 与超大 `tool_result` 从 state.json 抽出，按内容哈希存到 `sessions/media/<hash>.bin`；state.json 只留引用 | **无**（读取时按引用回填，内容一致） |
| 2.2 | **降频 + 自适应**：空闲/无新工具结果时 checkpoint 间隔 2s → 10s；有大块变化时立即写 | **轻微**（崩溃时可多丢 ≤8 秒） |
| 2.3 | **增量写**：只重写变化的 state 模块（`agent`/`mode_state` 分开成文件） | 需谨慎（恢复路径要同时读多文件） |

**建议只做 2.1 + 2.2，暂不做 2.3**：2.1 收益最大且语义零风险（内容一样，只是换个地方存）；
2.2 用可量化的"最多丢 8 秒"换 5 倍写入降低，是可接受取舍；2.3 收益已不大（2.1 之后文件已小），
但恢复路径复杂度显著上升，**不值得**。

**风险与交互**：
- ⚠️ **恢复路径**：`get_session_state_dict` / `loops.py` / `inbox_trace_store.py` / `fork.py` 都读
  state.json。外置后**所有读者必须透明地拿到回填后的完整状态**——做法是在 `load_session_state`
  里统一回填，**让上层无感**（这是关键：不能让每个读者各自处理引用）。
- ⚠️ **清理**：外置文件会累积。需要与 state.json 生命周期绑定（会话删除时一并删），并加定期 GC。
- ⚠️ **不能改锁语义**：`get_path_lock` 的保护范围不变（仍以 state.json 路径为键），否则并发写
  会重现此前修过的截断问题。
- ⚠️ **备份兼容**：外置目录必须在备份清单里（`data/working/` 已覆盖，确认路径在其中）。

**验证**：
1. 构造含图片的会话 → 存 → 读 → **逐字节比对回填后状态与原状态一致**；
2. 崩溃演练（写入中途 kill）→ 重启 → 状态可恢复；
3. 压测：50 并发 checkpoint 的写盘量下降 ≥5 倍。

**回滚**：外置为**新增**行为，保留"大块仍内联"的开关；关闭即回旧路径。

---

### 阶段 3：事件循环阻塞（B4）

**问题**：21 个 async 端点直接跑同步 DB，阻塞事件循环。

**改动**：

| 改动 | 内容 |
| --- | --- |
| 3.1 | 逐个把同步 DB 调用包进 `run_sync_io(..., pool="fast")`（阶段 1 已就绪） |
| 3.2 | 或把端点改为同步 `def`（FastAPI 自动进线程池）——**两种都要评估后择一，不混用** |
| 3.3 | **合并 N+1**：`path_tree_with_contents` 的 42 次 DB 调用合并为少数几条查询（见下） |

**关于 3.2 vs 3.1 的取舍（重要，避免制造新问题）**：
- 改 `def`：改动小，但该请求整体占一个线程池线程；**且它内部再调 `run_sync_io` 会形成
  "线程池里的线程再等线程池" → 在池满时可能自锁**。所以**只对"不再嵌套线程池调用"的端点用 `def`**。
- 用 `run_sync_io`：更细粒度，但要确保**不嵌套**（同一路径上不要二次 `run_sync_io`）。
- **结论**：统一用 3.1（显式 `run_sync_io`），并在测试里断言"同一调用链不出现嵌套 `run_sync_io`"。

**3.3 的 N+1 合并**（这是 B5 的一半）：
`path_tree_with_contents` 现在做：
```
_account_document_ids  → HTTP 全量分页拉所有文档（page_size=100 循环）
_pending_document_ids  → HTTP 拉 pending
data_tables 查询 registry + import_job  → 2 次
path_store 各节点 count  → N 次
```
优化为：
- 知识服务**新增一个聚合端点** `/v1/paths/summary`，一次返回"文档 id 列表 + pending 集合"；
- 平台库把"每节点 count"改成**一次 GROUP BY 查询**，在内存里按节点分配；
- 结果：**42 次 → ~4 次**。

**风险与交互**：
- ⚠️ 新增知识服务端点 → **主应用与知识服务必须同时升级**（否则老知识服务没有该端点，要回退到旧路径）。**这是本方案唯一需要"双端同步上线"的改动**，必须写进发布说明。
- ⚠️ 合并查询要注意**路径权限语义不变**（仍按授权路径过滤，不能因合并而放宽）。
- ⚠️ 阶段 1 的池必须先生效，否则 21 个端点的 `to_thread` 会挤爆线程池。

**验证**：单端点延迟对比；并发下事件循环不被单个慢查询卡住（人为注入慢查询，其他请求仍响应）；权限矩阵测试全通过。

### 阶段 4：前端轮询（B5）

**问题**：空转即产生大量请求。且已发现问题：轮询只在"账号有 pending"时启动，但**一旦启动就全量刷新**。

**改动**：

| 改动 | 内容 |
| --- | --- |
| 4.1 | 轮询只请求**轻量增量**：新增 `/v1/jobs/pending-count`（已有）+ 只拉**变化的部分**，不重拉整棵树 |
| 4.2 | 间隔自适应：连续 N 次无变化 → 2.5s 退避到 10s；有变化 → 回到 2.5s |
| 4.3 | **页面不可见时暂停**轮询（`document.visibilityState`）——50 人里多数在后台时不产生负载 |
| 4.4 | 知识/数据空间**不要各自轮询整棵树**：改为订阅一个账号级"版本号"，变了才刷新 |

**风险与交互**：
- ⚠️ 退避逻辑可能让"刚完成的任务"延迟显示 → 用 4.4 的版本号机制兜底（服务端**推送变化**而非客户端猜）。
- ⚠️ 不能移除轮询的"跨路径可见性"修复（此前修过：切到别的路径后原路径任务仍在跑）。
  4.4 的账号级版本号**天然满足**这一点，比现在的实现更正确。
- ⚠️ 前端改动需重新构建 `console/dist` 并重启（AGENTS.md 规定）。

**验证**：50 个浏览器标签（含后台）下，服务端 QPS 对比；确认任务状态仍能及时更新。

---

### 阶段 5：知识服务并发（B7）

**问题**：worker 单线程，一次一个文档；大 PDF 解析 15 分钟期间**所有上传排队**。

**改动**：

| 改动 | 内容 |
| --- | --- |
| 5.1 | worker 支持**多副本**：`claim_job` 已用 `FOR UPDATE SKIP LOCKED`（**已确认**），天然支持并发消费；把 worker 容器 `--scale 2`（或 2 个 service） |
| 5.2 | 分**队列分级**：解析（CPU 重）与 embedding（网络重）分开跑，避免大解析挡住小文档 |
| 5.3 | 每个 worker 的心跳已是 `worker_id` 唯一键（**已确认**），多副本不会互相覆盖 |
| 5.4 | PostgreSQL 连接预算要重算：worker 从 1 → 2，知识池 +30、图谱 +8 |

**风险与交互**：
- ⚠️ **CPU 争抢**：MinerU 解析吃满核。多副本必须配合 CPU 上限，否则 50 人的对话服务被解析挤死。
  建议：解析副本限定 `cpus=2`，api 保 `cpus=2`。
- ⚠️ **内存**：worker `mem_limit` 80g；多副本不能简单 ×2（机器装不下）。需按实际模型常驻内存重算。
- ⚠️ **必须先在阶段 0 观测**：否则不知道解析实际占多少资源，多副本会翻车。
- ⚠️ 与阶段 1 交互：解析是**子进程**，走 `io_subprocess` 池，池只有 4 线程 → 解析副本数不应超过它，
  否则线程池又成瓶颈。**5.1 的副本数 ≤ 1.4 的 subprocess 池容量**。

**验证**：并发上传 N 个文档，观察队列消化速度与对话延迟（确认对话不受影响）。

### 阶段 6：容量与运维（B1 / B6 / B8 / B9 / B10）

| 改动 | 内容 | 关键取舍 |
| --- | --- | --- |
| 6.1 | **模型服务扩容**（B1，最重要） | 这是唯一不在代码里的瓶颈。要么提高模型服务并发（vLLM 多副本/张量并行），要么接受排队并把 `LLM_ACQUIRE_TIMEOUT` 提到合理值 + **前端显示排队位置** |
| 6.2 | 平台库池 8 → 20（B6） | 需同步确认 `max_connections`（当前 200，126+32=158 仍有余量） |
| 6.3 | 审计异步批量写（B8） | 改为"入内存队列 + 后台批量 flush"，去掉进程锁串行；**注意崩溃时可能丢最后几条审计**（需评估是否可接受） |
| 6.4 | shell 加全局并发上限（B9） | e.g. Semaphore(4)；超限**明确报错**"当前 shell 任务过多" |
| 6.5 | 自动备份（B10） | cron 每日 `pg_dumpall` + 保留 N 份；**备份期间 IO 影响**要用 nice/ionice 控制 |
| 6.6 | 前端展示排队状态（配合 6.1） | 让"排队中"可见，而不是静默等待或超时报错 |

**风险与交互**：
- ⚠️ 6.1 若模型服务本身不支持高并发，**其它所有优化都白做**——所以这是第一优先，但要先测出模型服务真实能力。
- ⚠️ 6.2 提池会**增加 PG 连接总量**，必须同时算 6.4/阶段 5 的新增，不能只看当前。
- ⚠️ 6.3 改变审计语义（从强一致变最终一致）。**若审计是合规要求，则不能异步**——需你确认。
- ⚠️ 6.5 备份与 checkpoint 抢磁盘 IO，建议错峰（凌晨）并把备份目录与数据目录分盘。

## 3. 改动依赖图（顺序不可颠倒）

```
阶段 0 观测
   │
   ├─► 阶段 1 线程池分池 ──► 阶段 3 事件循环（必须后者先）
   │                              │
   │                              └─► 阶段 3.3 N+1 合并（需知识服务同步上线）
   │
   ├─► 阶段 2 checkpoint（与阶段 1/3 无强依赖，可并行）
   │
   ├─► 阶段 4 前端轮询（依赖 3.3 的聚合端点）
   │
   └─► 阶段 5 知识服务并发（依赖阶段 0 的观测数据定副本数）
                              │
                              └─► 阶段 6 容量（6.2 依赖阶段 5 的连接数增量）
```

**禁止的操作组合**（会制造新问题）：
- ❌ 先做阶段 3（`to_thread`）再做阶段 1（分池）→ 线程池被打爆
- ❌ 阶段 3 用 `def` 端点 + 内部再 `run_sync_io` → 线程池自锁
- ❌ 阶段 5 多副本但不限 CPU → 解析抢光 CPU，对话服务饿死
- ❌ 阶段 5/6.2 加池但不重算 `max_connections` → PG 拒连
- ❌ 阶段 2 外置大块但不改所有读者 → 会话恢复出问题

## 5. 明确不做（及理由）

| 不做 | 理由 |
| --- | --- |
| 应用多 worker（`--workers>1`） | **进程内状态会崩**：文件锁注册表（`io_utils.py:21` 注释明确依赖单 worker）、`TaskTracker` 的 SSE 队列、LLM 限流器、配置缓存全在内存。要做必须先把这些外置（Redis 等），工作量大于收益，**不在本次范围** |
| checkpoint 增量写（2.3） | 2.1 之后收益已小，恢复路径复杂度显著上升 |
| 审计改 PG 表结构 | 只改写入方式（6.3），不动 schema |
| 引入 Redis/消息队列 | 属于架构级更换，需单独评估 |
| 改知识服务的图谱池语义 | 上一轮已修正文档，代码无误 |

## 6. 建议的落地节奏

| 阶段 | 预估工作量 | 可否独立上线 |
| --- | --- | --- |
| 0 观测 | 小 | ✅ 可 |
| 1 线程池分池 | 中 | ✅ 可 |
| 2 checkpoint 外置 | 中 | ✅ 可 |
| 3 事件循环 + N+1 | 大（含知识服务） | ⚠️ 需双端同步 |
| 4 前端轮询 | 中 | ✅ 可 |
| 5 知识服务并发 | 中（含容量调参） | ✅ 可 |
| 6 容量与运维 | 小（6.1 需外部配合） | ⚠️ 6.1 依赖模型服务 |

**建议先做 0 + 1 + 2**：这三项风险低、可独立上线，且能直接缓解 B2/B3（线程池与 checkpoint 这两个
"人越多越恶化"的问题）。**再做 6.1（模型服务容量）验证**，因为它决定后面值不值得投入——
如果模型服务只能扛 6 并发，那 50 人场景需要的是**横向扩容模型服务**，而不是继续抠代码。
