# 50 人并发改造方案

> 目标：把系统从"能跑"改造到"**50 人同时使用不排队恶化、不互相拖垮**"。
>
> 本方案基于对现有代码的逐项核查（含实测数据），不是推测。每一项都标注了
> **实测依据**、**改动风险**、**与其它改动的交互**、**验证方式**、**回滚方式**。
>
> 编写日期：2026-10-10　适用版本：`huizhi-runtime:2.2.1`
>
> **修订（2026-10-13）**：第三轮改造（10.11–10.13）在实施中又发现并修复了 8 处缺陷，其中多处正落在本方案要动的区域（线程池、连接池、审计、导入调度、向量检索）。本次修订做了三件事：① §0.3.1 列出**已修项**，避免把已修的现状当待办；② §0.3.2 给出**缺陷类 avoid 清单**，每条绑定到本方案的具体阶段；③ 补上评审发现的**两个方案自身缺口**（审计阻塞事件循环、启动恢复无 owner 判定）。**实施前必读 §0.3。**

## 0. 结论摘要

### 0.1 真正的瓶颈排序（按"决定 50 人能否可用"排序）

| # | 瓶颈 | 性质 | 现状实测 | 影响 |
| --- | --- | --- | --- | --- |
| **B1** | **模型服务并发只有 6** | 部署/架构 | `QWENPAW_LLM_MAX_CONCURRENT=6` | ❌ 50 人排队，长任务击穿 300s 上限直接报错 |
| **B2** | **全应用共享 ≤32 线程的同步 IO 池** | 代码/架构 | `to_thread` 默认 `min(32, cpu+4)` | ❌ 50 人 × 每 2s 一次 checkpoint ≈ 50 任务/秒 抢 32 线程 |
| **B3** | **checkpoint 每 2 秒整文件重写 4MB** | 代码 | 实测 state.json 4MB（1.9MB 图片 base64） | ❌ 50 人 = 100MB/s 写盘 + 大量 JSON 序列化 |
| **B4** | **21 个 async 端点直接跑同步 DB** | 代码 | `paths.py` 等，0 处 `to_thread`；**同类还有 `audit.record`** | ❌ 单个慢查询卡死**所有**用户的请求 |
| **B5** | **轮询放大** | 前端 | 2.5s / 3s 轮询；`/paths/tree` 每次 42 次 DB + 全量分页 HTTP | ❌ 空转即产生 ~840 DB 操作/秒 |
| **B6** | 平台库连接池仅 8 条 | 配置 | 第 9 个并发开始排队 | ⚠️ 抖动 |
| **B7** | 知识 worker 单线程串行 | 代码/部署 | 一次只处理一个文档，MinerU 超时 15 分钟 | ⚠️ 上传高峰排长队 |
| **B8** | 审计进程锁 + 每工具调用一次插入 | 代码 | 全局 `RLock` 串行，**且在事件循环上同步 INSERT+commit**（平台池满时等待 15s） | ❌ 每次工具调用阻塞**所有**用户；**10-13 修订重新分级**，见 §0.3.3 缺口 1 |
| **B9** | shell 工具无并发上限 | 代码 | 无 semaphore | ⚠️ 可无限堆子进程 |
| **B10** | 无自动备份 | 运维 | 仅 README 手动步骤 | ⚠️ 数据风险 |

### 0.2 改造原则（这是"不制造新问题"的核心）

1. **先测量，再改**：每阶段上线前后都跑同一套压测脚本，用数字判断是否真的改善。
2. **一次只改一层**：并发改造牵一发动全身（线程池、连接池、锁、状态存储互相耦合），分层推进、每层可独立回滚。
3. **先加"上限与隔离"，再"放开并发"**：没有背压的放开并发只会把过载点从 A 挪到 B。
4. **不改变数据语义**：checkpoint / 转录的**内容与恢复语义必须保持一致**，只改"怎么写、写多频"。
5. **失败要可见**：任何新增限制（池满、队列满）都必须给出**可读原因**，不能退化成一个光秃秃的超时。

#### 0.3.2 缺陷类 avoid 清单（每条绑定到本方案的具体阶段）

这 8 处缺陷不是孤立的 bug，而是**同一批模式**。本方案要改的正是这些模式的高发区，
所以逐条给出"在哪个阶段最容易重演 → 具体禁令"。

| 缺陷类 | 实际案例 | 本方案中高风险位置 | 禁令（实施时必须做） |
| --- | --- | --- | --- |
| **A. 状态标记不回滚 → 永久降级** | 导入调度标记；pgvector 否定结论 | 阶段 1 新池的"已创建/已耗尽"标记；阶段 5 worker 的 `processing` 标记 | 任何"先标记、后可能失败的动作"都必须 **try/finally 回滚标记**；标记的写入与清除要在同一函数内可见 |
| **B. 只增不删的进程内集合** | `_bg_tasks`；rate_limiter 键空间 | 阶段 0 的观测计数器；阶段 1 池的等待统计；**阶段 6.3 审计内存队列** | 新增的每个内存集合都要**同时给出上限与回收时机**，并在阶段 0 的观测接口里暴露当前大小 |
| **C. 连接借还与池键不一致** | `data_tables` 借还键错位（线上故障根因） | **阶段 1 新分池**、阶段 3 `run_sync_io` 迁移 | 池键必须**从连接/任务自身的元数据恢复**，不依赖调用方重复传参；加一条"借出后立刻归还"的自检 |
| **D. 在启动路径做重活** | HNSW 索引同步建 → 22s 阻塞 → 503 | **阶段 2 checkpoint 外置的回填**、阶段 5 多副本启停、阶段 6.5 备份 | 启动路径只允许"轻量、幂等、可失败"的动作；重活交给后台/worker 空闲分支，并且**必须能在不启动的情况下验证** |
| **E. 缓存否定结论** | pgvector `_vector_column_available` | 阶段 1 "池不可用"缓存；阶段 6.1 "模型服务不可用"缓存 | 只缓存**肯定**结论；否定结论要么不缓存，要么带短 TTL + 明确失效条件 |
| **F. `finally`/异常路径引用可能未绑定的变量** | `importer.py` | 阶段 3 把 21 个端点搬进线程池时的 `try/finally` | 异常路径里只允许引用**在 try 之前已绑定**的变量；真实错误不能被替换成 `UnboundLocalError` |
| **G. 清理/回收循环无逐个容错** | `acp/service.py` | 阶段 2 外置文件 GC；阶段 5 worker 的 stale 回收；阶段 6.5 备份轮转 | 循环内**每个对象单独 try/except 并记录**；单个失败不得中断整轮，也不得让 `finally` 抛出 |
| **H. 阻塞调用放在事件循环上** | `paths.py` 端点；**`audit.record`（见 §0.3.3）** | **阶段 3 的全部内容** | 事件循环上不出现同步 DB / 同步文件 / 长等待；迁移后用"注入慢查询，其余请求仍响应"验证 |

**变异验证是硬要求**：第三轮确立的口径是"每处修复都配回归测试，并**把修复回退，确认
测试精确失败**"。本轮已多次抓到"测试其实测不中目标"（例如某测试替换掉整个
`_create_table_sync`，删掉真正的调用点它照样通过；另有一处缩进检查无论对错都通过）。
本方案每个阶段新增的测试都必须做这一步，否则视为未完成。

#### 0.3.3 评审补充：方案自身的两个缺口（10-13 发现）

**缺口 1（严重性判断偏低）：B8 审计不是"串行点"，是事件循环的阻塞点。**

§0.1 把 B8 列为 ⚠️"工具密集时成串行点"，但实测路径是：

```
audit.py: record()  → with self._lock (全局 threading.RLock)
                    → get_conn()   (平台池，max 8)
                    → INSERT platform.audit_events + commit()
```

而它是从 **`async def _policy_tool_check_permissions`（`governance/tool_adapter.py`）里
同步调用**的 —— 也就是跑在事件循环上。后果比"串行"严重得多：

- **每次工具调用都阻塞全部用户**（事件循环停住 → SSE、轮询、心跳全停）；
- 平台池满时 `get_conn()` 会等待 **`POOL_WAIT_SECONDS = 15.0` 秒**，这 15 秒整个应用
  是冻结的。

这恰好对应正式环境观察到的"稍微用一用就报 pool exhausted" + "页面特别卡、干什么都慢
一拍"。因此：

- **B8 应重新分级为 ❌，与 B2/B4 同级**（本方案的核心场景恰好是工具密集）；
- **修复顺序应提前**：把 `governor.audit(...)` 包一层 `run_sync_io` 即可，改动极小、
  风险极低，是全部 8 项里性价比最高的一处。建议作为**阶段 1.5**（见 §2 阶段 1.5）。
- **§6.3 的顺序要倒过来**：第一步是"搬离事件循环"，第二步才是"要不要批量异步写"。
  把需要合规确认的语义讨论排在前面，会卡住一个本来零风险、可立刻做的改动。

**缺口 2（会导致阶段 5 直接失败）：启动恢复无 owner 判定。**

`knowledge-service/app/store.py: recover_interrupted_jobs()` 无条件重排**所有**
`processing` 任务：

```sql
UPDATE jobs SET status = 'queued' WHERE status = 'processing'   -- 无 owner / heartbeat 判定
```

单副本下正确（启动即意味着唯一的 worker 死了）；**多副本下是错的**——任一 worker 重启
都会抢走其他存活 worker 正在处理的任务 → **重复解析、重复 embedding、重复写图谱**。

修法明确：启动恢复也要带 owner/heartbeat 判定（或直接删掉启动那次、只保留已有的
`requeue_stale_jobs` 定时 sweep）。**这一步必须先于阶段 5.1**。

**已实施（2026-10-13，含一次复审发现的重启回归修复）**：第一版按"心跳行是否引用该
job"判定，复审发现它把"某 worker 心跳新鲜"误当成"该 job 的 owner 存活"——心跳行按
worker 每 ~10s 无条件刷新，与它命名的是哪个 job 无关，于是 fast restart 会把死 worker
的任务搁置到小时级 sweep 才回收（实测复现：HEAD 立即回收 vs 新版 0 回收）。现实现：
`jobs.owner_worker_id` 记录归属（claim 与心跳同事务写入）、恢复按 **owner 的心跳新鲜度**
判定、worker 以固定 `KNOWLEDGE_WORKER_ID`（会话级 advisory lock 保证同 id 不双活）
启动时通过 `reclaim_owner` 立即收回自身前世任务、idle 分支每 60s 周期回收兜住非重启类
死亡、心跳行按 24h 保留期清理。测试：`test_startup_recovery_respects_owner.py`（静态
守卫 + live-PG 行为用例）。

**两处与原文的刻意偏离**（都是为避免制造新问题）：

1. **没有把默认 executor 指向 `fast` 池。** 原文阶段 1 的论证是「16+8+4=28 < 32，所以总线程数
   不增反降」，这个论证不成立：默认 executor 不会因为新建三个池就消失，而全仓仍有约 250 处
   直接调用 `asyncio.to_thread`，把默认池换成一个 16 线程的池会**静默砍掉它们一半容量**。
   现在的做法是保留默认池，只让 `run_sync_io` 的调用点按用途分流。分池的目的是隔离，不是
   线程总数——B2 的实质问题是「慢的文件写挤掉快的 DB 读」，这一点已经解决。
   迁移那 250 处是后续可选项，不是前置条件。
2. **`POOL_WAIT_SECONDS` 未在本次调整。** 原文 §6.2 要求「提池时一并决定等待时长」。本次
   没有改平台池大小，所以保持 15 秒不变；但审计已不在事件循环上，15 秒的等待现在只影响
   工作线程，不再冻结应用。等待语义仍应在 §6.2 与提池一起定。

### 1.2 一次对话回合的开销

| 操作 | 频率 | 走线程池? |
| --- | --- | --- |

| 转录写入 | 每消息/每 tool_result 一行 | 是（`to_thread`） |
| 审计插入 | 每工具调用一次 | **否（在事件循环上直接执行）**，有进程锁；**10-13 补：平台池满时等待 15s → 冻结全应用**（§0.3.3 缺口 1） |
| LLM 流式 | 整轮 | 否（网络） |

**50 人同时对话的推演**：
```
checkpoint: 50 人 ÷ 2 秒 = 25 次/秒 × 2 次线程跳 = 50 个线程任务/秒
每个任务: 序列化 4MB JSON + 写盘
可用线程: ≤32
```
→ **线程池在 50 人满负载时是饱和状态**，任何额外同步 IO（保存会话、读配置、写文件）都要排队。

> **与已修项的边界**：checkpoint 仍然"每 2 秒整文件重写"（未修），但**瓶颈的形态在 10-13 后
> 略有变化**——平台库与数据表池现在有界等待（池满排队而非 500），所以"线程被打满"会先表现为
> **延迟上升**而不是报错。缺陷类 D/G 的禁令（§0.3.2）适用于本阶段外置方案（回填离开启动路径、
> GC 逐项容错）。

### 阶段 1：线程池（B2）— ✅ 已实施

**问题**：全应用共享 ≤32 线程，且**没有区分"快操作"与"慢操作"**。一个 4MB checkpoint
和一个"读配置"抢同一批线程。

**改动**：

| 改动 | 内容 |
| --- | --- |
| 1.1 | 启动时**显式创建**专用池（`utils/io_pools.py`）：`fast`（DB/配置，16 线程+64 队列）、`file`（会话 checkpoint/远程下载，8+32）、`subprocess`（shell/git/chromium，8+16）、`audit`（治理审计专用单线程通道，1+256） |
| 1.2 | `run_sync_io` 增加 `pool=` 参数，默认 `fast`；已显式归类：会话 checkpoint 读写→`file`、审计写→`audit`、远程下载→`file`、shell Windows 同步路径 / chromium spawn+kill / browser worker 进程 spawn/terminate / `run_command_async`→`subprocess`。**其余 ~100 处 `run_sync_io` 调用点仍走默认 `fast`**（含若干较长操作），逐个归类是后续工作；直接 `asyncio.to_thread` 的 ~250 处不在任何池内 |
| 1.3 | 每个池加**有界队列 + 满时明确报错**（`ThreadPoolBusy`），而不是无限排队；audit 通道有独立的更短等待预算（`QWENPAW_IO_AUDIT_WAIT_SECONDS`，默认 30s） |
| 1.4 | 启动日志打印各池容量；修复时顺带补上 **contextvars 传播**（`run_in_executor` 不会像 `to_thread` 那样复制 context，已改为 `contextvars.copy_context()` 派发，并有回归测试） |

**为什么分池而不是只调大**：调大单一池会让"50 个 checkpoint 挤掉所有 DB 查询"变成
"50 个 checkpoint 挤掉 50 个 DB 查询"——只是把墙推远。**分池才是隔离**：慢的文件写
不会占住 DB 查询要用的线程。

**风险与交互**：
- ⚠️ **线程数总量持平**：16+8+8+1=33，与默认池原本的 ≤32 基本相当（audit 池 1 线程）。
- ⚠️ 未归类的 `run_sync_io` 调用点（尤其远程下载前的较慢操作）仍在 `fast` 池内竞争，
  归类错误只影响隔离效果，不会导致功能错误（最坏是同池竞争）。
- ⚠️ **不能在这个阶段把 paths.py 的 DB 调用搬进来**——那是阶段 3，顺序不能反。

**验证**：压测对比前后 P95；确认三个池互不影响（人为压满 `file` 池，`fast` 池仍可用）。
**回滚**：`run_sync_io` 忽略 `pool` 参数、退回默认池即可。

### 阶段 1.5：审计搬离事件循环（B8，10-13 新增，建议优先做）— ✅ 已实施

**为什么插在这里**：审计是**唯一一处"改动极小、但命中 B4+B8 两类"**的修复，收益/风险比
最高；且必须在阶段 1 的池就绪之后、阶段 3 之前做——因为它本身就是一次"把同步 DB 调用
搬进线程池"的演练，用的还是同一个 `fast` 池。

**问题**（§0.3.3 缺口 1）：`audit.record()` 从 `async def _policy_tool_check_permissions`
同步调用，每次工具调用都在**事件循环**上做一次 `INSERT`+`commit`，并持全局 `RLock`；
平台池满时等待 15 秒 → 全应用冻结。

**改动**：

| 改动 | 内容 |
| --- | --- |
| 1.5.1 | `governor.audit(...)` 包进 `run_sync_io(..., pool="audit")`，把 `INSERT`+`commit` 移出事件循环，并放进**专用单线程审计通道**（`utils/io_pools.py` 的 `audit` 池：1 线程 + 256 队列 + 独立 30s 等待预算）——审计写由日志自身的 `RLock` 串行化，专用通道让它既不会被 fast 池挤掉、也不会反过来拖住工具调用；通道积压满 30s 后按既有"尽力而为"契约丢弃该条并记 ERROR |
| 1.5.2 | 现有契约不变：**审计写失败仍不传播、不打断策略决策**（`record()` 已 catch，改造后要保持） |
| 1.5.3 | `RLock` 保留（它保护的是连接借还的顺序，不是性能来源）；**去掉锁不是本阶段目标**，阶段 6.3 再议 |

**为什么不是直接做 §6.3 的"内存队列 + 批量 flush"**：那是**语义变更**（强一致 → 最终一致，
需合规确认），而 1.5 是**纯位置变更**（同一把锁、同一次写，只是不在事件循环上）。
顺序颠倒会把一个零风险改动卡在合规讨论上。

**风险与交互**：
- ⚠️ **不能嵌套** `run_sync_io`：确认 `_policy_tool_check_permissions` 的调用链上
  （含 `assert_policy`）没有其它已进池的同步 IO。这与阶段 3 是同一条约束
  （§3 的"禁止组合"第 2 条）。
- ⚠️ 工具调用非常频繁——这正是给审计建**专用通道**而不是并入 `fast` 池的原因：
  审计大概率在那个池里是最频繁的访客。
- ⚠️ 属于 §0.3.2 缺陷类 **H**（阻塞调用在事件循环上）与 **C**（借还键）的双重高发点。

**验证**：
1. 注入慢查询（`pg_sleep`）后，**其它用户的请求仍能响应**（改造前会整体冻结）；
2. 人为把平台池占满，确认事件循环不被冻结，且审计失败有可读日志；
3. 回归：策略决策与审计记录**逐条仍一致**（改造是位置变更，不应改变任何一条审计）。

**回滚**：把 `run_sync_io` 去掉、恢复直接调用。改动局部，回滚无副作用。

**问题**：4MB 整文件、每 2 秒重写；其中 1.9MB 是**图片 base64**，内容在整轮对话里**根本不变**。

| 改动 | 内容 | 语义影响 |

### 阶段 3：事件循环阻塞（B4）— ⬜ 未实施

**问题**：21 个 async 端点直接跑同步 DB，阻塞事件循环。

**改动**：

| 改动 | 内容 |
| --- | --- |
| 3.1 | 逐个把同步 DB 调用包进 `run_sync_io(..., pool="fast")`（阶段 1 已就绪） |
| 3.2 | 或把端点改为同步 `def`（FastAPI 自动进线程池）——**两种都要评估后择一，不混用** |
| 3.3 | **合并 N+1**：`path_tree_with_contents` 的 42 次 DB 调用合并为少数几条查询（见下） |

**关于 3.2 vs 3.1 的取舍（重要，避免制造新问题）**：
- 改 `def`：改动小，但该请求整体占一个线程池线程；**且它内部再调 `run_sync_io` 会形成
  "线程池里的线程再等线程池" → 在池满时可能自锁**。所以**只对"不再嵌套线程池调用"的端点用 `def`**。
- 用 `run_sync_io`：更细粒度，但要确保**不嵌套**（同一路径上不要二次 `run_sync_io`）。
- **结论**：统一用 3.1（显式 `run_sync_io`），并在测试里断言"同一调用链不出现嵌套 `run_sync_io`"。

**3.3 的 N+1 合并**（这是 B5 的一半）：
`path_tree_with_contents` 现在做：
```
_account_document_ids  → HTTP 全量分页拉所有文档（page_size=100 循环）
_pending_document_ids  → HTTP 拉 pending
data_tables 查询 registry + import_job  → 2 次
path_store 各节点 count  → N 次
```
优化为：
- 知识服务**新增一个聚合端点** `/v1/paths/summary`，一次返回"文档 id 列表 + pending 集合"；
- 平台库把"每节点 count"改成**一次 GROUP BY 查询**，在内存里按节点分配；
- 结果：**42 次 → ~4 次**。

**风险与交互**：
- ⚠️ 新增知识服务端点 → **主应用与知识服务必须同时升级**（否则老知识服务没有该端点，要回退到旧路径）。**这是本方案唯一需要"双端同步上线"的改动**，必须写进发布说明。
- ⚠️ 合并查询要注意**路径权限语义不变**（仍按授权路径过滤，不能因合并而放宽）。
- ⚠️ 阶段 1 的池必须先生效，否则 21 个端点的 `to_thread` 会挤爆线程池。

**验证**：单端点延迟对比；并发下事件循环不被单个慢查询卡住（人为注入慢查询，其他请求仍响应）；权限矩阵测试全通过。

  4.4 的账号级版本号**天然满足**这一点，比现在的实现更正确。

### 阶段 5：知识服务并发（B7）— 🟡 5.5 已实施

**问题**：worker 单线程，一次一个文档；大 PDF 解析 15 分钟期间**所有上传排队**。

**改动**：

| 改动 | 内容 |
| --- | --- |
| 5.1 | worker 支持**多副本**：`claim_job` 已用 `FOR UPDATE SKIP LOCKED`（**已确认**），天然支持并发消费；把 worker 容器 `--scale 2`（或 2 个 service）。**注意**：5.5 落地后，多副本必须**每个副本一个不同的 `KNOWLEDGE_WORKER_ID`**（compose 默认 `worker-1`） |
| 5.2 | 分**队列分级**：解析（CPU 重）与 embedding（网络重）分开跑，避免大解析挡住小文档 |
| 5.3 | 每个 worker 的心跳已是 `worker_id` 唯一键（**已确认**），多副本不会互相覆盖 |
| 5.4 | PostgreSQL 连接预算要重算：worker 从 1 → 2，知识池 +30、图谱 +8 |
| **5.5** | **✅ 已实施（2026-10-13，含复审回归修复）**：`jobs.owner_worker_id` 记录归属（claim 与心跳**同事务**写入，关闭"claim 后未写心跳被误抢"窗口）；`recover_interrupted_jobs` 按 **owner 心跳新鲜度**判定遗弃（修复第一版按 job_id 匹配心跳行导致 fast restart 搁置任务约 1 小时的回归）；worker 以固定 `KNOWLEDGE_WORKER_ID` + 会话级 advisory lock 启动，`reclaim_owner` 立即收回自身前世任务；idle 每 60s 周期回收兜住非重启类死亡；心跳行 24h 保留期清理 |

**风险与交互**：
- ⚠️ **CPU 争抢**：MinerU 解析吃满核。多副本必须配合 CPU 上限，否则 50 人的对话服务被解析挤死。
  建议：解析副本限定 `cpus=2`，api 保 `cpus=2`。
- ⚠️ **内存**：worker `mem_limit` 80g；多副本不能简单 ×2（机器装不下）。需按实际模型常驻内存重算。
- ⚠️ **必须先在阶段 0 观测**：否则不知道解析实际占多少资源，多副本会翻车。
- ⚠️ 与阶段 1 交互：解析在知识服务自身的 worker 进程内串行执行，不经主应用的
  `io_subprocess` 池；主应用侧该池现为 8 线程 + 16 队列。

**缺口 2（10-13 发现，会导致 5.1 直接失败）**：`store.recover_interrupted_jobs()`
无条件重排**所有** `processing` 任务，**没有 owner/heartbeat 判定**：

```sql
UPDATE jobs SET status = 'queued' WHERE status = 'processing'   -- 无 owner 条件
```

单副本下这是对的（启动即意味着唯一的 worker 死了）。**多副本下是错的**：任一 worker
重启都会把**其他存活 worker 正在处理**的任务抢回队列 → 重复解析、重复 embedding、
重复写图谱。所以 **5.5 必须先于 5.1**。

修法（二选一，优先第一种）：

1. 启动恢复也带 owner/heartbeat 判定（只回收本 worker 实例遗留的、或心跳已过期的行）；
2. 直接删掉启动那次无条件恢复，**只保留已有的 `requeue_stale_jobs`**——它按
   `updated_at` 超时可回收，是天然副本安全的；且 `max_age_seconds` 已按解析超时推导
   （必须**显著大于**最长单阶段耗时，否则会把"健康但慢"的任务抢走，同样造成重复工作）。

**已按方案 1 实施（并经复审迭代）**——见本节"改动"表中 5.5 的 ✅ 行与 §缺口 2 开头的
实施记录；METHOD 上比"job_id 匹配心跳行"更进一步：**`jobs.owner_worker_id` + 对 owner
心跳行的新鲜度判定**。第一版实现（心跳行 `job_id` 匹配 + 60s 宽限）经实测是**不正确的**：
新 worker 的 idle 心跳会被误认为"该 job 的 owner 还活着"，把重启恢复从"立即"变成
"最多 1 小时"。该回归已在本地 PostgreSQL 上复现并修复；`requeue_stale_jobs` 仍保留为
hang 类故障的兜底（它按 `jobs.updated_at` 超时回收，两套语义现在各自独立、不再声称一致）。

**已就位、不要重写的基础（10-13 补）**：`worker_heartbeats`（`worker_id` 唯一键）、
`processing_stage`、`requeue_stale_jobs`（含"用尽次数则 failed 而非反复重排"）、
`fail_job` 的 `next_retry_at::timestamptz` 显式转换。阶段 5 要**建立在这套之上**。

**验证**：并发上传 N 个文档，观察队列消化速度与对话延迟（确认对话不受影响）。
**多副本专项**：跑到一半 `docker restart` 其中一个 worker，确认**没有任务被重复执行**
（文档 chunk 数、图谱写入次数、`attempts` 都不翻倍）。

## 5. 明确不做（及理由）

| 不做 | 理由 |
| --- | --- |
| 应用多 worker（`--workers>1`） | **进程内状态会崩**：文件锁注册表（`io_utils.py:21` 注释明确依赖单 worker）、`TaskTracker` 的 SSE 队列、LLM 限流器、配置缓存全在内存。要做必须先把这些外置（Redis 等），工作量大于收益，**不在本次范围** |
| checkpoint 增量写（2.3） | 2.1 之后收益已小，恢复路径复杂度显著上升 |
| 审计改 PG 表结构 | 只改写入方式（6.3），不动 schema |
| 引入 Redis/消息队列 | 属于架构级更换，需单独评估 |
| 改知识服务的图谱池语义 | 上一轮已修正文档，代码无误 |
| **重复实现第三轮已修项** | 见 §0.3.1：连接池借还键、导入调度回滚、限流器剪枝、`_bg_tasks` 回收、LSP 自愈、ACP 清理容错、pgvector 否定缓存、`fail_job` 时区转换，**全部已在位**；本方案只在它们之上增量改造，不重写 |
| **给知识服务任务重做一套可观测性** | `processing_stage` / `worker_heartbeats` / `requeue_stale_jobs` 已就位（§0.3.1），阶段 5 直接复用 |

**修订后的建议顺序（10-13）**：

1. **阶段 0**（观测）——没有它，后面每一步都无法证伪。
2. **阶段 1.5**（审计搬离事件循环）——改动最小、命中 B4+B8、零语义变更，性价比最高。
   放在这里而不是阶段 6，是因为它同时是"外置同步调用的演练"，为阶段 3 铺路。
3. **阶段 1**（线程池分池）——注意把 §0.3.2 缺陷类 A/B/C 的禁令套上（新池会产生新标记与新集合）。
4. **阶段 2**（checkpoint 外置）——回填必须按缺陷类 D 离开启动路径；外置文件的 GC 按缺陷类 G 写。
5. **先测 6.1（模型服务真实并发）**——它决定后面值不值得持续投入。如果模型服务只能扛 6 并发，
   50 人场景的答案是**横向扩容模型服务**，继续抠代码的收益上限很低。
6. **阶段 3 + 4 一起做**（N+1 合并不是可选项，否则 50 人轮询会把 `fast` 池灌满）。
7. **阶段 5**：**先 5.5（启动恢复 owner 判定）、再多副本**；否则任务会被重复执行。
8. **阶段 6**：6.3 在 1.5 之后；6.2 提池时一并定 `POOL_WAIT_SECONDS`。

**贯穿所有阶段的两条硬要求**（来自第三轮，见 §0.3.2 末）：每个修复都要配回归测试，
并且**把修复回退、确认测试精确失败**；每个新增的内存集合/标记都要给出**上限与回收时机**。
