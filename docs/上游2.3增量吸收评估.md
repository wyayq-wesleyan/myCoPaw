# 上游 2.3 增量吸收评估（199e9558 → 2cf28d14a）

- 评估日期：2026-11-08
- 范围：上游 `agentscope-ai/QwenPaw` 自我们上次对齐点（`199e9558`，2026-10-27）
  到 `2cf28d14a`（2026-11-06）之间的 **87 个提交**，以及新 tag `v2.3.0-beta.2`
- 方法：按改动路径分类 → 对候选逐一看完整 diff → 在本地检索同名函数/常量 →
  判断"是否真实缺失、能否移植、移植风险"；**不按 commit message 批量 cherry-pick**
- 结论：**能直接融的只有 2 项（本次已融）**；另有 6–8 项"需适配"值得单独排期；
  其余约 60 项属于上游 2.3 的新架构或不适用模块。

## 0. 为什么"能融尽融"在这一次只能融两项

上游已经走到 **2.3.0-beta.2**，而我们的基线是 2.2.1 + 大量本地改造。两个关键目录的
差异不是"几个补丁"，而是结构性重构：

| 目录 | 本地 vs 上游 |
| --- | --- |
| `src/qwenpaw/providers/` | 109 个文件、+56561/−4192 行 |
| `src/qwenpaw/plugins/` | 101 个文件、+42131/−1071 行 |
| `src/qwenpaw/agents/skill_system/` | 8 个文件、+1818/−584 行 |
| `src/qwenpaw/agents/context/` | 33 个文件、+3960/−3947 行 |

上游新增了我们没有的模块（`model_error_policy.py`、`shell_resources.py`、
`overflow_recovery.py`、`provider_model_state.py`、`module_isolation.py` 等）。
**任何依赖这些模块的修复，都不是"移植一个函数"，而是"搬一套子系统"**——这类只
在它能解决我们真实痛点、且测试能覆盖时才值得做。

## 1. 本次已融（2 项，均有测试 + 变异验证）

### 1.1 `#8066` 空媒体块（`2d99b016b`）

- **上游改动**：`message_request_normalizer.py` 新增 `_is_empty_media_block()`；在
  `normalize_messages_for_model_request()` 的多模态分支**之前**无条件剥离
  base64 载荷为空的媒体块；同时修正"tool_result 本来为空却被替换成占位符"的问题。
- **本地问题（已确认）**：空 base64 会序列化成 `data:<mime>;base64,`，OpenAI/vLLM/
  DeepSeek 一律 400；一旦写进历史，**整个会话之后每一轮都 400**（与之前修过的空文本块
  同类）。
- **移植**：直接适用。本地 `message_request_normalizer.py` 有同名的
  `_strip_media_blocks_in_place` / `_is_media_block`，只需加判定与调用。
- **新增测试**（`tests/unit/agents/test_message_request_normalizer.py`）：
  空媒体被剥离、非空媒体保留、tool_result 内空媒体被剥离、本就空的 tool_result 不被
  改成占位符、URL 源不被误删。
- **变异验证**：去掉 `empty_only` 调用 → 2 条失败；`if stripped_count` 改成 `if True`
  → 1 条失败。

### 1.2 `#8198` 技能二进制导入（`c935c7fe7`）

- **上游改动**：`hub.py` 的 `files` 映射允许 `bytes`；`SKILL.md` 按 UTF-8 解码（非法
  编码报 `SkillsError`）；其余文件原样传递；`store.py` 的 `_create_files_from_tree`
  对 `bytes` 用 `write_bytes`。
- **本地问题（已确认）**：本地 `_files_to_tree` / `_normalize_bundle` 只接受 `str`，
  二进制附件（图片/字体/模板）会被跳过或损坏；`_github_read_file` 把所有内容按文本
  解码，`errors="replace"` 会把二进制写坏。
- **移植**：直接适用（本地 `_http_bytes_get` 已存在，无需新增网络层）。
- **新增测试**（`tests/unit/agents/test_skill_binary_import.py`）：
  bytes 版 `SKILL.md` + 二进制附件往返、非 UTF-8 `SKILL.md` 拒绝、`_files_to_tree`
  保留 bytes、`_create_files_from_tree` 原样写盘。
- **变异验证**：`store.py` 不写 bytes → 1 条失败；`SKILL.md` 不解码 → 2 条失败。

## 2. 建议下一批（需适配，按性价比排序）

### 2.1 `#8574` Shell 内存保护（`4f0976d9c`）— 中高价值

- 上游新增 `utils/shell_resources.py`（242 行）：`ShellGuard` 用 `psutil` 监控一条
  命令的进程树总内存，超 `QWENPAW_SHELL_MEMORY_LIMIT_MB` 杀树；`auto` 取可用内存的
  一个比例；`0` 关闭。另有输出上限 1MB。
- 本地价值：我们的 shell 是**无约束**的（沙箱关闭），一条 `pandas.read_csv` 或
  `zip` 炸弹就能吃掉宿主机内存；50 人并发下是真实风险。
- 适配点：上游把 guard 接在 sandbox 后端；我们沙箱关闭，需要接到 `shell.py` 的
  执行路径（或只在 `sandbox_enabled` 时启用）。`psutil` 本地已有依赖。
- 风险：监控线程/采样频率对短命令的开销；`auto` 比例要按我们 1.5TB 机器调。
- 建议：**单独一批**，默认 `0`（关闭），先在企业网关上验证再开。

### 2.2 `#8235` `edit_file` 保留 CRLF（`68605611e`）— 中高价值

- 上游在 `tools/utils.py` 新增约 500 行的换行符保持逻辑（`read_file_native`、
  `replace_text_preserving_newlines` 等），`file_io.edit_file` 改用它。
- 本地价值：警务内网大量 Windows 文件（CRLF）。现在的 `edit_file` 读文本后整体
  重写，会把 CRLF 改成 LF，**git diff 全文件变更、后续工具按行处理出错**。
- 适配点：逻辑自包含在 `tools/utils.py`，但代码量大、边界多（混合换行、只读区域、
  缩进）。建议**原样移植上游实现 + 上游测试**，不要自己重写。
- 风险：500 行新代码；必须用上游的 209 行测试 + 本地补 Windows 样例。
- 建议：单独一批，优先级仅次于 shell 内存。

### 2.3 `#8034` 每请求内联媒体预算（`42117d43c`）— 高价值，改动大

- 上游把 `capping_formatter.py` 从 ~300 行扩到 1022 行：除了**单文件**上限，再加
  **单请求累计预算**（`max_total_bytes`）、请求内媒体去重、超预算时丢弃较旧媒体；
  用 `ContextVar` 做请求级隔离，并两遍格式化（先测后裁）。
- 本地现状：我们已有单文件上限（`MAX_INLINE_MEDIA_BYTES=20MB`），但**没有请求级
  预算**——多张 15MB 图片仍可拼出 100MB+ 请求体，导致连接被 provider 断开。
- 适配点：我们的 formatter 没有 `format()` 覆写、没有去重基础设施；直接搬 721 行
  风险高。建议**只实现"每请求累计预算"最小版**：在 `_maybe_cap` 里累加、在
  `format()` 入口重置（ContextVar），不做两遍测量/去重。
- 风险：预算太小会误删用户刚上传的图片；需要按"保留最新"策略并写清楚。
- 建议：单独一批，先做最小版 + 压测。

### 2.4 `#8395` 请求体过大恢复（`aa669eedc`）— 中价值

- 上游新增 `is_request_body_too_large()`（413 / "request entity too large" 等），
  在 `model_error_policy` 里归类为 `request_body_overflow`，然后由 `react_agent`
  在重试时剥离历史媒体。
- 本地：**没有 `model_error_policy.py`**；但有 `error_utils.py`。可把分类函数加进
  `error_utils.py`，并在本地重试/降级路径里加"剥离历史媒体后重试一次"。
- 风险：不能把"token 超限"误判成"body 过大"（上游注释专门强调了这点）；需要测试。
- 建议：与 2.3 一起做（同一类问题），或作为 2.3 的兜底。

### 2.5 `#8435/#8468` LLM 启动静默挂起（`74b3c9b98`）— 中价值

- 上游在 `retry_chat_model` 里给"流式启动"加超时（`_call_inner`），避免
  `await model(...)` 永久挂起而没有任何日志/错误。
- 本地：`retry_chat_model.py` 有 `_pending_stream_cleanup_tasks`，但**没有**
  `_cancel_model_call` / `_call_inner`；需要按本地结构实现"启动超时 + 取消 + 日志"。
- 风险：与我们的"首内容超时/空闲超时"叠加，要保证预算口径一致（上游用
  `first_content_budget` 扣除排队时间）。
- 建议：单独小批，先写复现（mock 一个永不返回的 `_inner`）。

### 2.6 `#8571` Scroll token 估算与溢出恢复（`86f8ee857`）— 中价值

- 上游在 scroll manager 里记录"provider 实际拒绝时的估算偏差"，把 margin 带入后续
  触发判断；并改进溢出恢复。
- 本地：`scroll/manager.py` 已有 `recover_from_context_overflow`，但结构与上游分叉
  （我们做过大量 context 改造）。需要先做符号级对比，只取"margin 记账"这一小块。
- 风险：改错会提前压缩或反复压缩；必须用长会话回归。
- 建议：先对比再定，不急着融。

### 2.7 `#8496` 慢摘要模型与输出 token 上限（`165a08806`）— 小价值/可直接融一部分

- 上游把 `max_tokens` / `max_completion_tokens` 的归一化收进
  `_normalize_output_token_kwargs`，让每次调用的摘要上限能覆盖配置默认值。
- 本地：`openai_chat_model_compat.py` 已有 `_output_token_param`，但没有归一化函数。
  这部分约 20 行，可以单独融；"慢摘要模型"的其余改动依赖上游 provider 重构，暂不跟。
- 建议：与下一个 provider 小批一起做。

## 4. 移植原则（沿用前两批）

1. **先证伪**：先在本地写一个失败用例（或符号级对比），证明问题真实存在；
2. **不按 PR 批量 cherry-pick**：只取目标函数/常量，避免把上游 2.3 的依赖带进来；
3. **每项必须变异验证**：回退修复 → 用例精确失败；
4. **全量回归零新增失败**；
5. **依赖新模块的项**（`model_error_policy`、`shell_resources`、`overflow_recovery`）
   要么整模块移植并补测试，要么不融——不要"半套"。
