## 1. 论证方法（后续每批都按这个走）

### S1 先在本地复现，而不是相信描述

上游的 commit message 描述的是"上游当时的现象"。同一个描述在本地可能：
- 已经完全修过（假阳性）；
- 被本地其他机制挡住（不可达）；
- 只在特定版本/配置下成立（条件可达）；
- 依然可达（真阳性）。

**没有复现证据的项不许进入移植队列。** 复现形式可以是：一个失败的单元测试、一段可执行的
decisive 脚本（如 §2.1）、或日志/抓包证据。

### S2 读 diff 确认"改动与根因对应"

判断标准：**把上游新增的判据/分支去掉，bug 是否会回来？** 如果去掉后 bug 依旧被别的东西挡住，
说明这项改动不是必需的。PS：要看完整 diff，不看 commit message 的摘要。

### S3 分析上游修复自身的风险

每个补丁都可能是新 bug 的来源。必查：
- 新增分支/提前返回是否漏掉了资源释放、事件通知；
- 是否改变了失败路径的语义（把异常吞掉、把错误换成成功）；
- 是否依赖特定版本的行为（例如 AgentScope 的生成器实现、前端的渲染约定）；
- 并发/重入下是否仍成立（锁、幂等、顺序）；
- 性能与阻塞（尤其在事件循环上）。

### S4 本地适配性

- 依赖版本是否一致（我们 `agentscope==2.0.4.post1`，上游已到 2.0.10）；
- 本地是否改过同一函数（冲突与语义漂移）；
- 调用点是否不止上游改的那一处（非全部移植 = 假修复）；
- 前端/数据库/部署差异（我们是 PostgreSQL、host 网络、自研控制台）。

### S5 移植后验证

1. 定向测试：复现用例从"失败"变"通过"；
2. 边界测试：上游没覆盖的分支（如 dict 输出、绝对路径名）；
3. **变异验证**：把修复回退，定向测试必须精确失败（否则测的不是修复）；
4. 全量回归：`tests/unit` 与基线逐项比对失败集合，零新增。

### S6 副作用与回滚

- 行为变化是否对用户可见（历史内容变短、临时目录改名等）；
- 能否用配置/开关回退；
- 出问题时如何定位（日志里有没有可读线索）。

## 2. 逐项论证

### 2.1 #8065 技能名路径注入

**上游主张**：`skill_name` 参与 staging 路径拼接，可被注入逃出目标目录。

**上游改动**（`0547cacf`，稳定线内）：
1. `import_skill_dir`：`target_dir = target_root / skill_name` → `safe_skill_dir(target_root, skill_name)`；
2. `import_skill_dir` 的临时目录：前缀改成固定字符串，`stage_dir` 用 `safe_skill_dir`；
3. `staged_skill_dir`：前缀固定 + `yield safe_skill_dir(temp_root, skill_name)`。

**本地复现（已实测）**：

```
zip 内解析出的技能: [('evil', '../PROOF_ESCAPE_DIR')]
import_skill_dir 返回: True
技能根目录内: []
写到根目录外: True ['PROOF_ESCAPED.txt', 'SKILL.md']
```

复现路径：`extract_zip_skills` → `_resolve_skill_name`（只 `.strip()`，**不校验**）→
`import_skill_dir(skill_dir, skill_root, "../PROOF_ESCAPE_DIR")` → `target_root / name`
（`pathlib` 对 `..` 不丢弃左侧）→ `copy_skill_dir` 写到根目录之外。

**可达性分析（与上游描述不完全一致）**：

| 路径 | 本地是否可达 | 证据 |
| --- | --- | --- |
| `import_skill_dir`（zip 导入 / 池导入） | **可达** | `_resolve_skill_name` 取自 zip 内 `SKILL.md` frontmatter，纯 `strip()`；`workspace_service.py:518`、`pool_service.py:320` 直接传入 |
| `staged_skill_dir`（10 个调用点） | **不可达** | 每个调用点之前都调用了 `normalize_skill_dir_name()` 或 `safe_skill_dir()`，顺序在 staged 之前：`workspace_service.py:158/299/384-385`、`pool_service.py:173/555/626-631/693-694/800-801/988`、`registry.py:342` |

`normalize_skill_dir_name` 会拒绝空名、`.`/`..`、`/`、`\`、控制字符（`store.py:636-657`），
`safe_skill_dir` 再做 `resolve + is_relative_to`（`store.py:658-673`）。所以
**staged 那一半是防御性加固，不是当前可用的攻击面**。

**影响评估**：逃逸后是"以 root 创建目录并写入文件"。`import_skill_dir` 在目标已存在时返回
False，所以不能直接覆盖已有目录；但可以：
- 在另一个账号的 workspace 里**种下一个技能目录**（后续该账号若启用，扫描器默认 `warn`，
  不阻止）；
- 在 `/app/working.secret` 等目录下创建新子目录与文件；
- 创建任意目录（磁盘 / pids 消耗）。
**是跨租户写入/完整性风险，不是直接读取**——因此定为 **P1**，上一轮标的 P0 过重。

**上游修复是否治根**：是。两处都用了本地已有的 `safe_skill_dir`，语义一致。
一个小缺口：`_resolve_skill_name` 仍然不校验，意味着**其他未来调用方**仍可能拿到恶意名。
建议移植时顺手在 `_resolve_skill_name` 里调用 `normalize_skill_dir_name`（更早失败、错误信息更清楚），
但这会改变"frontmatter 里有非法名时的返回方式"（从"能导入"变成"导入失败"），
需要确认产品语义（宁可拒绝，不要静默改文件名）。

**上游修复自身风险**：低。
- `safe_skill_dir` 返回的是 `resolve()` 后的路径；后续 `copytree`/`rmtree` 语义不变；
- `import_skill_dir` 里 `target_dir.exists()` 的判断对象从"未解析路径"变成"解析后路径"，
  在正常名字下两者相同；
- 临时目录前缀改成固定字符串，只影响调试时看到的目录名。

**本地适配**：`safe_skill_dir` 已存在且实现相同（甚至更严：额外做了 `is_relative_to`），
可以直接用，不需要引入上游任何新依赖。

**验收测试**：
1. zip frontmatter `name: ../x`、`/abs/x`、`a/b` → 导入必须失败，且根目录外无新文件（复现用例）；
2. 正常名（含中文、空格）→ 仍能导入；
3. 变异验证：把 `safe_skill_dir` 回退成 `target_root / name` → 用例 1 必须失败。

**结论**：**采纳（P1）**。同时建议加 `_resolve_skill_name` 的早期校验（单独评审）。

### 2.2 #8007 task_tracker / 删除会话时停 run

**上游主张**：run 在 producer task 创建前就注册，若创建失败会永久留下"running"；删除会话不停 run，会一直计入运行数。

**本地复现/可达性**：

| 部分 | 本地现状 | 结论 |
| --- | --- | --- |
| 注册顺序 | `task_tracker.py:438` 先 `self._runs[run_key] = run`，`:524` 再 `create_task` | 与上游修复前一致 |
| 删除会话 | `chats/api.py:1046-1047`（单删）、`:699-700`（批删）都没有 `request_stop` | 与上游修复前一致 |

但**注册顺序这一半，上游自己在补丁注释里写明"实际不可达"**：

> "This is defensive hardening: the window is synchronous and a running loop cannot be closed, so the failure is not reachable in practice."

也就是说，这项的价值主要是代码卫生；把它当"修 bug"会高估收益。

**删除不停 run 的影响（本地可达）**：
- 被删会话的推理继续跑，**继续消耗模型 token**；
- producer 可能继续写该会话的 session/replay，留下孤儿文件；
- `running_count` 在它结束前一直包含它（不是"永久"，但与界面显示不一致）。

**上游修复是否治根**：删除部分治根（先 stop 再删）；注册部分是加固。
`request_stop` 在本地是幂等的：run 不存在或已完成时返回 False（`task_tracker.py:391-396`），
所以对空闲会话调用它不会报错。

**上游修复自身风险**：
- `request_stop` 会 `await task`（`task_tracker.py:404-407`），即等待停止流程完成；
  如果停止流程卡住，`delete_chat` 会被拖住。上游同样如此。本地的停止流程有超时/取消处理，
  但需要在移植后验证"删除一个正在长工具调用的会话"的耗时上限。
- 顺序是 stop → 删除 spec → 删 checkpoint，与本地一致；stop 写的状态随后会被 checkpoint 删除覆盖。

**本地适配**：`delete_chat` 与 `batch_delete_chats` 都有 `workspace` 参数，可直接调用
`workspace.task_tracker.request_stop(chat_id)`。批删要循环（逐聊天容错，避免一个异常中断整批——
对应我们反复强调的"清理循环逐个容错"）。

**验收测试**：
1. 启动一个 run（mock 的长时间 producer）→ 删除会话 → run 被取消、`running_count` 回落、
   不再写入该会话文件；
2. 删除空闲会话 → 正常返回（`request_stop` 返回 False 不报错）；
3. 批删中一个会话的 stop 抛错 → 其余会话仍被删除（逐个容错）；
4. 变异验证：去掉 `request_stop` → 用例 1 必须失败。

**结论**：**采纳删除部分**；注册顺序作为低优先级加固，可与其它改动一起做，不单独立项。

### 2.3 #8212 GeneratorExit 时结束工具流

**上游主张**：工具流在 interrupted yield 处被 `close()` 时，AgentScope 会在 `finally` 里
再 `yield`，触发 `RuntimeError: async generator ignored GeneratorExit`。

**根因在本地是否成立（关键验证）**：本地安装的是 `agentscope==2.0.4.post1`，其
`tool/_toolkit.py:225` 的 `call_tool` 末尾是：

```python
finally:
    # Finally, yield the complete tool response
    yield tool_response
```

也就是说，**在 interrupted chunk 的 yield 处关闭生成器，GeneratorExit 会进入这个 finally，
而 finally 里又 yield → 必然 RuntimeError**。根因在本地成立，且与上游版本无关（2.0.4 就有）。

**本地代码的旧写法（三处，均已核对）**：

| 文件 | 行为 |
| --- | --- |
| `agents/tools/run_tool_batch.py:633-637` | 收到 INTERRUPTED 后 `break`，`:648` 在 finally 里 `await tool_stream.aclose()` |
| `tool_calls/_coordinator.py` | 多处 `await entry.stream.close()`（`:651/:667/:692/:727/:741`），在 terminal 时提前关闭 |
| `runtime/runtime.py:176` | `except (asyncio.CancelledError, KeyboardInterrupt)`，无 `GeneratorExit` 分支 |

**上游修复是否治根**：是。思路是"不再在 yield 处 close，而是把生成器 drain 到 EOF"，
让 AgentScope 的 `finally: yield` 在正常迭代中完成。对 2.0.4 而言，INTERRUPTED 之后
生成器只剩 finally 的一次 yield，**drain 是有界的**，不会无限等待。

**上游修复自身风险**：
1. **drain 时长**：如果某个工具的异步生成器在取消后仍持续产出，drain 会一直消费。
   本地需要在 coordinator 的流循环上加一个"终止后最多再读 N 个 chunk / T 秒"的保险。
   上游没有加，这是移植时要补的（属于"上游修复自身的缺口"）。
2. **`runtime.py` 的 `except GeneratorExit`**：上游在里面 `await self._try_save_on_cancel(ctx)`。
   本地 `_try_save_on_cancel` 需要确认：内部是否有 IO、是否有超时、是否可能再 yield。
   在 GeneratorExit 上下文中**允许 await，不允许 yield**；如果内部有 yield，会变成新的 RuntimeError。
3. **只改一处不够**：上游只改了 `_coordinator` 的一个函数，本地 coordinator 有 5 处 close，
   必须逐处判断哪些在"terminal/中断"路径上。

**本地适配**：结构一致，但 close 点更多；需要在 coordinator 增加一个统一的
`_drain_after_terminal(stream, max_chunks, timeout)` 辅助函数，避免逐处复制。

**验收测试**：
1. 直接用一个会 `finally: yield` 的假工具生成器，在 interrupted chunk 处 close → 修复前抛
   RuntimeError，修复后正常结束（这可以做成不依赖 AgentScope 的单元测试）；
2. 集成：模拟客户端断开（关 SSE）时正在跑工具 → 无 RuntimeError、无"stuck"事件；
3. drain 保险：假工具在中断后持续产出 1000 个 chunk → 必须在 N 个/超时后停止；
4. 变异验证：把 drain 改回 close → 用例 1 失败。

**结论**：**先写复现测试，再采纳**。复现不依赖上游，用假生成器即可，成本低、证据硬。

### 2.4 #8229 服务历史时截断超大工具输出

**上游主张**：`tool_result` 里的 base64（截图、send_file）会让单次历史响应到 10MB+，
前端 30 秒超时；因此在"服务历史"时截断。

**本地是否成立**：成立。
- `app/chats/api.py` 的 `get_chat` 直接调用 `agentscope_msg_to_message(memories)`，无截断参数；
- 本地 `state.json` 实测约 4MB，其中约 1.9MB 是图片 base64（见 `docs/50并发改造方案.md` §1.2）；
- 工具输出（截图、文件）会以 base64 持久化在 `tool_result` 里。

**上游修复是否治根**：是。上游 `_cap_tool_output` 只处理 `list`（替换大 base64 block）
和 `str`（切片），`dict` 直接返回。我最初据此判断"本地存在 dict 输出、必须补"，**实测后修正**：
`ToolResultBlock.output` 被 AgentScope 限定为 `str | list`，会话历史的两个出口
（durable transcript 的 `load_session_messages` 与 live window 的 `AgentState`）
都会经过 `Msg` 校验，dict 形态在服务历史时**不可达**（构造 dict 会直接 ValidationError）。
因此 dict 分支不是必需项；移植时仍补上，作为"未来若绕过 Msg 也不失效"的纵深防御，
但测试按函数级验证，不假装它来自真实链路。

**上游修复自身风险**：
- 截断是**结构化的**（不切 JSON 字符串），不会产生非法 JSON——这一点上游做对了；
- `str` 截断到 64KB 并加标记；用户重开会话时看到的是截断后的内容。需要确认产品上可接受
  （本地有"发送文件"卡片，原文件仍在，可下载；截断的只是历史里的 base64 副本）；
- **前端兼容性已验证**：本地 `ToolCards/shared/utils.ts:134-141,170` 对"大 base64 结果"直接
  `return null`（不渲染媒体卡片）。也就是说，前端本来就不依赖大 base64 渲染；替换成文本
  block 不会造成"图片卡片消失"的回归（两者都不显示图片卡片）。
- 阈值与前端一致（64KB），不会出现"前端认为大、后端没截"的错位。

**本地适配**：直接可用；建议把阈值做成常量并与前端常量加注释互相引用，避免以后漂移。

**验收测试**：
1. 构造一条 `tool_result`：list + 2MB base64 → 服务历史返回的 JSON 大小 < 100KB，且可解析；
2. str 输出 5MB → 截断并带标记；
3. dict 输出 5MB（本地缺口）→ 同样被截断（这条是我们补的）；
4. 正常小输出 → 字节级不变（不能影响普通历史）；
5. 变异验证：把 `truncate_oversized_outputs` 默认值改回 False → 用例 1 失败。

**结论**：**改造后采纳**（补 dict；保留截断标记；加"原文件仍在"的提示）。

### 2.5 html2text → 标准库实现（许可）

**上游主张**：html2text 是 GPL，替换为标准库实现。

**本地是否成立**：成立，且是**交付许可风险**，与功能无关。
- `pyproject.toml:78` 声明 `html2text>=2024.2.26`；
- 安装元数据：`License-Expression: GPL-3.0-or-later`；
- 使用点：`agents/tools/web_search.py` 的 `_html_to_text`（`web_fetch` 用它把网页转文本给模型）。

**上游修复是否治根**：是。上游新增 `_html_to_markdown.py`（约 247 行，`html.parser` 实现），
覆盖：标题、段落/列表/表格/引用/`pre`、加粗/斜体/删除线/行内代码、链接；丢弃 script/style/
title/iframe 与图片。本地用法只需要 `ignore_links=False`、`ignore_images=True`、`body_width=0`，
覆盖面够用。

**上游修复自身风险**：
- **输出质量差异**：表格、嵌套列表、`<pre>` 空白、HTML 实体、畸形标签的处理与 html2text 不同，
  而这段文本直接进模型上下文；差异会影响"网页总结"的质量。
- 需要 golden 对比：用 20 个真实页面（新闻/表格/文档/中文）对比新旧输出，人工抽检。
- 上游实现是纯 stdlib，无新依赖、无网络行为，安全面反而更小。

**本地适配**：直接替换 `_html_to_text` 内部实现即可；`web_fetch` 其余逻辑不变。
注意本地是内网离线部署，`web_fetch` 实际很少用（甚至可能被账号权限关闭），
所以**功能风险低、许可收益明确**。

**验收测试**：
1. 20 个页面的 golden 对比（人工确认可读性不下降）；
2. 恶意/畸形 HTML（未闭合标签、超长属性、实体炸弹）不崩溃、不无限循环；
3. 表格与代码块保留结构（这两类对模型最有用）；
4. 移除依赖后 `pip check` 无残留、镜像构建通过。

**结论**：**采纳**（许可驱动），配 golden 对比与畸形输入测试。

### 2.6 #8370 emSign CA 信任整改

**上游主张**：依赖里的 certifi 仍信任 emSign CA；安装插件时把 `certifi>=2026.10.19` 拉进来，
并校验 pip/uv 版本。

**本地是否成立**：部分成立。
- 本地插件安装确实会跑 `pip install`（`plugins/loader.py:471` → `_install_requirements`），
  入口是 admin-only（`routers/plugins.py:676`）；
- 但生产是**内网离线**：pip 没有索引，插件带 requirements 的安装本来就会失败，
  因此"拉入不安全 CA"的实际暴露面很小；
- 开发机/构建机联网时才有意义。

**上游修复是否治根**：是（把 certifi 升到移除该 CA 的版本）。但对我们：
- `require_pip/require_uv` 的版本下限检查依赖本地安装器版本，可能在离线环境误报（需要确认
  `pip --version` 解析在受限环境下的行为）；
- 强制 `certifi>=2026.10.19` 会改变插件安装的依赖集合，可能与离线镜像里的版本冲突。

**结论**：**只取 certifi 下限**（在插件安装命令里加 `certifi>=2026.10.19`），
`require_pip/require_uv` 的版本检查**暂不移植**（离线场景收益低、误报风险高）。
