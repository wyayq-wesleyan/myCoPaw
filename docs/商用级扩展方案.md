> 目标：把当前「单机单进程、文件落本地盘、图谱寄生在 LightRAG 表里」的可用形态，
> 推进到可交付给客户的商用形态——**能扩容、能故障切换、能备份恢复、能观测、能解释**。
>
> 本文的定位是**决策文档**，不是实施清单。每一节都给出「结论 + 理由 + 被否决的选项 +
> 前置条件」，便于逐节评审。文中所有"现状"均标注了可核查的位置；所有"假设"都显式
> 写出，未测的数字一律标 `【待实测】`，不用推算值冒充实测值。

## 0. 先纠正一个前提（这一条会影响整个图谱选型）

你的描述里有一条需要更正：**「PG19 带图数据库功能」目前不成立。**

核实来源（2026-10-19）：

- PostgreSQL 官方文档站显示 **PostgreSQL 19 处于 RC 1（2026-10-15 发布）**，
  最终发布日期仍为 `2026-??-??`，其文档页明确标注 *"This documentation is for an
  unsupported version"*（开发版本）。
- PostgreSQL 19 的官方 release notes 里**没有**出现 `SQL/PGQ`、`property graph`、
  `CREATE PROPERTY GRAPH`、`GRAPH_TABLE` 中的任何一个（按关键词检索为零命中）。
- 当前稳定版 **PostgreSQL 18 的 release notes 同样没有** SQL/PGQ 或属性图特性。
  18 的重点是异步 I/O、B-tree skip scan、`uuidv7()`、虚拟生成列、OAuth 认证、
  时间约束等。

结论与后果：

| 结论 | 说明 |
| --- | --- |
| **不要把 PG19 当作生产底座** | RC 版本 + 官方标注 unsupported + 扩展（pgvector / AGE / PostGIS）对新版的适配尚不可知。警务内网做等保与交付时，"生产跑 RC 数据库"本身就是一条风险项 |
| **"用 PG 做图"在今天是靠扩展，不是靠内核** | 现实可用的路线是 **Apache AGE**（在 PG 上提供 openCypher + 属性图）、或基于**递归 CTE / 闭包表**自建，或 `pgRouting` 做路径类计算。SQL/PGQ 值得跟踪，但不能作为本方案的依赖 |
| **PG17 也不该盲升** | 现在生产是 PG17 + pgvector + HNSW（已实测 15 万 chunk 从 78s/OOM 降到 P50 6ms）。升级到 18/19 的唯一合理理由是拿到明确收益，而不是版本号更新 |

> 如果你看到"PG 支持图数据库"的说法，多半指的是 **Apache AGE 扩展**、**SQL/PGQ 标准提案**
> 或某个商业发行版（如某些国产 PG 发行版自带的图能力）。这三者的成熟度、许可、可维护性
> 差别很大，需要指名核对。**请确认你当时看到的是哪一个**，这直接决定 §4 的选型。

### 2.2 商用级必须言行一致的三件事

1. **每一层都能单独扩容**：接入、应用、模型、数据库、存储各自的容量单位不同，
   不能被"一台更大的机器"掩盖。
2. **每一个单点都有替代路径**（HA）或**明确的停机窗口与恢复步骤**（可接受的单点 = 有承诺的）。
3. **每一次故障都有数字**：SLO + 错误预算 + 告警；没有数字的"稳定性"不可交付。

### 2.3 部署编排：K8s 还是继续 Compose？

| 选项 | 适用 | 代价 |
| --- | --- | --- |
| 继续 Docker Compose + 单机 | 50 人在**一台**够用；可用性目标 ≤ 99% 且写入交付文档 | 无 HA、滚动升级=停机、节点故障=整体停 |
| Compose + 多机 + keepalived/VIP | 3-5 台、不想引入 K8s 复杂度 | 状态化组件（PG/MinIO）仍需手工编排；升级麻烦 |
| **K8s（推荐 3 节点起步）** | 要 HA、滚动升级、自动重启、HPA、多副本 | 运维门槛、需要 CI/CD 与镜像仓库、内网要先建好 |

**推荐**：如果目标是"商用、可交付、能扩容"，就上 K8s（3 节点起步，控制面也可复用现有机器）。
但**排期上放在后面**（§7 阶段 P5）——先把应用做成无状态、把存储解耦，否则上了 K8s 只是把
同一个单进程应用换个壳。

**明确不做**：多地域/多集群、服务网格（Istio）、微服务拆分。50 人规模上这些只增加故障面。

## 3. 对象存储：MinIO

### 3.1 为什么必须做（当前绑定点，逐个列出）

| # | 绑定点 | 位置 | 后果 |
| --- | --- | --- | --- |
| 1 | 知识文档落本地盘：`settings.files_dir / space_id / "{document_id}-{filename}"` 流式写 | `knowledge-service/app/main.py:247-262` | 单机容量上限、无法水平扩容、实例迁移要搬盘 |
| 2 | 文档路径以**绝对路径**入库（`documents.path`） | `store.create_document(... str(target_path))` | 换了节点/目录，历史记录全部指向不存在的文件 |
| 3 | 下载/预览直接 `FileResponse(path=document["path"])` | `main.py:417` | 文件必须与 API 进程同机可见 |
| 4 | 删除用 `os.path.exists` + `os.remove` | `store.py:740-746` | 删除与元数据不在同一事务域，易出现"有行无文件/有文件无行" |
| 5 | 解析/转换需要本地文件（MinerU、`soffice`） | `parsers.py`、`main.py:365` | 解析强依赖本地盘权限与空间 |
| 6 | 主应用工作区（生成的图表/文档、会话目录、技能、代码工程）也是本地 bind mount | `deploy/docker-compose.code-mount.*.yml` | 同上；且与"每账号隔离"的路径校验耦合 |
| 7 | 备份是 zip 打包 | `app/routers/backup.py` | 大库时打包/恢复耗时不可控 |

### 3.2 选型与许可（商用必须先过这一关）

| 候选 | 许可 | HA | 适用判断 |
| --- | --- | --- | --- |
| **MinIO** | **AGPLv3** | 纠删码 + 多节点（社区版具备） | 生态与 S3 兼容性最好，运维文档最全；**AGPL 需要法务确认**：作为产品的一部分交付给客户、或对外提供服务时的源码义务 |
| Ceph RGW | LGPL | 强 | 若客户环境已有 Ceph 或要求宽松许可；运维复杂得多 |
| SeaweedFS | Apache-2.0 | 中 | 许可友好、小文件场景好；生态与运维资料少于 MinIO |
| 客户既有对象存储 | 视客户 | 强 | 若警务云已提供 S3 兼容存储，**优先用客户的**，我们只做适配 |

**结论**：
- 技术接口层面**只依赖 S3 API**，把 MinIO 当成"默认实现"而不是"架构依赖"——这样许可或
  客户环境变化时，替换的是一个适配器，不是业务代码。
- MinIO 的许可与社区版/企业版功能矩阵**落地前必须由法务与采购确认**（尤其是纠删码、
  多站点复制、密钥管理这几项在生产里会用到）。这一条我无法替你决定，标为**决策门 3**。

### 3.3 对象模型（bucket / key / 隔离 / 配额）

**bucket 划分**（按"生命周期"和"访问模式"分，不按业务分）：

| bucket | 内容 | 版本控制 | Object Lock | 生命周期 |
| --- | --- | --- | --- | --- |
| `hz-docs` | 知识空间原始上传件（不可变） | 开启 | 关闭 | 跟随文档删除 |
| `hz-artifacts` | 会话生成物：图表、DOCX、导出包 | 关闭 | 关闭 | 90 天/可配 |
| `hz-chat-uploads` | 聊天附件（解析后可丢弃原件，按需） | 关闭 | 关闭 | 30 天/可配 |
| `hz-backups` | pgBackRest 全量+WAL、配置快照 | 关闭 | **开启**（防勒索/误删） | 按保留策略 |
| `hz-audit-archive` | 审计日志归档（合规） | 关闭 | **开启**（WORM） | ≥ 等保要求年限 |

**key 布局**（对象键即寻址，必须可预测且天然隔离）：

```
hz-docs/<tenant>/<space_id>/<document_id>/<sha256前2位>/<sha256>.<ext>
        └ 账号哈希            └ 空间            └ 内容寻址（同一内容只存一份）
hz-artifacts/<tenant>/<agent_id>/<session_id>/<artifact_id>-<name>
hz-chat-uploads/<tenant>/<agent_id>/<message_id>/<filename>
```

设计要点（每条都有事故对应）：

- **内容寻址 + 去重**：键里放 sha256 → 上传天然幂等（`If-None-Match`/已存在即跳过），
  与现有 `find_document_by_hash` 去重逻辑同源；对象名不含用户可控字符串，
  **避免路径穿越**（对应本仓库两次文件名穿越事故）。
- **租户前缀用哈希**：与现有"目录名对中文账号名做哈希"的口径一致，减少信息暴露。
- **不用"每个租户一个 bucket"**：bucket 数量在对象存储里是稀缺资源，且跨租户报表/迁移会变难。
  隔离靠**前缀 + 服务端强制校验 + 每租户配额**三层。
- **配额**：MinIO 支持按 bucket/用户配额；我们还需要**按账号的应用级配额**（键前缀累计大小，
  在 `hz-docs` 与 `hz-chat-uploads` 各维护一份计数，存 PG 或 Redis），超限时上传端点返回
  明确的 413 与"已用/上限"。这是商用交付里客户一定会问的能力。

### 3.4 代码改造：引入 StoragePort 抽象

新增一个**薄端口**（不是完整 SDK 封装），只覆盖四种动作：

```python
class StoragePort(Protocol):
    async def put_stream(key: str, chunks: AsyncIterator[bytes],
                         *, content_type: str | None,
                         max_bytes: int) -> PutResult: ...      # 边写边算 sha256 与大小
    async def open_stream(self, key: str,
                          *, range: tuple[int, int] | None = None) -> AsyncIterator[bytes]: ...
    async def stat(self, key: str) -> ObjectStat | None: ...     # 不存在返回 None，不抛
    async def delete(self, key: str) -> None: ...                # 幂等
    def presign_get(self, key: str, *, expires: int = 300,
                    filename: str | None = None) -> str: ...
```

实现两份：`LocalFsStorage`（保持现有行为，便于回滚与本地开发）与 `S3Storage`（boto3）。

**关键约束（都是踩过的坑）**：

1. **boto3 是同步库**。所有调用必须走 `run_sync_io(POOL_FILE, ...)`，**不允许出现在事件循环上**
   （模式 H；本仓库已有"事件循环上写库冻结全应用"的事故）。
2. **分片读写**：下载预览不要整文件读进内存。`open_stream` 用 boto3 的 Range GET 分片，
   通过 `StreamingResponse` 直接转发；大文件（10GB 级）沿用现有流式上传路径。
3. **SHA256 边写边算**，不要写完再读一遍（当前上传已经在做，MinIO 版本保持同样语义）。
4. **写对象与写元数据的顺序**：先写对象（内容寻址，天然幂等）→ 再提交 `documents` 行。
   失败时"有孤儿对象、无行"，由 GC 清理；**绝不允许"有行、无对象"**（那是用户可见的坏数据）。
5. **删除**：先删行（事务内）→ 再删对象（异步、可重试）。删除失败进入重试队列，不阻塞用户。
6. **不许用 FUSE（s3fs/goofys）挂载给解析器**。理由：解析要随机读大文件，FUSE 的语义与
   性能会在 MinerU/`soffice` 并发时变成不可预测的挂起；而且我们刚花了很大代价把解析的
   进程树与 pids 收住，再引入 FUSE 等于把不确定性放回去。**改为"本地 scratch + LRU"**：
   worker 处理前把对象拉到 `/scratch/<document_id>`（本地 NVMe），处理完删除；
   热文档（近期被检索/预览）保留在 scratch 中按容量 LRU 淘汰。

**改造点清单**（逐个替换，不改语义）：

| 位置 | 现在 | 改后 |
| --- | --- | --- |
| `main.py:247-262` 上传 | 写 `files_dir/...` | `storage.put_stream(key, ...)` |
| `main.py:417` 下载/预览 | `FileResponse(path)` | 302 到 presigned URL（或 `StreamingResponse` 代理；见 §3.5 的取舍） |
| `store.py:740-746` 删除 | `os.remove` | `storage.delete(key)` |
| `parsers.py` 解析 | 直接读 `document["path"]` | `storage.materialize(key) -> local_path`（scratch） |
| `documents` 表 | `path TEXT`（绝对路径） | 新增 `storage_backend TEXT`、`storage_key TEXT`、`checksum TEXT`；**保留 `path` 作为兼容列**，过渡期双写 |
| 主应用生成物 | 写工作区目录 | `hz-artifacts` + 现有按账号路径校验口径不变 |
| 备份 | zip 打包到本地 | `pgBackRest` → `hz-backups`（§4.6）+ 配置快照 |

**下载路径的取舍**（要明确选一个，别两者都做半个）：

- **Presigned URL 直连**：不占用应用带宽与连接，最适合大文件。要求浏览器能直连 MinIO 端点
  （内网可达即可；等保环境下需要在反代上暴露 `minio` 的域名/端口）。
- **应用代理流式转发**：客户端只见应用域名，权限校验留在应用里，MinIO 可完全不对外。
  代价是双份带宽与连接。

**推荐**：默认**代理流式**（更符合"数据不出内网边界"的交付习惯），把 presigned 作为
可配置项；两者都实现，但同一时刻只启用一种（配置项 `STORAGE_DELIVERY=proxy|presign`）。

### 3.5 一致性、GC 与"不会删错东西"的机制

- **健康检查**：`/v1/health` 增加 `storage` 段（能否 list 一个探针对象），但**只缓存肯定结论**
  （模式 E）：失败必须每次重试，不能因为一次抖动把存储判死。
- **GC（标记-清除）**：每天一次，扫描 `documents`/`artifacts` 表中引用的 key 集合，
  与 bucket 列表求差；孤儿对象**先记录、超过 24 小时宽限再删**。逐对象 `try/except` 并计数
  （模式 G），单对象失败不中断整轮。
- **反向一致性巡检**：抽样校验"有行必有对象"（每小时 N 个随机行做 HEAD），
  发现缺失立即告警——这是**用户可见**的坏数据，必须比"孤儿对象"优先处理。
- **不变量**：`documents.storage_key` 一旦写入不得修改；内容的替换必须产生新 key（内容寻址
  天然满足）。这保证任何缓存/副本都不会读到"半新半旧"的对象。

### 3.6 HA 与容量模型

- **HA**：3 节点起，纠删码 `EC:2`（容忍 2 节点/盘故障）；**不启用多站点复制**（内网单机房
  场景没有收益，反而增加一致性复杂度）。四节点以下不要指望"集群"带来的可用性提升，
  真正防的是单盘/单进程故障。
- **容量公式**（写入交付文档，客户一定会问）：

```
可用容量 = 裸盘容量 × 节点数 × 0.75(纠删码开销) × 0.9(预留)
例：3 节点 × 4 盘 × 4TB = 48TB 裸 → 约 32TB 可用
```

- **节点/磁盘规格建议**：NVMe SSD 做数据盘（对象存储对随机读敏感，尤其 scratch 场景），
  万兆内网；`mc admin` 的 `heal` 需要预留 IO 余量。
- **`mc` 运维清单**：`mc admin info`、`mc admin heal`、配额设置、`mc ilm rule`（生命周期）、
  备份桶的版本与 Object Lock 校验，写成运维手册（对应 OPS_GUIDE 的一节）。

### 3.7 迁移方案（可回滚是硬要求）

```
阶段 1  双写：新上传同时写本地盘与 MinIO；读取仍走本地盘。
        （同时新增 storage_key 列并回填已有行，回填在后台、可中断、可重跑）
阶段 2  影子读：对 5% 请求用 MinIO 读取并与本地盘结果比对（大小 + sha256），
        差异全部记日志、不改变返回。
阶段 3  切换读：默认走 MinIO，本地盘作为 fallback（本地文件被清理时仍能服务）。
阶段 4  停双写：只写 MinIO；本地盘文件按保留期清理，但**保留目录结构一个月**。
阶段 5  下线本地盘路径：删除兼容列与 fallback（放在下一个版本，避免同版本内不可逆）。
```

每阶段都有独立的回滚动作（改一个配置项即可回退），且阶段之间**至少间隔一个版本**。
回填与巡检都要能"不启动服务也能验证"（模式 D）。

## 4. 数据库：关系/向量/图谱的落位

### 4.1 结论先行

| 结论 | 理由 |
| --- | --- |
| **继续用 PostgreSQL 17 作关系库 + 向量库** | 现有 pgvector+HNSW 已实测达标；升级到 18/19 没有可得收益，反而带回"RC 版本 + 扩展适配"风险 |
| **不依赖 PG19 的图能力** | §0 已核实：19 是 RC，且 release notes 无图特性 |
| **本体/图谱层先落在 PG（可选 Apache AGE），把接口做成可换** | 先用单一存储换"事务一致性 + 运维简单"；当实测证明多跳遍历成为瓶颈时，再引入专用图库，且只换适配器 |
| **专用图库作为"按需"的第二阶段**，不在一开始上 | 判断依据是**实测的跳数与边数**，不是感觉（见 §4.2） |

### 4.2 图/本体层的三条路线 + 决策矩阵

| 维度 | A. PG17 + 关系表（现状扩展） | B. PG17 + Apache AGE | C. 专用图库（NebulaGraph / TuGraph / Neo4j） |
| --- | --- | --- | --- |
| 查询语言 | SQL（递归 CTE） | openCypher | Cypher / nGQL / GQL |
| 事务一致性 | **单库单事务，最强** | 单库单事务 | 跨库最终一致（需自建补偿） |
| 1-2 跳遍历 | 好（有索引） | 好 | 好 |
| 3-6 跳遍历 | 差（join 深度爆炸） | 中（仍是 join 实现） | **好（原生邻接）** |
| 亿级边 | 不现实 | 勉强 | 符合设计目标 |
| 运维复杂度 | 最低 | 低（多一个扩展） | 高（独立集群、独立备份、独立监控） |
| 许可/合规 | PG 许可 | Apache-2.0 | 差异大（Neo4j 集群为企业版；国产图库在公安行业有交付先例） |
| 迁移成本 | 0 | 低 | 高（双写 + 校验 + 切读） |
| 适用判断 | **当前规模与多数查询** | **需要 Cypher 表达力、又不想拆库** | **实测到 3 跳以上高频 + 边数上亿 + 已有运维能力** |

**推荐路线（两阶段）**：

1. **现在**：走 A + 把现有 LightRAG 图谱"降级为抽取与检索的一种手段"，把**本体层**
   （entity/relation 的类型体系、约束、来源、置信度、版本）建成**我们自己的、可解释的表结构**
   （§4.3）。理由：图谱的价值在**本体治理**，不在遍历引擎；现在最缺的是后者的前十步。
2. **当实测触发阈值时**（决策门 2）：引入 C 中的**一个**专用图库，作为本体的读模型
   （CQRS 式：PG 是真相、图库是查询加速），PG→图库单向同步 + 定期全量校验。
   选型按客户环境（是否已采购、是否有运维能力、许可）定，不由我们单方面锁定。

> AGE 的位置：如果你确实需要 Cypher 的表达力（比如图分析的规则库要可配置），
> 用 AGE 是"不拆库"的最优解。但要注意 AGE 的**版本敏感**（跟 PG 大版本绑定）、
> 以及它仍是"用表实现的图"，别指望它解决深度遍历的性能问题。**决策门 2 一并定**。

### 4.3 本体层设计（这是"商用级"与"demo"的分界）

现在的图谱是 LightRAG 自动抽取的产物：有节点、边、workspace 隔离，但**没有本体治理**。
商用交付要求能回答："这个实体类型有哪些？这个关系是谁定义的？这条结论的依据是哪份文件
哪一段？改成新版本后旧结论怎么办？" 这些都需要显式设计。

建议的表结构（`ontology` schema，与 `platform`、业务表分离）：

| 表 | 关键列 | 说明 |
| --- | --- | --- |
| `ontology_types` | `id, kind(entity\|relation), name, version, status(draft\|active\|deprecated), json_schema` | 类型体系 + 版本；`status` 支持灰发与退役 |
| `ontology_constraints` | `type_id, rule(jsonb)` | 定义域/值域、唯一性、基数（如"一案件一主办人"） |
| `entities`（已有，扩展） | `+ canonical_name, aliases[], type_id, first_seen, last_seen, merged_into` | **实体消解**的外键：同一实体的多个写法合并到 canonical，`merged_into` 保留可回溯 |
| `relations`（已有，扩展） | `+ type_id, valid_from, valid_to, confidence, source_kind, source_ref, extractor_version, review_status` | **时间有效性**（业务事实会变）+ **来源血统** + 置信度 + 人工复核状态 |
| `entity_evidence` | `entity_id, relation_id, chunk_id, page, span, doc_version` | 让每一条结论都能点回原文 |
| `ontology_migrations` | `version, applied_at, description, details` | 本体变更与数据迁移成对记录（沿用本仓库"迁移可重跑、幂等"的口径） |

**必做的三个机制**：

1. **实体消解（Entity Resolution）**：不做的直接后果是同一人/同一案在库里变成 5 个节点，
   图分析结论全错。第一版可以是"规则 + 相似度 + 人工确认队列"，但**必须有人工确认入口**
   与 `merged_into` 的可回退记录（对应模式 A：合并标记必须可回滚）。
2. **来源血统（Provenance）**：任何写入图谱的结论都必须带 `chunk_id` + 文档版本。
   否则一旦文档更新，图谱里就是无主事实——这在审计场景是硬伤。
3. **抽取器版本（`extractor_version`）**：模型/提示词升级后，可以按版本重跑并对比，
   而不是"悄悄变好了/变坏了"。这也让 §4.4 的混合检索可以按版本权重调优。

### 4.4 检索路径（50+ 并发下的实现）

现有多路融合（全文 / 文件名 / 关键词 / 语义 / 实体 + 图谱配额）保持不变，改造点：

| 改造 | 理由 |
| --- | --- |
| 图谱查询**设独立超时与配额**，超时降级为"仅向量+全文" | 图库/AGE 的慢查询不得拖垮整次检索（模式 H 的查询侧版本） |
| 语义检索走**只读副本**（若引入） | 检索是读密集；与写入/事务隔离 |
| 检索结果**缓存**（Redis，键 = 查询指纹 + 路径集合 + 索引版本） | 50 人里重复问题很多（制度类问答），TTL 短（60-300s）即可挡掉大部分重复计算 |
| 缓存键包含**索引版本** | 文档增删后必须失效；用版本号而不是逐条失效，避免漏删（模式 A） |
| 图谱结果标注**置信度与来源** | 前端能展示"依据哪份材料"，这是警务场景的刚需 |

### 4.5 连接管理：PgBouncer 与池预算

现状（`docs/50并发改造方案.md` §1.3）：各池合计 ≈126 连接 / `max_connections=200`。
一旦应用多副本、知识 worker 多副本，这个数字会**乘上副本数**。

**改造**：

1. **引入 PgBouncer（transaction 模式）**作为唯一入口：应用与知识服务连 PgBouncer，
   服务端连接数由 PgBouncer 统一管理（如 `default_pool_size=40`、`max_client_conn=1000`）。
2. **重算池预算**（交付文档的一部分）：

| 组件 | 副本数 | 应用侧池/副本 | PgBouncer 服务端连接 |
| --- | --- | --- | --- |
| 主应用（平台库 + 元数据 + 目标池） | 3 | 8 + 10 + 32 = 50 | 由 PgBouncer 复用，峰值 ~40 |
| 知识服务 api | 2 | 30 | 复用同一池 |
| 知识服务 worker | 4 | 30 | 复用同一池 |
| 图谱池（AGE/LightRAG） | — | 8 | 复用 |
| `max_connections` | — | — | 建议 400（含 20 条管理预留） |

> ⚠️ **transaction 模式的语义陷阱**（模式 C）：应用**不能**依赖会话级状态
> （`SET search_path`、会话级临时表、advisory lock 的会话锁、prepared statement 名）。
> 本仓库现在**大量使用 `search_path` 与 schema 级隔离**，还用了会话级 advisory lock
> （知识 worker 的实例锁）。因此：
> - 要么用 **session 模式**（牺牲复用率），
> - 要么把 `search_path` 改成**显式全限定表名**（更彻底，但要先审计），
> - advisory lock 改用**带 key 的事务级锁**（`pg_try_advisory_xact_lock`）。
>
> 这一条**必须在 PgBouncer 落地前完成审计**，否则会出现"偶发的、无法复现的跨租户查询"。

3. **目标池（`_MAX_LIVE_POOLS=16` × maxconn 2）**是当前最容易失控的部分：即使有 PgBouncer，
   应用侧仍会持有最多 32 条连接。**LRU 回收已经实现**（`data_tables/connection.py:115`
   按最久未用关闭空闲池），所以这里要做的是：把"当前存活池数/连接数"暴露成指标（现在只能
   从进程内看），并对单账号的并行查询设上限（语句级 30s 超时保留）。

### 4.6 HA、备份与版本升级

| 项 | 方案 | 目标 |
| --- | --- | --- |
| 主库高可用 | Patroni + etcd（或 pg_auto_failover），1 主 1 同步备 + 1 异步备 | 主故障自动切换 ≤ 30s，应用侧用 PgBouncer/连接串多主机 |
| 只读副本 | 1 个流复制只读副本 | 承担检索、报表、`pg_dump`，避免影响在线事务 |
| 备份 | **pgBackRest**：全量每周 + 增量每日 + **WAL 连续归档到 MinIO** | RPO ≤ 5 分钟、RTO ≤ 30 分钟；季度演练恢复 |
| 备份加密 | pgBackRest `repo-cipher` + MinIO SSE-KMS | 备份与在线数据同等级保护 |
| 版本升级 | PG17 → 18/19：先在小规模环境跑 pg_upgrade + 扩展兼容验证 + 压测 | 只在有明确收益时升级；**不追 RC** |
| 大表治理 | 会话历史/审计按时间分区 + 归档到 MinIO（Parquet/JSONL） | 保证在线表规模可控（这是长期稳定性的关键） |

## 5. 50+ 并发的性能与稳定性保证

### 5.1 容量模型（先立假设，再算，再实测校正）

**假设**（需要你用现网数据替换，替换后结论会变）：

| 变量 | 假设值 | 说明 |
| --- | --- | --- |
| 在线用户 | 50（目标 75 峰值） | |
| 同时在生成回答的比例 | 20–30% → 10–15 路 | 真实分布取决于使用习惯 |
| 单路输出速度 | 20–40 token/s | 取决于模型与硬件 |
| 单轮输入上下文 | 8k–32k token | 长文档/多轮会更高 |
| 每日对话量 | 50 人 × 20 轮 = 1000 轮 | |
| 知识语料 | 100 万 chunk/年量级 | 现在 15 万 |
| 文档上传 | 50 人 × 5 份/天，均 5MB | |

**由此得出的三个"硬瓶颈"**：

1. **模型推理是第一位的外部瓶颈**。
   `10–15 路 × 30 token/s ≈ 300–450 token/s` 是稳态；若 50 人同时提问（早高峰），
   需要 `50 × 30 = 1500 token/s`。而当前 `QWENPAW_LLM_MAX_CONCURRENT=6` 是**进程内信号量**，
   说明现有设计默认"模型服务只有 6 路容量"。
   → **必须先测出模型服务的真实吞吐（token/s）与并发曲线**，再决定：加卡、加副本、
   还是引入排队与降级（短回答模式）。这是**决策门 1**。
2. **数据库操作速率**。当前 2.5s/3s 轮询在 50 人下产生 ~840 操作/秒的**空转**。
   → 改成 SSE/长轮询 + 缓存 + 批量后，目标稳态 **< 200 操作/秒**。
3. **checkpoint 写盘**。`4MB × 25/秒 = 100MB/s` 的持续写入在任何单机上都是灾难。
   → 必须外置（大对象进 MinIO，状态行进 PG，30s 或轮次结束才落盘）。

### 5.2 多副本前必须消灭的"全局串行点"

**这是本方案最容易被忽略、也最容易翻车的部分**：把单进程应用复制成 3 份，会让下面这些
"进程内唯一"的东西变成 3 份，行为从"排队"变成"超发"：

| 机制 | 现状 | 多副本后果 | 改法 |
| --- | --- | --- | --- |
| LLM 并发上限 | 进程内 `asyncio.Semaphore`（`providers/rate_limiter.py`） | 3 副本 = 18 并发，模型服务被压垮 | **全局令牌桶（Redis）+ 模型网关排队** |
| 限流器 | 进程内计数 | 实际配额 ×N | Redis 计数（已有定期剪枝逻辑，迁移时保留） |
| 会话/checkpoint | 进程内字典 + 本地文件 | 刷新后落到别的副本 → 丢上下文 | checkpoint 外置（PG + MinIO），副本无状态 |
| SSE 流 | 单进程持有连接 | 重连可能落到别的副本 → 接不上 | 事件写入 Redis Stream，任意副本可续播 |
| 后台任务/定时器 | 每副本各跑一次 | 重复执行（重复清理、重复重试） | leader 选举（Redis/etcd）或改由 worker 承担 |
| 知识 worker 实例锁 | 会话级 advisory lock（已实现） | 已正确；但 PgBouncer transaction 模式下锁语义会变 | 改事务级锁（§4.5） |
| 进程内缓存 | 配置、模型清单、技能扫描结果 | 各副本不一致，出现"时好时坏" | 明确哪些缓存可以不一致（多数可以），哪些必须共享 |

> 判据：**任何"限制"或"选举"如果只存在于进程内，多副本化时都会失效。**
> 上线多副本前，逐个过一遍这张表并给出结论（共享 or 明确接受不一致）。

### 5.3 无状态化与 SSE 跨副本续播

目标：任意副本都能服务任意用户的任意会话。

1. **会话状态**：checkpoint 从"本地 4MB 文件"改为
   `PG 状态行（小、频繁）+ MinIO 大对象（图片/工具结果，只在变更时上传）`。
2. **SSE 续播**：推理事件按 `(session_id, turn_id, seq)` 写入 Redis Stream（带 TTL），
   客户端重连带 `Last-Event-ID`，由任意副本从 Stream 补发。
3. **会话亲和**：**不依赖**粘性会话。粘性是"看起来能用"的临时方案，一旦 LB 抖动或副本重启
   就会出现"回答串到别的会话"这类难以复现的问题。

### 5.4 任务队列与 worker 扩容

现有 DB 行锁抢占 + owner 心跳 + 启动回收（5.5 已完成）**已经是可扩展的正确形态**。
要做的是：

- worker 副本数按 CPU 与解析并发定（每副本 `KNOWLEDGE_PARSE_CONCURRENCY=2`，
  4 副本 = 8 路解析；注意每个副本的**内存上限**要能装下 MinerU）；
- 队列深度与**等待时间**作为一等指标（前端显示"前面还有 N 个"），而不是让用户猜；
- 毒文档治理：重试上限 + 失败原因 + 一键重投（已有 attempts 上限修复，保留）；
- 是否引入 Redis/Celery：**暂不**。DB 行锁在 50 人规模完全够用，引入消息队列只是增加
  一个必须 HA 的组件。等"解析洪峰压垮 API 进程"实测出现再说。

### 5.5 降级与背压矩阵（客户最关心的"坏了会怎样"）

| 故障 | 用户可见行为 | 系统行为 | 恢复 |
| --- | --- | --- | --- |
| 模型服务变慢/排队 | 显示"排队中，前面 N 位"，可取消 | 全局令牌桶 + 队列上限；超限直接拒绝并提示 | 队列自然消化；不降级为静默超时 |
| 模型服务不可用 | 明确错误 + 重试按钮 | 熔断（连续失败 N 次打开），后台探测恢复 | 熔断半开探测 |
| 向量/图谱查询超时 | 回答仍生成，标注"未使用知识库证据" | 检索侧独立超时，逐路降级（图谱→向量→全文） | 自动 |
| PostgreSQL 主库故障 | 短时 5xx（≤30s） | Patroni 自动切换；应用重连 | 30s 内恢复 |
| MinIO 故障 | 新上传失败（明确报错）；已缓存文档仍可读 | 读走本地 scratch 缓存；写快速失败不排队 | 恢复后上传重试 |
| 知识 worker 全挂 | 上传成功但"排队中" | 心跳超时后其他副本接管（已有机制） | 重启副本 |
| 队列积压 | 显示预计等待 | 自动扩 worker（K8s HPA 或人工） | 消化后缩容 |
| 磁盘将满 | 管理端红色告警 | 拒绝新上传（明确提示），触发 GC | 扩容/清理 |

**原则**：任何降级都必须**在界面上说清楚发生了什么**，不允许变成"没反应"或"转圈到超时"。

### 5.6 SLO 与观测

| 指标 | 目标（50 人规模） |
| --- | --- |
| 控制台/API 可用性 | ≥ 99.9%（月） |
| 非 LLM 接口 P95 / P99 | ≤ 300ms / ≤ 1s |
| 首 token P95 / P99 | ≤ 5s / ≤ 12s（模型相关，需实测校准） |
| 检索 P95 | ≤ 1.5s |
| 上传接收 P95 | ≤ 2s（不含解析） |
| 解析完成（≤20MB PDF） | 90 分位 ≤ 5 分钟 |
| RPO / RTO | ≤ 5 分钟 / ≤ 30 分钟 |

**必须有的指标**（否则无法定位"慢在哪"）：

- 应用：请求速率/延迟/错误率（按端点）、SSE 连接数与续播次数、线程池各池 active/waiting/拒绝数（已有 `/api/debug/io-pools`）、事件循环延迟（`loop lag`，**必须暴露**）。
- LLM：排队长度与等待时间、token/s、首 token 延迟、上游错误率。
- DB：PgBouncer 池使用率与等待、慢查询 TOP N、锁等待、复制延迟、checkpoint/autovacuum 影响。
- 存储：MinIO 请求延迟、错误率、容量水位、heal 状态。
- 队列：各状态任务数、最老任务年龄、失败率、重试次数。
- 业务：每日活跃、轮次、知识命中率、图证据命中率。

**告警**（有阈值 + 有处理手册，避免"狼来了"）：主库切换、复制延迟 > 30s、池等待 > 1s、
loop lag > 200ms、队列最老任务 > 30min、磁盘 > 85%、备份失败、MinIO 节点掉线。

### 5.7 压测与验收（不接受"感觉快了"）

**必须做的场景**（沿用现有 `docs/50并发改造方案.md` §4 的验收口径并量化）：

| 场景 | 负载 | 通过标准 |
| --- | --- | --- |
| 稳定态混合 | 50 并发用户，60 分钟 | 可用性 100%（无 5xx 归因于自身）、P95 达标、无内存/连接增长趋势 |
| 生成洪峰 | 50 人同时提交问题 | 排队可见、无超时雪崩、模型服务不被打挂 |
| 上传洪峰 | 20 人同时上传 20MB 文档 | 接收 P95 ≤ 2s、队列积压可见、worker 按预期消化 |
| 混合风暴 | 生成 + 上传 + 检索 + 图分析并发 | 检索/生成互不拖垮（隔离生效） |
| 长稳 | 75 并发 × 8 小时 | 无泄漏（RSS、连接、fd、Redis 键、MinIO 对象数）、无错误累积 |
| 故障注入 | 杀主库/杀一个 MinIO 节点/杀 worker/网断 5s | 按 §5.5 矩阵表现，恢复有明确时间 |
| 数据量 | 生产规模数据（chunk、图边、会话） | 上述指标不退化（**必须用真实规模数据，不能用空库**） |

工具：k6 或 Locust 驱动 HTTP + SSE；`pgbench` 做库侧基线；MinIO 用 `warp`/`mc bench`。
压测脚本入库（`scripts/bench/`），**每次上线前后跑同一套**，结果存档对比。

## 6. 安全与合规（商用交付的门槛项）

| 项 | 要求 | 落点 |
| --- | --- | --- |
| 传输加密 | 控制台 HTTPS/TLS；内部服务（PG、MinIO、Redis、模型）也走 TLS 或独立网段 | 反代 + 各组件证书；等保三级通常要求 |
| 密钥管理 | 数据库口令、MinIO 密钥、模型 Key 不落明文配置；用 Vault 或 K8s Secret + 定期轮换 | 现在 `.env` 明文（内网可接受，对外交付不可） |
| 审计不可篡改 | 审计记录归档到 MinIO 并开 Object Lock（WORM） | `hz-audit-archive` |
| 数据分级与出境 | 明确哪些数据可进模型、是否出网；当前全内网离线，需保持 | 交付文档 |
| 越权回归 | 每次上线跑多账号越权用例（文件、会话、知识、数据表、图谱） | 现有测试集扩充为回归门禁 |
| 备份加密 | 备份与在线数据同等级（pgBackRest cipher + SSE-KMS） | §4.6 |
| 供应链 | 镜像来源固定、依赖锁定与漏洞扫描（`syft`/`grype`）、离线包校验 | 构建流水线 |
| 许可合规 | MinIO(AGPL)、Neo4j(企业版)、模型权重许可逐项确认 | 法务 + 采购 |

## 7. 路线图（阶段、依赖、验收、回滚）

> 原则：**先测量 → 再解耦 → 再扩容 → 最后编排**。每阶段独立可上线、可回滚。

| 阶段 | 内容 | 依赖 | 验收 | 估算 |
| --- | --- | --- | --- | --- |
| **P0 观测与基线** | Prometheus/Grafana/Loki 接入；loop lag、池、队列、MinIO 指标；压测脚本入库；采集现网数据量 | — | 能在压测中复现 50 并发瓶颈并给出数字 | 2–3 人周 |
| **P1 全局并发与轮询治理** | LLM 全局令牌桶 + 排队可见；限流器迁 Redis；轮询改 SSE/长轮询；21 个端点搬离事件循环；checkpoint 外置（方案阶段 2） | P0 | 生成洪峰不雪崩；空转 DB 操作 < 200/s；单进程内存不随人数线性增长 | 4–6 人周 |
| **P2 存储抽象 + MinIO** | StoragePort + LocalFs/S3 双实现；文档/生成物迁 MinIO；scratch+LRU 解析；配额；GC 与巡检；双写→回填→切换 | P1（checkpoint 外置先做，避免两处同时动文件层） | 迁移零数据丢失（逐条校验）；MinIO 停机时读路径可用；上传/下载 P95 达标 | 6–8 人周 |
| **P3 数据库层加固** | PgBouncer（先做会话语义审计）；池预算重算；只读副本；Patroni HA；pgBackRest→MinIO；大表分区与归档 | P2（对象存储先就位，备份才有落点） | 主库切换 ≤30s；PITR 恢复演练通过；连接数不再随副本数线性增长 | 5–7 人周 |
| **P4 本体/图谱层** | ontology schema + 类型版本；抽取管线带血统与 `extractor_version`；实体消解 + 人工确认；混合检索按版本权重；AGE 或专用图库（按决策门 2） | P1/P3 | 每条结论可点回原文；同实体不重复；3-6 跳查询 P95 达标 | 6–10 人周 |
| **P5 多副本与编排** | 应用无状态化收尾；SSE 跨副本续播；K8s 3 节点 + Ingress + HPA；滚动升级；混沌演练 | P1–P3 | 滚动升级零中断；杀任一应用副本用户无感；扩容后模型/DB 压力受控 | 5–8 人周 |
| **P6 交付化与合规** | mTLS、密钥管理、审计 WORM、越权回归门禁、等保材料、运维手册与演练脚本 | P3–P5 | 通过客户方等保/安全评审；交付文档齐全 | 4–6 人周 |

**总量级**：约 **32–48 人周**（1 名熟练后端约 8–12 个月；2–3 人并行约 4–5 个月）。
作为对照：如果不做 P1–P2 而直接上 K8s，投入照旧但**问题一个都不会少**，只是分布到更多机器上。

## 8. 明确不做（及理由）

| 不做 | 理由 |
| --- | --- |
| 上 PostgreSQL 19（RC）或任何非 GA 版本 | 官方标注 unsupported；扩展适配未知；等保与交付风险 |
| 依赖 SQL/PGQ 作为图能力的核心 | PG18/19 release notes 均无此特性，属于"将来可能会有" |
| 一开始就引入专用图库 | 在没有实测跳数/边数前引入，等于用运维复杂度换一个可能用不到的收益 |
| 用 FUSE 把对象存储挂给解析器 | 语义与性能不可预测，会把刚收住的解析不确定性问题放回去 |
| 引入 Kubernetes 之前先微服务化 | 服务拆分会把"库内事务"变成"跨服务补偿"，与当前单库事务的强一致优势相悖 |
| 引入消息队列（Kafka/RabbitMQ）替换 DB 行锁队列 | 50–100 人规模不需要；多一个必须 HA 的组件 |
| 多地域/多活 | 内网单机房场景无收益，复杂度极高 |
| 用 Redis 存"真相"（会话正文、文档） | Redis 是缓存与协调层；持久真相只有 PG 与对象存储 |

## 9. 我需要你确认的输入（现在就能回答的）

1. **模型服务的硬件与实测吞吐**（几个副本、多少并发、token/s、首 token 延迟）。
2. **现网数据量**：知识 chunk 数、图谱边数、会话历史行数、文档总大小与日增。
3. **服务器规格与数量**：现有几台、CPU/内存/磁盘（是否 NVMe）、万兆与否。
4. **交付形态与合规**：客户自建还是我方托管；等保等级；是否要求国产化（图库/数据库的国产权重）。
5. **许可偏好**：MinIO(AGPL) 是否可接受；是否已有 S3 兼容存储可用；图库是否已有采购。
6. **50 人是"注册用户"还是"同时在线"**，以及典型使用节律（早高峰集中提问？）。

这六项答完，§5.1 的容量模型与 §7 的估算可以给出**带数字的版本**，而不是区间。
