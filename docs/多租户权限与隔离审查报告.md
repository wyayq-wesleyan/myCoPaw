# 多租户权限与隔离审查报告（含改造方案）

- 审查对象：`huizhi-assistant-v2.2.1`（QwenPaw 多用户改造版）
- 审查日期：2026-10-21
- 审查范围：设计理念、系统架构、子模块实现、具体代码
- 交付性质：**方向与方案评审**，本报告不含代码改动
- 配套文档：`docs/50并发改造方案.md`、`docs/商用级扩展方案.md`、`docs/知识服务多租户存储设计方案.md`

## 0. 结论摘要

### 0.1 总体判断

**架构的方向是对的，但当前的隔离强度等于"所有工具里最弱的那一个"。**

QwenPaw 上游是单用户 agent 框架，"账号/租户"是后加的。改造中已经建立了正确的原则——
**身份由服务端派生、工具层强制路径与库范围、失败默认拒绝**——并且在文件工具、数据表
schema、知识检索、会话历史这几条线上实现得相当扎实。

问题在于：这些正确的边界**没有形成一个统一的执行层**，而是分散在十几个地方各自实现；
同时系统里还保留着四个"万能能力"（任意 shell、浏览器里的任意 Python、MCP 任意命令、
图表生成的 `exec`）。**只要有一个万能能力开着，其它地方做得再对，攻击者都可以绕过去。**
审计中还发现两个"第二入口"（知识服务可直连且自称身份、`auth.json` 损坏后鉴权整体跳过），
它们各自就能直接击穿全部租户边界。

一句话概括：**现在的系统在"模型守规矩"的前提下是安全的；在"模型被攻陷"的前提下不安全。**
商用与公安场景必须按后者设计。

### 0.2 三个根因（设计理念层）

| 编号 | 根因 | 具体表现 | 后果 |
| --- | --- | --- | --- |
| **R1** | **把"模型不会乱来"当成控制点** | 工具面保留任意代码/任意网络/任意命令；治理策略默认 `allow`；图表工具用 `exec` 拼接模型输入 | 提示词注入即可获得与进程同权限的执行能力，所有应用层边界失效 |
| **R2** | **同一类边界分散实现** | "账号根目录"在文件工具里用 `resolve+relative_to`（正确），在 shell 里用正则字面匹配（可绕过），在项目目录/分享/备份里各自实现或缺失 | 隔离强度取决于最弱的实现点，且新增功能容易漏掉边界 |
| **R3** | **存在绕过前门的"第二入口"** | 知识服务信任 `X-User-Id` 且 key 可空、host 网络对局域网开放；`auth.json` 缺失时鉴权整体跳过；MCP 不在工具权限体系内 | 不经过主应用授权链也能读写他人数据，或直接获得管理员身份 |

### 0.3 风险统计

| 级别 | 数量 | 含义 |
| --- | --- | --- |
| **P0** | **12 项** | 只用自己合法账号 + 现有能力即可跨租户读写删，或直接拿到管理员权限；其中 2 项带条件（线上默认口令未改、图模式启用） |
| **P1** | **28 项** | 需要特定条件（工具开放、默认配置、管理员操作、竞态），或造成跨租户完整性/可用性破坏，或构成 XSS→接管链条 |
| **P2** | **54 项** | 纵深防御缺口、信息泄露、资源耗尽、账号内案件越权 |
| P3 | 1 项 | 数据残留等卫生问题 |
| 合计 | **95 条** | 另有 `TOOL-05` 与 `TEN-01` 是同一条（shell 无沙箱），只计一次 |
| 已确认正确 | 80+ 条 | 各节 B 部分列出，不要改，改动时作为回归基线 |

（详细清单见 §4。同一条缺陷在多路审计中重复出现的已合并。）

### 0.4 五个必须先定的决策

这些是方向问题，不定下来后面的实现会反复：

| 编号 | 决策 | 建议 |
| --- | --- | --- |
| **D1** | 普通用户是否允许"任意代码执行 / 任意网络访问"？ | **默认不允许**。代码执行只对管理员开放或放进受限沙箱；否则无法承诺租户隔离 |
| **D2** | 安全边界主要放在哪一层？ | **应用层只做第一层**：必须有 OS（用户/命名空间/网络）与数据库（角色/RLS）兜底。只靠代码判断迟早被绕过 |
| **D3** | 服务间是否接受"调用方自称身份"？ | **绝不**。身份只来自签名令牌/mTLS，或只允许受信服务调用（回环 + 密钥） |
| **D4** | admin 是否旁路？ | **不旁路**（与你之前定的口径一致）。运维动作走 break-glass + 双人审批 + 全量审计 |
| **D5** | 是否现在引入"密级"模型？ | 用户隔离 ≠ 密级隔离。若客户要求"同一账号内不同文件密级不同"，ABAC 必须单独做，不能靠租户隔离替代 |

### 0.5 改造顺序（一页）

```
第一步（止损，1–2 周）：关掉万能能力 + 堵住两个第二入口
    ├─ 普通账号禁用 shell / browser / MCP；图表去 exec；git 参数加固；导入文件名修复
    ├─ 知识服务强制密钥/仅回环；auth.json 损坏即拒绝服务；默认口令拒启
    └─ secret 移出业务容器

第二步（收口，3–6 周）：把所有边界收敛到一个授权层
    ├─ 统一 Authorizer：所有 "resource_id / path / agent / session" 走同一套归属校验
    ├─ 数据库：每账号角色 + RLS + 只读角色；SQL 解析器白名单
    ├─ 知识服务：签名令牌 + workspace 服务端映射
    └─ 前端：XSS 修复 + 按账号隔离本地存储

第三步（加固，6–10 周）：把执行面做成真正的沙箱
    ├─ 每账号 UID / 每会话命名空间 / 默认无网络 + 出口白名单
    ├─ 不可篡改审计（WORM）+ 异常访问检测
    └─ 密级标签 + ABAC + 外发审批
```

## 1. 审查口径

### 1.1 威胁模型（这是本报告与普通代码审查最大的区别）

**假设攻击者：**

1. 拥有一个合法普通账号，能正常登录、建智能体、上传文档、使用被授权的工具；
2. 能通过提示词注入（直接指令、文档正文、文件名、网页内容、工具返回值）让模型执行任意工具调用；
3. **假设模型完全服从攻击者**——不依赖模型"不够聪明"或"拒绝配合"；
4. 能在自己可写的目录里放符号链接、构造畸形文件、发起任意内网请求（在工具能力允许范围内）；
5. 不能直接读宿主机、不能改容器镜像、不能物理接触服务器。

**判定标准**：在上述假设下，攻击者能否读到/改到/删到他人数据，或以他人身份执行操作。
**能，就是缺陷；不能，才算隔离。**

### 1.2 严重度定义

| 级别 | 定义 |
| --- | --- |
| **P0** | 在上述假设下可直接跨租户读写删，或取得管理员权限；或无需任何特殊配置即可利用 |
| **P1** | 需要特定条件（某工具被启用、默认配置未被覆盖、管理员误操作、并发竞态），或造成跨租户完整性/可用性破坏，或构成"XSS→令牌→接管"完整链条 |
| **P2** | 纵深防御缺失、信息泄露、资源耗尽、单账号内案件（path）之间越权 |
| **P3** | 卫生问题、可维护性风险 |

### 1.3 证据与复核标记

每条发现标注复核状态：

- **✅ 已复核**：我本人读过对应代码，确认描述属实；
- **◐ 静态可构造**：代码事实已由子审计给出 file:line 确认，或已由我读过关键片段；
  利用链是静态分析得出，未在目标环境实测；
- **○ 待现网确认**：结论依赖线上配置/数据，代码无法单独判定。

**本报告没有在目标服务器上做任何验证或改动。** 所有"攻击路径"都是代码分析结论，
实施修复前应在隔离环境复现一次。

### 1.4 不在范围

宿主机与内核安全、物理安全、模型权重与推理服务自身的安全、供应链（镜像/依赖）的完整审计、
客户侧网络与等保测评。这些在 §7 以"需要现网确认"的形式列出。

## 2. 设计理念层（大方向）

### 2.1 已经正确的原则（必须保留）

| 原则 | 现状 |
| --- | --- |
| 身份只由服务端派生 | 主应用从 Bearer token 解析 username，注入 request context；知识工具不接受模型传入 owner |
| 失败默认拒绝 | 文件工具 `resolve_account_username` 在鉴权开启且无身份时抛错，不回退 admin；路径 API 无身份直接 401 |
| 路径 containment 用解析后的真实路径 | `ensure_inside_account` 用 `Path.resolve()` + `is_relative_to(root)`，静态符号链接指向外部会被拒 |
| 数据库按账号物理隔离 | 每账号独立库 + 路径 `p_<uuid>` schema；连接池按 (db, schema) 分键，checkout 时重新 pin `search_path` |
| 知识服务不因 `is_admin` 放宽 SQL | 所有 store 查询只按 `owner_id` 过滤，`is_admin` 未参与任何 SQL |
| 会话/历史按 workspace 隔离 | `platform.conversation_history` 所有查询带 `workspace_key` |
| 硬编码的"admin 回退"已被识别为问题 | 数据表接口里的 `or "admin"` 是残留，本报告要求清除（§4.2） |

**改造时这些是回归基线**：任何方案不得以"简化"为理由拆掉它们。

### 2.2 根因 R1：万能工具让应用层边界失去意义

系统里有四个能力，本质上都是**任意代码执行**或**任意网络访问**：

| 能力 | 位置 | 等价于 |
| --- | --- | --- |
| `execute_shell_command` | `agents/tools/shell.py` | 进程用户（root）的 shell |
| `browser(code=...)` | `agents/tools/browser.py:32` + `browser/execution/worker.py:602` | 进程用户（root）的 Python 解释器（`__builtins__` 完整） |
| MCP `stdio` 配置 | `app/mcp/schemas.py:78-114` + `drivers/handlers/mcp_stateful_client.py:703` | 进程用户（root）的任意子进程 |
| `generate_chart` 的 `exec` | `agents/tools/generate_chart.py:263` | 主应用进程内的 Python 执行 |

当前部署的前提（已核实）：容器 `Config.User` 为空（**root**）、`security.sandbox_enabled=False`、
镜像内**没有 bwrap**、`/app/working.secret` 与所有账号目录在同一个文件系统。

结论：**在 R1 解决之前，讨论"文件工具是否隔离"没有意义**——绕过它只需要一行
`python -c`。这也是本报告把"关闭/沙箱化万能能力"放在第一步的原因。

### 2.3 根因 R2：同一类边界分散实现

以"账号根目录"为例，至少存在五种实现：

| 实现方式 | 位置 | 强度 |
| --- | --- | --- |
| `resolve()` + `relative_to()` | `agents/tools/user_files.py:56` | 强（唯一正确的一种） |
| 正则匹配字面量 `workspaces/<name>` | `agents/tools/shell.py:51-95` | 弱（源码注释自认不是边界） |
| 数据库 owner 条件 | `platform_store/*`、`knowledge-service/store.py` | 强（但有的接口漏了 owner） |
| 字符串 `startswith` 前缀 | `routers/workspace.py:1902` | 中（`u_abc` vs `u_abcdef`） |
| 完全没有 | `paths.bind_resource`、`data_tables.import_api` | 无 |

**后果**：安全评审不能问"系统隔离了吗"，只能问"这个具体入口隔离了吗"；每加一个功能
就多一个漏点。改造的核心不是再加检查，而是**把所有资源访问收敛到同一个授权函数**。

### 2.4 根因 R3：第二入口

| 第二入口 | 为什么危险 |
| --- | --- |
| 知识服务 `18100` | 它信任 `X-User-Id`/`X-Is-Admin`；`KNOWLEDGE_API_KEY` 为空时完全放行；host 网络下同网段可达。**绕过主应用的整条授权链** |
| `auth.json` 缺失/损坏 | `has_registered_users()` 把"读不到"当成"没有用户"，`_should_skip_auth` 因此跳过全部 `/api/*` 鉴权；注册端点在"无用户"时开放，可重新注册一个 admin |
| MCP | 不在工具权限体系里：普通用户创建后，agent 加载时以服务进程身份 spawn 任意命令 |
| 备份/恢复 | 全局 admin 能力，包含所有账号工作区与可选 secrets；按你的口径 admin 不应旁路 |

### 2.5 隔离强度模型

| 级别 | 描述 | 本系统现状 |
| --- | --- | --- |
| L0 | 靠前端隐藏、后端不校验 | 局部（管理菜单） |
| L1 | 应用层按 owner 字段过滤 | **当前主体** |
| L2 | 应用层统一授权 + 数据层（DB 角色/RLS、对象存储前缀）强制 | 文件工具达到，其它未达 |
| L3 | 执行面 OS 级隔离（独立 UID/命名空间/默认无网络），数据层强制 | 未达 |
| L4 | 密级标签 + ABAC + 不可篡改审计 + 异常检测 | 未达 |

**目标：商用交付至少 L3；涉密场景 L4。** 当前不是"某些细节没做好"，而是**整体停在 L1**，
且被 R1/R3 击穿后实际接近 L0。

### 2.6 五个决策的展开

**D1 万能能力的产品定位。** 三种选择：

| 选择 | 后果 |
| --- | --- |
| A. 普通用户禁用 shell/browser/MCP | 隔离可承诺；但"数据分析/代码编写"类场景受限 |
| B. 保留但放进真沙箱（独立容器/UID、默认无网） | 能力与安全兼得；工程量大（见 §6.5） |
| C. 保留现状 | 无法对客户承诺租户隔离 |

建议：**先 A 止损，再 B 作为增值能力**。不要停在 C。

**D2 边界层次。** 只靠应用代码判断 `relative_to` 有两类无法根治的问题：TOCTOU（检查后、
使用前被替换）和"开发者忘了调用"。必须有 OS/DB 兜底：每账号独立 UID 或独立挂载命名空间；
数据库每账号独立角色 + RLS。应用层检查用于"给出可读错误"，不作为最后一道门。

**D3 服务间身份。** `X-User-Id` 这种"自称身份"在单机单租户时代没问题，多租户下等于没有
身份。方案：主应用签一个短期 JWT（含 user、path 集合、过期、受众），知识服务验签；
或者知识服务只监听回环 + 强制密钥，并由主应用作为唯一入口（更简单，但没有跨机扩展性）。

**D4 admin 语义。** 已确认的方向：admin 可以管理用户与系统配置，但不旁路读取他人资料。
需要区分两类动作：
- **日常管理**（建号、授权、看统计）→ 只读元数据，不读内容；
- **break-glass**（恢复备份、排障）→ 显式开关 + 二次确认 + 双人审批 + 全量审计 + 事后通知。

**D5 密级模型。** 租户隔离解决"横向"（A 看不到 B），密级解决"纵向"（低密级用户/会话
看到高密级内容）与"聚合"（合法用户把多条低密级信息拼成高密级结论）。后者需要：
数据标签（密级、类别、来源、期限）+ 策略引擎 + 检索时强制过滤 + 输出前脱敏/审批。
这是独立于租户隔离的一层，**不能等到"以后再说"再返工**——标签要随数据一起产生，
补标签比补索引贵得多。

## 3. 系统架构层

### 3.1 信任边界（当前实际形态）

```
                 ┌──────────────────────────────────────────────┐
   浏览器 ──────▶ │ 反向代理（可选）                              │
                 └──────────────────┬───────────────────────────┘
                                    │
   ┌────────────────────────────────▼────────────────────────────────┐
   │ 主应用容器（root，host 网络）                                    │
   │  ┌──────────────┐  ┌──────────────────────────────────────────┐ │
   │  │ uvicorn 进程 │  │ 工具执行（同一进程/同一用户）              │ │
   │  │  - 认证       │  │  shell / browser(code) / chart exec / MCP │ │
   │  │  - 授权       │  │  → 可读 /app/working.secret 与全部账号目录 │ │
   │  └──────┬───────┘  └──────────────────────────────────────────┘ │
   │         │                                                        │
   │         ├─▶ PostgreSQL（127.0.0.1:15432，共享角色）               │
   │         └─▶ 本地文件系统（所有账号工作区 + secret + 备份）        │
   └──────────────────────────────┬───────────────────────────────────┘
                                  │ host 网络
        ┌─────────────────────────┼──────────────────────────┐
        ▼                         ▼                          ▼
  知识服务 18100（可选 key）   LightRAG 9621          模型服务 9988
  信任 X-User-Id 头           局域网可达                 局域网可达
```

**三个关键事实**：

1. **控制面与执行面在同一个进程/同一个 OS 用户里**——执行面的任意代码等于控制面的权限；
2. **数据面（PG、文件）与执行面之间没有 OS 边界**——只能靠代码自觉；
3. **服务间是"平面网络"**——任何能发请求的组件都能直接调用其它服务，没有身份。

### 3.2 数据面隔离现状

| 资源 | 隔离机制 | 评价 |
| --- | --- | --- |
| 账号工作区 | `workspaces/<hash(username)>` + 文件工具 resolve 检查 | 应用层达标；无 OS 兜底 |
| 会话历史 | `platform.conversation_history` 按 `workspace_key` | 达标 |
| 知识文档 | `documents.owner_id` + 文件按 `space_id` 目录 | SQL 达标；文件路径由服务端生成 |
| 知识图谱 | LightRAG `workspace` 进 13 张表主键 | 存储层达标；**接口层未校验 workspace 归属**（§4.5） |
| 数据表 | 每账号独立库 + `p_<uuid>` schema | 物理隔离达标；**SQL 守卫可被字符串/动态函数绕过**（§4.6） |
| 路径/案件 | `platform.paths` + `resource_bindings` | 路径归属达标；**绑定资源未校验 owner**（§4.7） |
| 审计 | `platform.audit_events` | 无 WORM；应用账号可删；覆盖不全（§4.1） |
| 备份 | 全局 admin | 含所有账号；与"admin 不旁路"冲突（§4.8） |

### 3.3 控制面隔离现状

- 认证中间件覆盖 `/api/*`，公开路径显式白名单——**正确**；
- 所有 agent 作用域路由走 `require_owned_agent_id`——**正确**；

## 5. 七条关键攻击链

单点修复不够，因为下面每条链只需要一个入口。按当前配置，**前三条不需要任何特殊条件**。

### 链 1：提示注入 → 任意 Python → 管理员

```
恶意文档/网页 → 模型调用 browser(code="__import__('os')...")
→ 以 root 读 /app/working.secret/auth.json + .master_key
→ 或直接 create_token('admin')
→ 调 /api/auth/users、/api/envs、/api/backups
```
**根因**：TOOL-01 + AUTH-02 + D-01。

### 链 2：提示注入 → shell → 删 auth.json → 重新注册

```
shell: rm /app/working.secret/auth.json
→ 中间件 has_registered_users()=False → 跳过全部鉴权
→ POST /api/auth/register {evil} → role=admin
```
**根因**：TEN-01 + AUTH-01。

### 链 3：提示注入 → MCP → 任意命令

```
POST /mcp {transport:"stdio", command:"/bin/sh", args:["-c","..."]}
→ agent 重新加载时 spawn
```
**根因**：TOOL-02。**不需要 shell 工具权限**，所以只禁用 shell 不够。

### 链 4：直连知识服务

```
curl http://<lan>:18100/v1/spaces -H 'X-User-Id: victim'
curl http://<lan>:18100/v1/documents/<id>/file -H 'X-User-Id: victim'
→ 下载他人全部知识文档
（或 /v1/search 带 workspaces 读他人图谱）
```
**根因**：KB-01 + KB-02 + host 网络 + 空 key。

### 链 5：跨租户资源绑定

```
PUT /api/paths/<自己的path>/resources {"resource_kind":"data_table","resource_id":"<B的表>"}
→ 物理 SET SCHEMA 把 B 的表移进 A 的 schema（或使 B 的表在 B 的路径消失）
```
**根因**：PATH-01。

### 链 6：前端 XSS → 令牌

```
恶意 Mermaid/docx → 注入脚本 → 读 localStorage 的 qwenpaw_auth_token
→ 以受害者身份调用全部 API
```
**根因**：FE-01/FE-03 + FE-02。

### 链 7：默认口令

```
POST /api/auth/login {"username":"admin","password":"Admin@123456"}
```
**根因**：AUTH-03（若线上未覆盖）。

> **共同点**：每条链都只需要一个缺口。这就是为什么本报告主张"先关万能能力 + 堵第二入口"，
> 而不是逐条修补业务接口。

## 6. 改造方案

### 6.1 目标状态与验收标准

**目标**：在"模型完全被攻陷"的前提下，任何普通账号**无法**：
1. 读取/写入/删除任何其他账号的文件、会话、知识文档、数据表；
2. 以其他账号身份执行任何操作；
3. 取得管理员权限；
4. 读写 `/app/working.secret`、其他账号目录、平台库敏感表；
5. 通过任何工具（含新加的工具）绕过上述约束。

**验收方式**：§9 的红队用例集全部"拒绝且可审计"；并且**把控制回退后用例必须重新通过**
（变异验证）。

### 6.2 B1 身份层

| 措施 | 对应问题 |
| --- | --- |
| 身份唯一来源 = 服务端签发的短期令牌；禁止客户端传 `user_id/session_id/owner` | AG-02、FE-07 |
| 服务间：主应用签 JWT（user、paths、aud、exp），知识服务验签；或知识服务仅回环 + 强制密钥 | KB-01、D-03 |
| 认证状态损坏（auth.json 读失败）→ 拒绝服务，不降级 | AUTH-01 |
| 用户唯一 ID 与用户名解耦（改名/删号重建不复用数据） | AUTH-08/09 |
| 令牌版本（`token_version`）+ 改密/重置即失效；固定绝对/空闲超时 | AUTH-04/15 |
| 口令 Argon2id；保留名禁止；默认口令拒启 | AUTH-03/07/08 |
| 登录限流按 IP+账号，未认证方不能锁任意账号；未知用户做假哈希 | AUTH-06/16 |
| WebSocket 与所有非 `/api` 路由纳入统一鉴权 | AUTH-20/21 |

### 6.3 B2 授权层（核心）

**新增一个统一授权模块**（不是又一个工具级检查），定义：

```text
Principal   = { user_id, role, paths[], session, request_id }
ResourceRef = { kind: file|document|table|agent|chat|skill|path|backup|mcp,
                id, owner_id, path_id?, tenant_id? }

Authorizer.check(principal, action, ref) -> allow | deny(reason)
```

规则：

1. **所有对外接口与工具**在访问资源前必须构造 `ResourceRef` 并调用 `check`；
   禁止直接按 id 查库（静态检查：所有 `where id=%s` 的位置必须同时有 owner 条件，
   或来自已经过 `check` 的 ref）。
2. **默认拒绝**：资源不存在、归属不明、`resource_kind` 未知 → deny。
3. **admin 不旁路**：`role=admin` 只影响"管理动作"，不影响"读他人内容"；
   后者必须走 break-glass 许可。
4. **资源归属随资源走**：`resource_bindings` 增加 `owner_id`；移动/绑定/解绑都校验。
5. **服务端生成标识**：session_id、chat_id、document_id、workspace 名全部服务端生成，
   客户端只能引用不能构造。
6. **工具权限与工具实现分离**：工具可用性与"工具能做什么"都由 Authorizer 决定，
   新增工具必须注册 `resource_kind` 与所需 action。

落地方式：先在路由层加一层依赖（FastAPI dependency），再把工具层逐个接入；
用一张"资源类型 × 动作"的矩阵做验收（§9 的用例表就是它的测试）。

### 6.4 B3 执行层

**短期（P0）**
- 普通账号默认关闭：`execute_shell_command`、`browser`、`mcp`；
- `generate_chart` 删除 `exec`（直接调 matplotlib）；
- `git clone`：URL 白名单（https/ssh）+ `--` + 拒绝 `-` 开头 + 私网/元数据黑名单；
- MCP：仅 admin，`command` 白名单，远程 transport 禁私网；
- secret 目录移出业务容器可读范围（独立 init 容器/主机路径 + 仅启动时读取）。

**中期（P1）**
- 引入 **执行面沙箱**：
  - 每个会话/任务一个受限进程：独立 UID（非 root）、bubblewrap（镜像需安装）、
    只读根文件系统、仅挂载本账号目录、独立 `/tmp`、默认无网络（白名单出站）；
  - `browser(code)` 改成受限 RPC 面（导航/点击/输入/截图/取文本），
    不再接受任意 Python；或至少在沙箱里跑；
  - 工具进程与主进程分离（同机不同容器/不同用户），主进程不持有也可不暴露 secret。
- 工具超时/资源上限/并发闸门统一（沿用现有 pids/线程池经验）。

**长期（P2）**
- 执行面与模型服务、数据库分网段；出站经审计代理；
- 每个租户独立执行工作卷，任务结束后销毁。

### 6.8 B7 审计与检测（没有它，前面都是"事后才知道"）

1. 审计覆盖：登录/登出/失败、注册、建号/删号/禁用、改密/重置、权限变更、
   工具调用（含参数摘要与结果大小）、资源访问（尤其是跨账号命中）、配置变更、break-glass。
2. 每条记录：who、role、IP、UA、request_id、action、resource_kind/id/owner、decision、reason。
3. 存储：独立库/独立凭据；追加写；应用角色无 DELETE；定期归档到 MinIO 并开 Object Lock。
4. 检测规则（实时告警）：
   - 同一账号在短时间内访问多个不同 owner 的资源；
   - 工具调用出现跨账号路径/资源 id；
   - 权限变更/改密/删号；
   - 大量下载/导出；
   - 非工作时间的批量读取；
   - 执行面访问 secret 路径（OS 审计）。
5. 保留期与隐私：按客户要求；日志内不写文件正文与密钥。

### 6.10 防回归机制（与既有口径一致）

1. **红队用例集**（§9）作为 CI 门禁；

## 8. 明确不做

| 不做 | 理由 |
| --- | --- |
| 用"更强的模型"当安全控制 | 模型只降低概率，不构成边界（§1.1） |
| 只在应用层加更多 `if owner ==` 判断 | 解决不了 TOCTOU、新增入口遗漏、万能工具绕过 |
| 为了隔离把所有功能砍掉 | 应分层：默认安全 + 按角色/沙箱开放能力 |
| 立即重写为微服务 | 当前问题在边界实现，不在服务拆分；拆了只会把库内事务变成跨服务补偿 |
| 引入第三方网关解决全部问题 | 网关能做认证与限流，做不了"这条 SQL 只能读本账号 schema" |
| 只在交付前做一次渗透测试 | 需要持续门禁（§6.10），否则下一个功能又漏 |
